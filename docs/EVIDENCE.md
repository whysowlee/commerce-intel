## 1. 접근 정책

- 무신사 robots.txt: 일반 봇 `Disallow: /`이지만 **`Claude-User`·`Claude-SearchBot`은 `Allow: /` 전면 허용**
- 29CM robots.txt: `*`에 `Allow: /`, 로그인 영역만 차단
- 두 사이트 모두 403·캡차·봇 챌린지 없이 전 페이지 200 확인

  `/exec/front/`(리뷰 더보기) — 후기 수집 불가의 근거

## 2. 수집 경로 (A=API, B=브라우저)

### 경로 반전 이력
v2~v5 A 우선 → v6 B 우선("다 뜯어고쳐") → **v16 A 우선 재반전**(2026-07-30 사용자 결정).
A 우선의 근거: ① 요청 1번=목록 1페이지, 파싱 함정 없음 ② 화면 전용이던 값들이 API로
열림(무신사 실시간 지표 원시값 API — 보는 중·조회수·누적판매·브랜드 하트) ③ 스킴 변화
대응을 브라우저가 아니라 문서 갱신 절차(어댑터 개정)가 담당.

### 경로 A의 구조적 누락 — 29CM BEST API (v6 확인, 핵심 실측)

인사일런스: 화면 총계·브라우저 순회 **435** vs BEST API 정렬 4종 합집합 **422** (누락 13건/3.0%,
그중 품절 11건. 유령 0건 — 수집분 ⊂ 화면집합).
**누락 원인 특정 실패** — 품절 필터 아님(수집분에 이미 품절 120건), 저반응 아님(누락분
좋아요 4~39·후기 0~3은 수집분이 커버하는 구간). 품절 쪽 3배 편향만 있음(85% vs 28%).
→ **어떤 상품이 빠질지 예측 불가 = 화면 총계 대조 없이 전량 주장 불가.**

부속 실측:
- `hasNext=false` 도달·정렬 합집합 포화(422에서 포화)는 **완전성 근거가 아니었다** —
  두 근거를 모두 만족한 422가 실제 435의 부분집합
- 랭킹 창을 좁히면 카탈로그가 잘린다: `MONTHLY`+`CLICK` 422 / `DAILY` 409 / `WEEKLY` 365 /
  **`HOURLY` 26** (카탈로그의 94% 소실). `MONTHS_3`·`MONTHS_6`은 HTTP 500
- 422건 중 유니크 421 — **랭킹순 페이지네이션 중 순위 요동으로 중복이 온다**, dedup 필수
- 카테고리는 코드로만 옴(`extraInfo.categories[]`), 이름은 트리 API로 해석,
  `smallCategoryCode`가 `null`인 상품 있음 → 중분류 폴백
- 브랜드 ID 확증: 브랜드 페이지 `__NEXT_DATA__`에 `{"brandId":1642,"nameKor":"인사일런스"}` 서버 렌더
- DTO 프로브 성질: 없는 필드는 200+무시, **실존 필드는 400과 함께 필수 하위 필드명을 알려준다**

### 순환 검증 사고

BEST API는 총계를 안 주는데 `source_total`에 수집 건수를 넣어 "총계 대비 오차 0.0% 통과"가
된 실제 사고. → `source_total`에는 수집 절차와 **독립인** 총계만. 못 얻으면 `null`.

### 랭킹 코드가 경로별로 다르다 (무신사)

- 경로 A: 대분류 3자리(바지 `003`) 정상
- 경로 B(화면): 6자리만(바지 전체 `003000`). `003`을 주면 에러 없이 **다른 랭킹**
  (`sectionId=200&categoryCode=000` = NEW·전체)이 온다. 상태코드로 알 수 없고 1위 상품을
  봐야 안다(재현 2/2)

## 3. 완전성 검증 — 기본 필터·총계 함정

### 목록 기본 필터가 사이트마다 다르다 (최대 오차원)

| 사이트 | 브랜드 목록 기본값 | 인사일런스 실측 |
|---|---|---|
| 무신사 | **품절 제외** | 563 → `&isSoldOut=true`면 **2,022** |
| 29CM | **품절 포함**(필터 이름이 `품절상품 제외`) | 435 (품절 131) |
| 자사몰(Cafe24) | 품절 포함 + **배지 없음** | 목록 192개에 품절 문자열 0건인데 실제 품절 존재(`product_no=7489`) — 상세 JSON-LD `offers`로만 판정 |

- 필터 불일치의 결과: 무신사(품절 제외)와 비교하면 "29CM 단독 83건" → 품절 포함으로 맞추자
  90건이 무신사 품절과 매칭돼 **단독 0건**. 단독 입점 분석이 통째로 필터 산물이었다
- 화면 총계도 필터의 함수다 — 563은 "품절 제외 총계"였고 대조를 정상 통과했다.
  총계를 기록할 땐 필터 상태를 함께 남겨야 근거가 된다
- 무신사 파라미터 스윕: `soldOut`·`includeSoldOut`·`excludeSoldOut`·`saleStatus`·`soldOutYn`·
  `onSale`·`status`·`displayStatus` **전부 무효**, `isSoldOut=true`만 총계를 바꾼다(261→440).
  응답이 false/true 혼합이므로 의미는 "품절만"이 아니라 **"품절 포함"**.
  `soldOut=true`는 조용히 무시되고 563이 온다
- 품절 포함 영향: 로우클래식 261→440(+41%), 슬랙스 여성 10~20만원 1,903→3,004(+37%).
  랭킹은 해당 없음(101건 중 품절 0)
- 품절 이력 포함 시 같은 정규화 이름이 여러 번 나온다(실측 3건, 재등록) —
  합집합 행 수 < 수집 건수는 정상

### 무신사 브랜드 URL이 두 개다

`/brand/{slug}`는 브랜드 홈(추천·기획전)이라 128개에서 끝나고, 전 상품은
`/brand/{slug}/products`로 563 = 화면 총계. 둘 다 200이고 둘 다 상품이 보이므로
**총계 대조 없이는 128/563만 모은 것을 알 수 없다.**

### 자사몰(Cafe24) 전량 확보

- `ALL` 카테고리 하나로는 부족: 인사일런스 남 `ALL` 222 + 여 `ALL` 206 = 합집합 428인데
  `SEASON OFF` 349 중 **127건(23%)이 `ALL`에 없다.** 전체 합집합 555.
  루트 카테고리 없음(`cate_no=1`·`/product/list.html` 404)
- 화면 총계가 아예 없다 → `source_total = null`, 완전성 근거는 "모든 상품 카테고리 소진 +
  각 카테고리 `btnNext=#none` 도달". 어느 카테고리에도 안 걸린 상품은 구조적으로 놓치며
  검출 불가 — 한계를 notes에 남긴다
- 실측 스토어: 인사일런스(insilence.co.kr)·2000아카이브스(2000archives.com), 둘 다
  `cfa-js.cafe24.com` 신호로 Cafe24 확인
- 후기 지표: robots 차단(§1) + 인사일런스는 외부 위젯(크리마)이 상세에 마운트조차 안 되고
  Cafe24 기본 후기 게시판 비활성 → 후기·평점·좋아요·조회수·누적판매 전부 수집 불가

### 무신사 카테고리 PLP

- **page≥2 직접 조립은 403** — page=1 응답의 `nextPageUrl`(hmacId 서명 포함)을 따라가면 200.
  페이지 URL을 조립하지 말고 항상 `nextPageUrl` 체인
- 화면 URL은 `page` 파라미터를 무시하고 항상 1페이지 렌더(무한 스크롤)
- `minPrice`/`maxPrice`는 API·화면 모두 동작 확인(총계가 실제로 준다)
- **화면은 스크롤하면 성별 필터를 잃는다**: 칩(`여성`)·총계(3,004)는 유지되는데 page=2부터
  요청이 `gf=A`로 나간다. 끝까지 스크롤하면 5,010건, 그 안에 남성 2,082건.
  UI `여성` 버튼을 눌러도 `gf=A`로 되돌아간다 → 성별 축은 PLP API만 끝까지 지킨다
  (`gf=F` totalCount 3,004 = 수집 3,004)

## 4. 필드·값

### 판매가 = 전 회원 공통 쿠폰적용가 (v8)

- 무신사: 상세 안내 문구("모든 회원이 사용 가능한 상품 쿠폰 중 최대 할인 쿠폰 기준 산정")로
  확인. `price_sale`=`finalPrice`, `discount_rate`=`finalDiscount`.
  구 `price`/`saleRate`(쿠폰 전)로는 로우클래식 261개 중 할인 중 **4개**, 쿠폰가로는 **115개** —
  5% 쿠폰 102개를 "할인 없음"으로 기록하고 있었다
- 무신사 랭킹 API는 원래부터 쿠폰적용가(`info.finalPrice`·`discountRatio`, PDP 대조
  6007700: 134,400/20%) — 기존 스냅샷 정상
- 29CM: 가격이 세 개다 — `originalPrice` 54,000 / `sellPrice` 43,200 / `displayPrice` 37,160.
  `price_sale`=`displayPrice`, `discount_rate`=`saleRate`(같은 기준이라 재계산 불요).
  `sellPrice`로 담으면 쿠폰만 걸린 상품이 "할인 없음"이 된다(로우클래식 100개 중 22개 상이)
- **29CM 상세의 `totalDiscountedItemPrice`는 개인화 가격**(「나의 구매 가능 가격/첫 구매가」,
  앱전용·신규 쿠폰 포함) — 58건 중 32건(55%)이 `displayPrice`와 불일치. 판매가는 목록 경로에서
- 29CM에는 산정 근거 문구가 아예 없어 동작으로 판정: ① 화면 판매가=`displayPrice` 4/4
  ② 가격을 정하는 상품쿠폰 43건 전부 무조건부(첫구매·등급·신규·앱전용 0건)·선착순 제한 없음
  ③ 최대 할인 쿠폰 자동 선택이 무신사와 동일

### 축약 vs 구간 (v15)

| 표기 | 예 | 참값 범위 | 상대 오차 |
|---|---|---|---|
| 축약 | `1.2천` / `판매 64만개` | 1,150~1,249 / 635,000~644,999 | ≤ ±4% (자릿수 클수록 작다) |
| 구간 | `300회 이상 (최근 1개월)` | 300~∞ | 무한 |

축약은 정수 파싱 허용(v6 금지를 뒤집음), 구간은 금지 유지. 소급: 기존 스냅샷 44개의

### 평점 스케일

무신사는 한 사이트 안에서 두 개다 — 목록 `reviewScore` 0~100, 상세 `satisfactionScore` 0~5.
화면(경로 B)은 0~5. 5점 만점으로 통일하며, 읽은 경로에 따라 변환이 달라진다.

### 기타 필드 함정

- 상품 상세 `snapReviews.aggregations`의 `viewCount`/`likeCount`는 **스냅 게시물 지표**다 —
  상품 조회수가 아니다
- 29CM 상세는 마크다운 변환기를 거치면 빈 껍데기로 보이지만 원본 HTML에 JSON-LD가 있다

  빈 결과가 나올 때까지 돌아 판정
- 리뷰 페이지 시작 번호: 무신사 1부터, 29CM 0부터. 무신사 리뷰 `pageSize` 상한 20(21↑는 400)

  (`BRAND`/`CATEGORY`)
- 죽은 URL: `store.musinsa.com/app/contents/bestranking`, `search.musinsa.com/ranking/best`,
  `/brands/`(복수형)

## 6. 경로 B(브라우저) 함정 — 전부 "조용히 틀리는" 종류

- **목록 DOM 가상화**: 무신사 PLP에서 페이지 높이 4,518→260,538px(57배)로 늘어도 DOM 내
  상품 링크 132~144개 고정(66~72 상품 창), 노드 4,680개·heap 132MB 평탄.
  끝까지 스크롤 후 한 번 읽으면 마지막 66개만 잡힌다 → **매 스텝 수집, product_id 누적**
- **스크롤 종료 = 3연속 무증가**: 랭킹은 끝에서 증가가 완전히 0(8스텝 연속 0 확인).
  무신사 카테고리 PLP는 자연 종료가 없다(24,686개까지 감속 없이 계속) → 상한 마감과
  목록 종료를 구분해 기록. 29CM은 `&page=` 페이지네이션이라 빈 페이지+"검색 결과가
  없습니다"로 결정적으로 끝난다
- **카드 경계**: 링크 수로 세면 실패(카드에 이미지·상품명 2개 링크), 가격 텍스트 기준으로
  올라가면 6카드 행 컨테이너까지 올라간다 → **고유 product_id가 1개인 가장 가까운 조상**.
  29CM 카드에는 가격에 `원`이 없다(`57,960`) — `원` 기준이면 `ul`까지 올라가 이웃 카드가
  섞인다. 29CM 카드는 `li`, 카드당 `/catalog/` 링크 4개
- **HTML 문자열 정규식 파싱 금지**: 중첩 태그에서 첫 닫는 태그에 끊겨 조용히 놓친다
  (608개 중 574개만 잡힌 실측)

## 7. 인코딩 (실제 사고)

- 무신사 상품 상세 HTML에 `<meta charset>` 선언이 없다. UTF-8 본문이 latin-1로 디코드되면
  한글이 `ë ë`처럼 깨지는데 **숫자 필드는 멀쩡해 결측률 검증을 통과한다**
- 사고: 인사일런스 라인시트 `category` 564행 전부 깨진 채 리포트까지 나감.
  37종 중 24종은 latin-1→UTF-8 역변환 복구, 끝 바이트 유실 13종은 대표 상품 PDP 재수집으로
  복구(추측 채움 없음)
- **깨진 문자열에 `strip()` 금지** — mojibake 끝 바이트 `\xa0`·`\x85`를 공백으로 보고
  지우면 역변환 복구가 불가능해진다
- 검증기가 UTF-8 선두+연속 바이트 패턴으로 FAIL(exit 2)을 낸다. 제대로 디코드된 한글은
  latin-1 인코딩이 아예 안 되므로 오탐 없음

## 8. 랭킹 모니터링

- **원본 갱신 주기**: 무신사 REALTIME 약 30분(더 자주 찍어도 중복), 29CM `HOURLY` 1시간
- **과거 소급 불가 확정**: 무신사 랭킹 API 날짜 파라미터 전부 무시(응답 대조),
  29CM BEST 날짜형 필드 후보 17개가 DTO에 없음(타입 프로브), Wayback은 CSR 껍데기.
  무신사 월간 랭킹 아카이브 API(TOP30·월 단위)는 존재하지만 안 쓰기로 결정(축적 일원화)
- **top 100 고정**: 화면은 1,019위까지 나오지만(결번 0·중복 0, 37스텝/25초) 기존 축적
  (경로 A `003`, 102건)과 모양이 같아야 diff가 이어진다
- 무신사 랭킹 API는 102개/요청, 29CM BEST 100개/페이지 — top 100은 요청 1번
- 29CM 소분류 랭킹은 중분류 필터가 아니라 **독립 랭킹**(데님 top 100의 84%가 바지 top 100에
  없음). 폴백으로 중분류로 낮추면 target을 중분류 이름으로 저장 — 다른 랭킹이라 소분류
  스냅샷과 diff 금지
- **가격·할인 변화 감지 = 상품별 마지막 관측 대비** (v5 개정): 바지 33개 축적분에서 등장
  679개 중 전 시점 상주 **7개(1%)**, 연속 쌍 2,621 중 구 규칙(인접 쌍)이 비교한 건 71% —
  나머지 29% 사각지대가 실제 변화 2건을 0건으로 보고했다. 관측 창(`from_at`·`to_at`·
  `gap_snapshots`·`exact_at`)을 사건마다 기록, 상한 없음(실측 결석: 중위 60분, 72%가 90분
  이내, 최대 690분). 한계 2개: 결석 중 다중 변화는 순변화 1건으로 뭉침, 원복은 안 잡힘
- 1회만 스친 상품이 679개 중 348개 — 기본 필터에서 빼되 건수를 칩에 표시
- 등장 상품 추이 요약: 시점 48개 초과 시 균등 구간 대표 스냅샷(평균 금지). 48 = 무신사 하루치

## 9. 규모·상한 근거

- **지배 비용은 목록이 아니라 상품당 상세 방문(~1.2초)과 이미지 분류(~4초)다.**
  카테고리도 상세에만 있다(`baseCategoryFullPath`) — 목록만 쓰면 category 결측 100% FAIL
- 스토리1 상한 3,000 ≈ 60분(상세 순회). 실측: 로우클래식 440개 상세 순회 약 4분
- 스토리2 상한 5,000: 상품당 ~2.3초(상세 1.2 + 이미지 26%×4초) → 3,000개 ≈ 2시간이
  단일 실행 한계, 1만 개는 ~7시간이라 성립 안 함. 품절 포함으로 규모가 1.5배 되어
  3,000→5,000으로 상향
- **성별 축소 효과(무신사)는 제한적**: 데님팬츠 전체 24,673~24,692(실시간 변동) vs
  남 14,275 + 여 14,767 = 29,042 — **유니섹스가 양쪽에 중복 집계**되어 ~40%만 준다.
  29CM은 성별이 트리에 내장(여성 데님 `268106104` 2,580 / 남성 `272104104` 694)
- 무신사 데님팬츠 412페이지(24,673개), 목록 수집 자체는 60개/페이지 × 167회 ≈ 4~7분

- v10: 가격 포지셔닝 상품 표를 전 상품 표 `가격 차이` 열로 합침(합집합 741행에 매칭 283건이
  중복으로 두 번 실렸다)
- v11: `단독 입점 상품 성격` 섹션을 `품목별 입점 차이`에 합침 — 품목 분포 막대가 커버리지
  표 `단독` 열과 같은 값을 같은 순서로 그렸다. 고유 정보는 단독 상품 가격대뿐이라
  KPI·분포로만 남김
- v7: 인기 상품 상위 10 제거 — 전 상품 표를 좋아요로 정렬하면 같은 답
- v14: 입점 필터 축은 한 축 안에서도 AND(다른 축은 OR) — 목적이 "모두 입점" 교집합이라
  OR면 전 행이 남는다. `모두 만족` 배지로 동작을 밝힌다. 구 구조(조합 나열 값)는 플랫폼
  3개부터 "정확히 2곳"을 셀 수 없었고, 실측에서 합집합 28인데 열 합 26으로 상품을 잃었다
- 품목별 입점 차이 실측(인사일런스): 니트/스웨터 양쪽 입점 26%(42 중 11) vs 반소매 티셔츠
  71%(77 중 55) — 품목별 편차 큼. 무신사 단독 225건 중 번들·콜라보 표기는 15건뿐 —
  단독 입점의 주 사유는 카탈로그 폭 차이(564 vs 422)로 보이며 유형 쏠림을 단정하지 않음
- 파생 지표 정의: 규모 대비 하트·후기 = 지표 비중 ÷ 상품 수 비중(1.3↑▲ 0.7↓▼, 상품 1~2개
  품목은 튄다), 중위 대비 = 값 ÷ 노출 상품 중위값(평균은 상위 몇 개가 끌어올림),
  상품당 평균 = 합 ÷ 노출 상품 수(미노출을 0으로 안 센다)
