> **v5에서 바뀐 것 (사용자 결정, 2026-07-30):**
> - **스토리2 표에 이미지 열을 넣는다** — v3의 "전수조사 표는 이미지 열 제외" 결정을

>   축을 쪼개지 않고 한 값을 더하는 쪽을 택했다("와이드 쇼츠"는 표현되지 않는다) (§4 스토리2)
> - **카테고리·속성은 정렬 열이 아니라 다중 선택 필터 축이다** (§4 리포트 공통)
> - **스토리1 분석 심화** — 품목 성적표(규모 대비 반응 지수)와 인기 상품 상위 10 표

>   근거(33개 축적분 실측): 등장 상품 679개 중 전 시점 상주는 7개(1%)뿐이고,

>

> - **스토리3 동작 2개로 분리** — C-1 모니터링 시작(스냅샷 1개 + 스케줄 등록, 스케줄링이

> - 스토리3 판정 기준 확정 — 급등락 강조 **랭킹 길이의 10%(최소 3계단)**, 추이는

> 강건성 함정 목록(§7), 실시간 지표·구간 표기 필드(§6).

## 1. 배경

무신사·29CM는 공개 API를 제공하지 않는다. 이 프로젝트는 두 사이트에서 자연어 태스크를
수행하는 **강건한 스킬의 예제**를 만든다. 스킬은 Agent Skills 개방 표준을 따르며 특정
실행 환경에 국한되지 않는다.

### 접근 정책 (조사로 확인)

- 무신사 `robots.txt`는 일반 봇을 `Disallow: /`로 막지만 **`Claude-User`·`Claude-SearchBot`은
  `Allow: /`로 전면 허용**한다.
- 29CM `robots.txt`는 `*`에 `Allow: /`이고 로그인 영역만 막는다.
- 두 사이트 모두 403·캡차·봇 챌린지 없이 전 페이지 200이 확인됐다.

즉 이 스킬은 **우회 없이 사이트가 밝힌 정책 안에서** 동작한다.
User-Agent 위장은 금지한다(§7).

## 2. 실행 환경과 아키텍처

### 실행 환경 (둘 다 지원)

| 프로필 | 페이지 접근 | 후처리·리포트 생성 |
|---|---|---|
| Aside (주 환경) | 내장 에이전트가 스킬의 사이트 플레이북을 따라 수행 | 코드 실행 가능 시 `scripts/`, 불가 시 `assets/report-template.html` 구조를 따라 직접 생성 |
| Claude Code | 환경이 제공하는 브라우저 제어 도구로 플레이북 수행 | `scripts/` (deterministic) |

**전제 조건 (v6): 목록 수집에는 브라우저를 제어할 수 있는 도구가 필요하다.**
페이지를 열고 스크롤하고 **페이지 안에서 JS를 실행**할 수 있으면 된다. 특정 도구 이름에
의존하지 않는다(설계 원칙 1). 브라우저 도구가 없는 환경에서는 경로 A로 낮춰 수집하되,
**전량 보장이 깨진다는 것을 리포트에 명시한다** (§2 경로 A의 구조적 누락).

### 설계 원칙

1. **플랫폼 중립** — SKILL.md는 어떤 에이전트든 따라할 수 있는 절차서로 쓴다.
   특정 도구 이름에 의존하는 지시를 SKILL.md에 두지 않는다.
2. **deterministic 후처리** — 수집 결과는 §6 데이터 계약대로 JSON에 담고,
   검증·집계·diff·HTML 생성은 `scripts/`가 한다.
   **데이터 계약이 수집(에이전트)과 처리(코드) 사이의 이식성 경계다.**
3. **단일 스킬 + 사이트 어댑터** — 스킬은 하나, 사이트별 상세는 `references/<site>.md`로
   분리한다(progressive disclosure). 신규 사이트는 references 추가로 확장한다.
4. **판단은 최대한 코드로 내린다** — 사람의 해석이 개입할수록 결과가 흔들린다.
   만족/불만족 판정(§4-B), 결측 판정, 변화 감지는 전부 코드가 한다.

### 수집 경로 — 경로 B(브라우저) 우선 (v6 개정)

**v2~v5는 "경로 A 우선 → B 폴백"이었다. v6에서 뒤집는다.** 두 가지 이유다.

1. 이 스킬의 목적 자체가 **공개 API가 없는 사이트를 브라우저로 다루는 예제**다
2. **실측에서 경로 B가 더 완전했다** — 아래 "경로 A의 구조적 누락"

#### 페이지별 수집 가능 여부 (2026-07-30 실측)

구 표는 전부 **서버 HTML 기준**이어서, 브라우저로 열면 렌더되는 페이지가 "껍데기만"으로
적혀 있었다. 두 열로 나눈다.

| 페이지 | 서버 HTML | **브라우저 렌더 후** | 실측 |
|---|---|---|---|
| 무신사 상품 상세 | 있음 | 있음 | |
| 무신사 카테고리 목록 | 있음 | **완전 렌더** | 60개/초, 3,606개/60초 |
| 무신사 브랜드 목록 | 껍데기만 | **완전 렌더** | `/brand/{slug}/products` 563개 = 화면 총계 |
| 무신사 랭킹 | 껍데기만 | **완전 렌더** | 1,019위까지, 결번 0 |
| 29CM 상품 상세 | 있음 (JSON-LD) | 있음 | |
| 29CM 카테고리 목록 | 껍데기만 | **완전 렌더** | 50개/페이지, 7,567개 = 화면 총계 |
| 29CM 브랜드 목록 | 껍데기만 | **완전 렌더** | 435개 = 화면 총계 |

**브라우저로는 일곱 화면 전부에서 목록을 얻는다.** "29CM는 목록을 못 준다",
"랭킹은 화면으로 안 잡힌다"는 서술은 폐기된다.

#### 두 경로의 역할

- **경로 B (기본)** — 화면을 열어 **눈에 보이는 값만** 읽는다. 목록 순회·화면 전용 값
  (`viewers_now` 등)·**화면 총계**가 여기서 나온다. 추출은 접근성 스냅샷이 아니라
  **페이지 안에서 JS를 실행**해 한다 (수천 개 규모에서 스냅샷은 컨텍스트가 터진다).
- **경로 A (보완)** — 사이트가 화면을 그릴 때 쓰는 JSON. 경로 B가 화면에 **노출하지 않는
  정확값**을 채울 때 쓴다(예: 축약 표기 `1.2천` → 무신사 하트 배치 API의 정확값).
  상세 값 추출도 HTTP로 한다(JSON-LD 등). 경로 B가 막혔을 때의 대체 경로이기도 하다.

#### 경로 A의 구조적 누락 (2026-07-30 실측, v6에서 확인)

**29CM BEST API(`brandFacetInputs.frontBrandNo`)는 브랜드 카탈로그 전량이 아니다.**

| | 건수 |
|---|---|
| 브랜드 페이지 화면 총계 = 브라우저 순회 | **435** |
| 경로 A(BEST API, 정렬 4종 합집합) | **422** |
| 누락 | **13건 (3.0%)** — 이 중 **11건이 품절** |
| 유령(수집엔 있고 화면엔 없음) | 0건 (수집분 ⊂ 화면집합) |

**누락의 원인은 특정하지 못했다.** 처음에 "랭킹이라 품절을 뺀다"고 적었으나
**같은 수집분 안에 품절이 이미 120건 들어 있어 성립하지 않는다.** 저조한 반응 때문도
아니다 — 누락 13건은 좋아요 4~39·후기 0~3인데, 경로 A 수집분에는 좋아요 5 이하가 35건,
후기 0건이 172건 들어 있다. 즉 **누락된 상품을 다른 상품과 구별해 주는 관측 가능한 기준이
없다.**

확립된 것은 두 가지다.

- **경로 A는 전량이 아니다** (435 중 422, 재현됨). 화면 집합의 부분집합이며 유령은 0건이다
- **누락이 품절 쪽으로 치우친다** — 누락분 품절률 **85%**(11/13) vs 수집분 품절률
  **28%**(120/422). 약 3배 편향이지만 필터가 아니라 편향일 뿐이다

**원인을 모르는 것이 규칙을 더 강하게 만든다.** 어떤 상품이 빠질지 예측할 수 없으므로
**화면 총계 대조 없이는 전량을 주장할 수 없다.** 브라우저 브랜드 페이지는 품절 상품을
`품절` 배지와 함께 포함하며 435건 전부를 준다.

**따라서 "전량"을 요구하는 스토리1·스토리2는 경로 B로 모은다.** 경로 A는 보완이다.

#### 화면 총계 대조가 완전성 검증의 근거다

- 경로 B는 화면에 찍힌 총계를 읽을 수 있다 (`435개`, `7,567개`, `24,686개`)
- 경로 A는 총계를 주지 않아 `source_total`에 수집 건수를 넣었고, 그래서
  `총계 대비 오차 0.0% — 기준 통과`가 **자기 자신과 비교하는 순환 검증**이었다
- **`source_total`에는 화면에 노출된 총계를 담는다.** 수집 건수를 넣지 않는다
- 랭킹은 총계 대신 순위 번호로 검증한다 — `max(rank) == 수집 건수 == distinct(rank)`이고
  결번이 있으면 불완전이다 (실측: 1,019위까지 결번 0·중복 0)

어느 경로를 썼는지 `meta.notes`에 기록한다. 경로가 바뀌어도 §6 계약은 같으므로
리포트 코드는 영향받지 않는다.

## 3. 범위 / 비범위

### 범위

- P0: 무신사에서 스토리 1·2·3 각각 자연어 요청 1개로 end-to-end 수행
- P0: 결과가 HTML 페이지로 저장됨 (이미지는 원본 URL 핫링크)
- P0 (v6): **스토리1 멀티 플랫폼 비교** — 한 브랜드를 무신사·29CM 합집합으로 정리하고
  입점 차이를 드러낸다. 플랫폼 1개만 입력하면 단일 라인시트로 동작한다
- P1 (v6 완화): 29CM 어댑터 — 브랜드·카테고리 목록에 경로 A(BEST API)가 확보돼
  브라우저 없이도 수집은 된다(§7). **단 경로 A는 품절 상품이 빠져 전량이 아니므로
  기본 경로는 브라우저(경로 B)다** — 실측 435개 중 422개(§2). 조회수·누적판매를
  노출하지 않는 지표 비대칭은 남는다
- **플랫폼 간 동일 상품 매칭** (v6에서 비범위→범위) — 규칙은 §4 스토리1에 있다.
  **정규화 상품명 완전일치만** 허용하고 추정 매칭은 금지다
- 비로그인 상태에서 접근 가능한 데이터만 수집
- 수치는 **사이트 노출값만**. 추정·보간하지 않는다. 미노출은 `null`("미노출"로 표기)

## 4. 유저 스토리별 스펙

### 리포트 공통 — 표 조작과 파생 지표 (v5, 2026-07-30 확정)

리포트 구조 자체는 `references/report-spec.md`가 정본이다. 여기서는 **판정·정의**만 둔다.

- **정렬 대상 = 순서에 뜻이 있는 열**: 상품명 · 가격 · 후기 · 평점 · 좋아요 · 조회수 ·
  누적판매 · 순위. 열 머리를 눌러 오름차순↔내림차순으로 뒤집고, 눌리는 열임을 알 수 있게
  **중립 화살표를 항상 표시한다.** 값이 없는 행은 방향과 무관하게 뒤로 간다
- **필터 축 = 값의 종류가 정해진 열**: 카테고리 · 속성(핏 등) · 변화 종류. 이 열들은
  **정렬하지 않는다** — 가나다순은 열람에 쓸모가 없고, 정렬 화살표가 필터를 가린다.
  대신 값마다 건수를 붙인 **다중 선택 칩**을 낸다. 한 축 안에서 여러 개를 켜면 OR,
  서로 다른 축끼리는 AND다
- **파생 지표는 계산식을 리포트 안에 싣는다** — 이름만으로 뜻이 통하지 않는 열은
  열 머리에 hover 뜻풀이를, 섹션 각주에 계산식과 예시를 넣는다. 정의를 모르는 숫자는
  읽는 사람이 지어내서 해석한다
  - **규모 대비 하트·후기** = 그 품목의 지표 비중 ÷ 상품 수 비중. 1.00이면 상품 수만큼
    반응한 것이고 1.30 이상 ▲, 0.70 이하 ▼. 상품 수가 1~2개인 품목은 크게 튀므로
    **상품 수 열과 함께 읽어야 한다**고 각주에 밝힌다
  - **전 상품 중위 대비** = 이 상품의 지표값 ÷ 그 지표가 노출된 전 상품의 **중위값**.
    평균이 아니라 중위값으로 나눈다 — 상위 몇 개가 평균을 끌어올려 기준이 흔들린다
  - **상품당 평균** = 합 ÷ **그 지표가 노출된 상품 수**. 미노출을 0으로 세지 않는다
- 전부 노출값의 합과 비율이다. 추정 금지 원칙(§3 비범위)은 파생 지표에도 그대로 적용된다

### 스토리 1 — 브랜드 라인시트 (멀티 플랫폼 비교)

**이 스토리의 핵심은 한 브랜드를 여러 플랫폼에서 비교하는 것이다** (v6 재정의).

- **트리거 예**: "무신사랑 29cm에서 인사일런스 라인시트로 정리해줘",
  "무신사에서 인사일런스 상품 전체 라인시트로 정리해줘"(플랫폼 1개)
- **입력**: 브랜드명(필수), 플랫폼 **1개 이상**(필수 — 기본값 없음, 요청에 명시된 것만).
  현재 지원은 무신사·29CM이고 **플랫폼은 확장 축이다** — 새 사이트는 `references/` 추가로
  들어오며 아래 처리·리포트 규칙은 사이트 수와 무관하게 성립해야 한다
- **처리**: 플랫폼별로 브랜드 상품 목록 전체 순회 → 사이트별 JSON(§6) → 검증 →
  **매칭·합집합** → HTML
- **규모 상한 (v6 — 구 2,000)**: **3,000개까지 묻지 않고 진행** (초과 시 규모를 알리고 좁힐 축 협의 —
  §4 스토리2와 같은 절차). 근거: 스토리1의 지배 비용은 목록이 아니라 **상품당 상세 방문
  1회**다 — 조회수 구간·누적판매뿐 아니라 **카테고리(`baseCategoryFullPath`)도 상세에만
  있다**(2026-07-30 실측: 목록만 쓰면 `category` 결측 100%로 검증이 FAIL한다).
  예의 대기 포함 상품당 ~1.2초 → **3,000개 ≈ 60분**이 단일 요청 완주 UX의 한계선이다.
  실측: 로우클래식 440개(품절 포함) 상세 순회 약 4분, 인사일런스 무신사 2,022개(품절 포함).
  **멀티 플랫폼일 때 상한은 플랫폼별로 적용한다** (합집합 크기가 아니라 각 사이트 수집량)

#### 동일 상품 매칭 — 완전일치만 (v6 확정)

두 플랫폼의 상품을 이어붙이려면 "같은 상품"을 판정해야 한다. **규칙은 하나뿐이다.**

1. 상품명을 정규화한다 — 소문자화 · `[...]`·`(...)` 제거 · 영숫자와 한글만 남기고 나머지
   (공백·`_`·`/`·하이픈 등) 제거
2. 정규화 결과가 **완전히 같을 때만** 동일 상품이다
3. 같지 않으면 **단독 입점**으로 둔다. 이것은 매칭 실패가 아니라 유통 사실이다

**추정 매칭은 금지다** (§3 비범위). 유사도 매칭·가격 일치 보조·이미지 대조를 쓰지 않는다.
근거는 인사일런스 실측(2026-07-30)이다 — 유사도 0.82↑ 후보 11건 중 대부분이 다른 상품:

| 29CM | 무신사 | 실제 |
|---|---|---|
| 헨리넥 숏슬리브 BLACK (69,000) | 와플 헨리넥 롱슬리브 BLACK (77,000) | 소매 길이가 다른 별개 |
| 프렌치 워크 자켓 FADED BLUE (177,000) | 프렌치 워크 자켓 FADED BLACK (177,000) | 컬러웨이가 다른 별개 |
| 레터링 그래픽 티셔츠 CHARCOAL (66,000) | 스탠실 그래픽 티셔츠 CHARCOAL (66,000) | 프린트가 다른 별개 — **정가까지 같다** |

마지막 행이 결정적이다. **가격 일치가 오탐을 확증해주기 때문에 가격은 보조 신호로도
쓸 수 없다.** 완전일치의 실측 커버리지는 29CM 421개 중 338개(80.3%)이고 오탐 0이다.

매칭 결과는 리포트가 계산하며 근거를 남긴다 — 각 행에 어느 플랫폼에서 왔는지와
정규화 키를 보존해 사후 확인이 가능해야 한다.

#### 품목 비교축 — 매칭 상품에서 자동 추출 (v6 확정)

사이트 카테고리 이름은 서로 다르다. 인사일런스 실측에서 **29CM 43종 / 무신사 37종 중
이름이 그대로 겹치는 건 8종뿐**이다(반소매 티셔츠, 긴소매 티셔츠, 카디건, 코튼 팬츠,
베스트, 플리스, 피케/카라 티셔츠, 후드 집업). 무신사 `청/데님 팬츠` ↔ 29CM `데님 팬츠`,
무신사 `항공 점퍼/블루종/MA-1` ↔ 29CM `블루종`처럼 같은 품목이 다른 이름이라
원본 이름으로 나란히 놓으면 축이 어긋난다.

**사람이 매핑 표를 관리하지 않는다.** 매칭된 동일 상품이 각 플랫폼에서 어느 카테고리에
들어가 있는지를 세어 **코드가 대응 관계를 만든다**:

1. 매칭된 상품마다 `(무신사 카테고리, 29CM 카테고리)` 쌍을 센다
2. 한 카테고리의 대응 후보 중 **건수가 가장 많은 것**을 대응으로 정하고, 근거 건수를 남긴다
3. 대응이 생기지 않은 카테고리(단독 입점 품목)는 **통합하지 않고 그대로 둔다** —
   억지로 붙이지 않는다
4. 리포트는 통합축과 **각 사이트 원본 카테고리를 모두 싣는다.** 통합축은 근거 건수와 함께
   표시해 독자가 검증할 수 있어야 한다 (근거 1~2건인 대응은 약한 대응임을 표시)

#### 출력 리포트

① 헤더(브랜드, 수집 시각, **플랫폼 목록**, 플랫폼별 상품 수와 합집합 크기, 매칭 건수,
결측·노출 요약)
② **플랫폼 비교 요약** — 아래 고도화 4개 축
③ 플랫폼별 인기 상품
④ **합집합 전 상품 표** — 칼럼: 이미지 · 상품명 · **입점**(어느 플랫폼에 있는지) ·
품목(통합축) · 플랫폼별 정가/판매가/할인율 · 후기 수 · 평점 · 좋아요 · 조회수 ·
누적판매 · 링크. 매칭된 상품은 **1행**이고 플랫폼별 값이 나란히 들어간다

`입점` 칼럼은 필터 축이다(§4 리포트 공통) — "양쪽 입점 / 무신사 단독 / 29CM 단독"으로
걸러 볼 수 있어야 한다.

#### 플랫폼별 품목 인기 분석 — 고도화 4개 축 (v6 확정)

"플랫폼별로 어떤 품목이 인기인가"에 대한 답이다. 전부 `build_report.py`가 계산하고
**노출값의 합과 비율일 뿐 추정이 아니다.**

1. **품목별 입점 차이** (구 `품목별 입점 커버리지 갭` + `단독 입점 상품 성격`) — 품목마다 `양쪽 입점 / A 단독 / B 단독` 건수를 낸다.
   브랜드가 어느 품목을 어느 플랫폼에 몰아줬는지가 보인다. 실측(인사일런스, 2026-07-30):
   `니트/스웨터`는 양쪽 입점이 **26%**(42건 중 11건)로 무신사에 쏠려 있고,
   `반소매 티셔츠`는 **71%**(77건 중 55건)로 양쪽에 고르다 — 품목별로 편차가 크다.
   무신사 단독 225건에 `[2 PACK]`·`[SET]`·`[KKST 콜라보]` 같은 번들·콜라보 표기가 있지만
   **15건뿐이다** — 단독 입점의 주된 사유는 특정 상품 유형이 아니라 **카탈로그 폭 차이**
   (무신사 564 vs 29CM 422)로 보이며, 유형 쏠림을 단정하지 않는다
2. **같은 상품 반응 강도 비교** — **매칭된 상품만** 대상으로 플랫폼별 하트·후기를 품목
   단위로 대조한다. 동일 상품이므로 **상품 구성 차이가 통제된 비교**가 되고, 두 사이트가
   모두 노출하는 지표(하트·후기)만 쓰므로 추정이 없다. 매칭 건수를 함께 싣고,
   **단독 입점은 이 비교에서 제외**한다(제외 사실을 각주로 밝힌다)
3. **가격·할인 포지셔닝 차이** — **집계만 내는 섹션이다** (v10 개정, 2026-07-30).
   품목별 평균 판매가 차이와 "판매가 같은 것 / 다른 것" 요약까지다.
   **상품별 대조 표는 전 상품 표의 `가격 차이` 열로 합쳤다** — 구 구조는 매칭 상품 전 건을
   여기서 또 실어서 **같은 상품이 리포트에 두 번** 나왔다(로우클래식 실측: 합집합 741행인데
   매칭 283건이 별도 표로 중복).
   **판매가는 두 사이트 모두 쿠폰적용가다**(v8 — 무신사 `finalPrice`, 29CM `displayPrice`).
   정가가 같은데 판매가만 다르면 그것이 플랫폼별 할인 정책 차이다
4. (구 **단독 입점 상품 성격 분석** — v11에서 ①에 합쳤다. 품목 분포 막대가 ① 표의
   `단독` 열과 같은 값이었고, 고유 정보인 단독 상품의 **가격대**만 KPI·분포로 남겼다)

v5의 품목 성적표(상품 수 · 하트 합 · 상품당 하트 · 규모 대비 하트 · 후기 합 · 상품당 후기 ·
규모 대비 후기 · 중위 가격 · 평균 할인율 · 후기가중 평점)는 **사이트별로 그대로 유지한다.**
고도화 4개 축은 그 위에 얹히는 비교 레이어다. 지표 정의는 §4 리포트 공통.

**플랫폼이 1개면** 고도화 4개 축은 만들지 않는다(비교 대상이 없다). 빈 섹션을 만들지 말고
기존 단일 라인시트 구성으로 낸다.
- **`플랫폼별 인기 상품`(상위 10) 섹션은 만들지 않는다 (v7, 2026-07-30 사용자 결정)** —
  전 상품 표를 좋아요로 정렬하면 같은 답이 나온다. 전 상품 표에 좋아요 열이 있고
  (플랫폼이 2개 이상이면 사이트별로) 정렬 가능하다. 구간 표기 값(§6)은 여전히
  정렬 키를 갖지 않으므로 순위 비교에 끼지 않는다
- **성공 기준**: 상품 수가 사이트 노출 총계의 ±5% 이내, 필수 필드 결측 <5%.
  **멀티 플랫폼일 때는 플랫폼별로 각각 판정한다** — 한쪽이 미달이면 그 사이트만 경고를
  달고, 합집합 리포트는 만든다(부분 실패를 전체 실패로 처리하지 않는다).
  추가: 매칭 건수와 단독 입점 건수의 합이 합집합 크기와 일치해야 한다(코드가 검산)
  - **29CM 브랜드 목록은 `source_total`이 응답에 없다** — `pagination`이 `hasNext`만 준다.
    끝까지 순회해 센 값을 `item_count`에 담고 `source_total`은 그 값으로 두되,
    **사이트가 총계를 주지 않았다는 사실을 `meta.notes`에 남긴다.** ±5% 기준은 이 경우
    자기 자신과의 비교가 되어 무의미하므로, 완전성 근거는 **`hasNext=false` 도달**이다

### 스토리 2 — 상품군 시장 전수조사

- **트리거 예**: "무신사 데님팬츠 시장 전수조사 해줘"
- **입력**: 카테고리명(필수), 사이트(**필수 — 기본값 없음**), 성별(선택)

#### 리뷰 본문은 수집하지 않는다 (v3 — 사용자 결정)

만족/불만족 판단 재료는 사이트가 각 상품에 노출한 **후기 수와 평균 평점**뿐이다.
두 사이트 모두 이 값이 목록/상세에서 바로 보이므로 별도 수집 비용이 없다.
리뷰를 한 건씩 읽고 해석·요약하는 일은 **비범위**다.

리포트가 계산하는 것(전부 deterministic — `build_report.py`):
- 후기 수 **가중** 평균 평점 (후기 많은 상품이 더 무겁게)
- 상품 평점 분포 (~2.9 / 3.0~3.4 / 3.5~3.9 / 4.0~4.4 / 4.5~, 평점 미노출은 제외하고 건수 명시)
- 실수로 `reviews[]`가 담겨 오면 `validate_data.py`가 경고한다

#### 범위 정책 (v9 — 임계값 5,000)

조사 결과 무신사 데님팬츠(`003002`)는 **24,673개 / 412페이지**다.
목록 수집 자체는 1만 개도 감당되지만(60개/페이지 × 167회 ≈ 4~7분), **목록은 지배 비용이
아니다.** 스토리2의 실제 비용은 ① 상품당 상세 방문 1회(조회수 구간·누적판매) ~1.2초
② 핏 분류 중 **이미지 확인이 필요한 ~26%**(상품명 텍스트 분류 74% — 175개 실측) 장당
~4초로, 합쳐 상품당 ~2.3초다. 3,000개 ≈ 2시간이 단일 실행의 현실적 한계이고,
1만 개는 ~7시간이라 성립하지 않는다 (v3의 1만 기준은 목록 비용만 본 오류였다).

절차 — SKILL.md에 알고리즘으로 명시돼 있다:

1. 목록 첫 페이지에서 **사이트가 말하는 총 개수**를 읽는다 (`source_total`)
2. **0건** → 중단, "검색 0건" 보고
3. **5,000건 이하** → 묻지 않고 진행. 시작 시 개수·예상 소요 한 줄 보고
4. **5,000건 초과** → 수집을 시작하지 않는다. 좁힐 축의 **실제 개수를 조회해서**
   제시하고 사용자가 고른다. "전체로"라고 하면 전체 진행(예상 소요 먼저 보고)
5. 최종 범위를 `meta.target`에 쓴다 — "데님팬츠(남성)" 형식. 리포트 헤더에 그대로 실린다

**임의 샘플링 금지** — 묻지 않고 상위 N개만 수집하는 것이 최악의 실패다.

좁힐 수 있는 축(우선순위 순):

| 축 | 무신사 | 29CM |
|---|---|---|
| **성별** | `gf` 파라미터 (`A`/`M`/`F`) | 대분류 코드에 이미 포함 (여성의류 `268100100` / 남성의류 `272100100`) |
| 세부 카테고리 | 6자리 소분류 | 9자리 소분류 (예: 남성 데님 팬츠 `272104104`) |
| **가격대** | `minPrice`/`maxPrice` **확인** (10~20만원 5,464 실측) | 미검증 |
| 브랜드 | PLP 필터 파라미터 미검증 | 미검증 |

성별 필터의 실제 축소 효과는 §4 부록에 기록한다.

#### 처리

1. 카테고리 특정 → 규모 확인 → 범위 결정 (위 절차)
2. 상품 목록 전체 수집 — 후기 수·평점·좋아요는 목록 노출값 그대로
3. **속성 분류** — 근거 순서: ① 상품명·옵션·상세 텍스트 → ② **색상 변형 그룹 전파** →
   ③ 대표 이미지 확인 → ④ `unknown`. 찍지 않는다.
   판단 근거를 `attributes_basis`에 `name`/`detail`/`image`/`group`/`unknown`으로 남긴다
   - **② 그룹 전파 (v12 신설)**: 같은 상품의 색상 전개가 각각 별개 상품으로 올라온다.
     색상은 핏을 바꾸지 않으므로 **그룹당 한 번만 판단**한다. `group_variants.py`가
     `--plan`으로 그룹·대표를 뽑고 `--apply`로 구성원에 전파한다
   - 묶는 규칙은 **같은 브랜드 + 색상·품번·괄호를 뗀 이름 완전일치**뿐이다.
     **유사도로 묶지 않는다** — 이 프로젝트는 상품명 유사도 매칭을 실측으로 기각했다
   - 실측 절감: 슬랙스(여성 10~20만원) 3,004개에서 미분류 1,492건 →
     **판단 1,071회(28% 감소)**. 검증: 서로 다른 핏이 섞인 그룹 **0개**
   - 한 그룹에 값이 섞이면(`conflict`) 전파하지 않고 직접 정한다
4. 검증 → 리포트

#### 조사 칼럼 구성 (2026-07-29 확정)

- **표 칼럼**: **이미지** · 상품명(링크) · 브랜드 · 카테고리 · 정가/판매가/할인율 ·
  후기 수 · 평점 · 조회수(구간 문구) · 누적판매 · 좋아요 · 품절 + 분류 속성
  - **이미지 열을 넣는다 (v5, 2026-07-30 사용자 결정)** — v3의 "전수조사 표는 이미지 열
    제외"를 뒤집었다. 전 행 유지 원칙은 그대로이고, 썸네일은 `loading="lazy"`라 화면에
    들어올 때만 받는다(3,460행 실측 4.1MB, 단일 파일 유지)
- **분류 속성은 핏만 P0** — 부츠컷/와이드/스트레이트/슬림/테이퍼드/**쇼츠**/unknown.
  상품명 텍스트로 74%가 해결되고(175개 실측) 나머지 ~26%만 이미지 확인이라
  상한 5,000 규모에서 감당된다
- **`쇼츠`를 값으로 추가 (v5, 2026-07-30 사용자 결정 — B안)**: 앞의 다섯 값은 긴바지의
  레그 실루엣 축이라 반바지에는 정답이 없다. 그대로 두면 `unknown`에 뭉친다
  (실측: 쇼츠 107개 중 96개가 unknown, 11개는 `와이드`가 붙어 같은 종류가 갈렸다).
  **축을 쪼개지 않고 한 값을 더하기로 했다** — 대신 "와이드 쇼츠"는 표현되지 않는다
  - 이름 신호(근거 `name`): `쇼츠` `숏츠` `숏팬츠` `반바지` `버뮤다` `BURMUDA`(오타가
    실제로 쓰인다) `shorts` `하프` `N부`(2~5부)
  - 이름에 단서가 없어도 **대표 이미지에 무릎 위 기장이 보이면 `쇼츠`**(근거 `image`)
  - **함정: `하프 밴딩`·`Half-band`는 기장이 아니라 허리 밴딩이다** — 긴바지로 둔다
  - **함정: `shorts` 뒤에 밑줄이 오는 이름이 많다**(`A-line shorts_light blue`).
    밑줄은 단어 문자라서 단어 경계로만 찾으면 놓친다
  - 기장을 볼 수 없는 컷(허리 클로즈업)과 바지가 아닌 상품은 `unknown`으로 둔다
- **속성은 정렬 열이 아니라 다중 선택 필터 축이다** (§4 리포트 공통)
- 워싱 톤·기장·소재 등 추가 속성은 **사용자가 명시적으로 요청할 때만** 수행한다.
  이미지 전수 확인이 필요한 속성은 예상 소요를 먼저 알린다

- **출력 리포트**: ① 시장 요약(상품 수, 후기 합계, 중위 가격, 가중 평균 평점, 가격 분포,
  상품 평점 분포, 속성 분포) ② 전 상품 표(**이미지 열 포함**·전 행, 속성 컬럼 + 속성 칩 필터)
- **성공 기준**: 합의된 범위 완주(중단 시 부분 리포트에 명시), 속성 분류율 ≥80%,

### 스토리 3 — 카테고리 랭킹 모니터링

#### 동작 2개로 분리 (2026-07-29 확정)

| 동작 | 트리거 예 | 입력 | 하는 일 |
|---|---|---|---|
| **C-1 모니터링 시작** | "무신사 바지 랭킹 모니터링 시작해줘" | 카테고리·사이트(필수) | 스냅샷 1개 수집 → **스케줄 등록**(사이트별 주기) → 등록 내용 보고 |
| **C-2 변화 조회** | "무신사 바지 랭킹, 지난 일주일 변화 보여줘" | 카테고리·사이트·**기간**(필수) | 축적분에서 diff → 변화 리포트 |

- **스케줄링이 스펙 안에 들어왔다**: C-1은 실행 환경의 스케줄 기능(데모 기준
  Claude Code)에 주기 실행을 등록하는 것까지가 동작이다. 등록 전에 첫 스냅샷이
  정상 수집되는 것을 확인한다. 스킬이 자체 타이머를 돌리는 것은 여전히 비범위다
- **축적 주기 = 사이트의 원본 갱신 주기** (2026-07-29 확정): 무신사 실시간 **30분**,
  29CM `HOURLY` **1시간**. 원본 주기보다 촘촘히 찍으면 같은 랭킹을 중복 저장할 뿐이다
- **기간 없는 변화 요청**("변화 알려줘"): 변화 분석을 하지 않는다. 스냅샷 1개만 찍고
  C-1(모니터링 시작)을 제안한다
- **처리(C-2)**: 기간 내 스냅샷 diff → 변화 리포트. 스냅샷 1개 이하면 "비교 대상 부족"
- **수집 규모 (조사 확인)**: 무신사 랭킹 API는 한 번에 102개를 준다.
  **top 100은 1페이지로 끝난다** — 순회 부담이 없다.
  29CM BEST API도 100개/페이지라 top 100은 요청 1번이다
- **경로 B로 수집할 때의 랭킹 코드 (v6 실측, 2026-07-30)**:
  - **화면은 6자리 코드만 받는다. 바지 전체 = `003000`이다.**
    대분류 `003`을 주면 에러도 리다이렉트도 없이 **다른 랭킹**
    (`sectionId=200&categoryCode=000` = NEW·전체)이 온다. 상태코드로는 알 수 없고
    1위 상품을 봐야 안다(재현 2/2). **경로 A는 `003`으로 정상 200이므로 코드 체계가
    경로별로 다르다** — 어느 경로를 쓰는지에 따라 코드를 바꿔야 한다
  - **화면 랭킹은 1,019위까지 나온다** (실측: 순위 1~1,019, 결번 0·중복 0, 37스텝/25초).
    **그래도 top 100 고정을 유지한다** (2026-07-30 사용자 확정) — 기존 축적 스냅샷
    (경로 A `003`, 102건)과 모양이 같아야 diff 시계열이 이어진다. 100위 아래는 버린다
  - **완전성 검증은 순위 번호로 한다** — `max(rank) == 수집 건수 == distinct(rank)`.
    결번이나 중복이 있으면 불완전으로 처리한다. 화면 총계가 없어도 성립하는 검증이다
  - **광고 카드를 순위에서 제외한다** — 순위 번호가 붙지 않은 카드는 랭킹 항목이 아니다
- **29CM 랭킹 기준 (v3 확정, 2026-07-29 검증)**: 소분류 랭킹은 중분류를 필터한 것이

  구조 상세는 `references/report-spec.md`가 정본이다
  - **KPI** — 스냅샷 수 / **등장 상품 수** / **교체율** / 가격·할인 변화(시점 확정 수).
    신규 진입·이탈은 첫·마지막 두 시점만 비교한 값이라 기간이 길어지면 실제 교체를
    과소 표기한다 → **교체율 = 인접 스냅샷 평균 신규 유입률**로 대체
  - **상품별 추이 (한 행 = 한 상품)** — 기간에 순위권에 오른 상품 **전부**를 담는다.
    신규 진입·이탈은 `끝점` 축(`유지`/`신규 진입`/`이탈`/`기간 중만`)으로 흡수하고
    표를 따로 두지 않는다. 급상승·급하락 막대도 없앤다(표 정렬로 같은 답)
  - **`전 구간`/`일부 구간` 라벨 폐기** → **`랭킹 체류 28/33회 · 85%`** 숫자 + `끝점` 배지.
    구 라벨은 "첫·마지막 스냅샷 둘 다에 있었나"라는 구현 사정을 말하는데 읽는 사람은
    "관측이 온전한가"로 읽었다(2026-07-30 사용자 지적)
  - **처음·마지막 두 점이 아니라 추이를 싣는다** — 행마다 순위·가격 스파크라인.
    순위 축은 **전 행 공통 범위**(모양 비교 가능), 가격은 **상품별 범위**(높이 비교 금지),
    할인 구간은 가격 스파크라인 뒤 배경 띠
  - **1회만 스친 상품은 기본 필터에서 뺀다**(추이가 점 하나다). 건수는 칩에 표시해
    **조용히 숨기지 않는다**(33스냅샷 실측: 679개 중 348개가 1회)
  - **추이 차트** — **표의 현재 정렬·필터 순서대로 상위 N개**를 그린다. 차트가 따로 선택
    규칙을 갖지 않으므로 "왜 그 5개인지"를 설명할 필요가 없다
    - 계열 수 **1~100**을 사용자가 입력한다
    - **5개까지 겹쳐 보기**(계열 색 5개 — 상품끼리 비교), **6개 이상 나란히 보기**
      (작은 배수 격자). 순위선 100개를 겹치면 읽을 수 없다 — 색을 늘리지 않고
      **형태를 바꾼다**. 구 규칙("계열 5개까지")을 깨는 게 아니라 5를 넘을 때의 형태를 정한 것
    - 각 칸 = **순위(좌축) · 가격(우축) · 할인 구간(배경 띠)** 한 좌표계.
      **시간·가격·할인율·순위를 한 번에** 보려는 요청의 답이다
    - 가격이 안 변한 상품은 가격 선을 그리지 않고 우축 라벨만 둔다 —
      가운데 점선이 순위 그리드선과 혼동된다
    - 표 행을 누르면 그 상품의 큰 패널이 펼쳐진다
  - **계열 데이터는 문서에 한 번만 심는다**(`<script type="application/json">`) —
    스파크라인·차트·행 펼침이 같은 데이터 하나를 쓴다. 모든 시점을 `null`까지 채우면
    2만 칸이 되므로 **관측된 시점만** 담는다(실측 3,300건 ≈ 190KB).
    그리기는 인라인 JS가 한다 — **외부 리소스는 여전히 0**이다.
    코드 실행이 안 되는 폴백 환경에서는 스파크라인·차트 없이 표만 만든다
  - **모든 상품 표에 이미지 열 포함** — 이를 위해 `diff_snapshots.py`의 `trends`가
    `image_url`을 들고 있어야 한다(구 버전은 movers/entered/exited에만 있어서
    순위권을 드나든 상품이 빈칸이 됐다)
- **성공 기준**: 스냅샷 2개 이상이면 diff 리포트 생성. 1개 이하면 "비교 대상 부족"을
  명시하고 현재 스냅샷 리포트만 (빈 diff를 만들지 않는다)
- **리포트 판정 기준 (2026-07-29 확정 — 전부 코드가 계산)**:
  - 급상승/급하락 강조 = **랭킹 길이의 10%, 최소 3계단** (top100이면 10계단).
    강조에만 쓰이고 진입/이탈·전체 변동 표는 임계값과 무관하게 전부 실린다
  - 추이 요약 = 시점이 48개를 넘으면 **균등 구간의 대표 스냅샷만** 골라 그린다
    (첫·끝 포함, 평균 금지 — 실측 스냅샷을 고른다. 48 = 무신사 하루치).
    **가격·할인 변화 감지는 요약과 무관하게 원본 전체 해상도**로 한다
  - **가격·할인 변화 감지 = 상품별 마지막 관측 상태 대비 (v5 개정, 2026-07-30 사용자 결정)**.
    구 규칙은 "연속한 스냅샷 쌍에 둘 다 있는 상품"만 비교했다. 개정 근거(바지 33개
    축적분 실측):
    - 등장 상품 **679개 중 전 시점 상주는 7개(1%)** — top 100이 30분마다 크게 교체된다
    - 연속 관측 쌍 **2,621개 중 구 규칙이 비교하는 것은 1,868개(71%)**.
      나머지 **753개(29%)는 비교 자체가 안 됐다**
    - 결과: 축적분에 남아 있는 실제 변화 2건을 **0건으로 보고**했다. 값이 없다고 표시한
      게 아니라 없다고 단정한 것이라, "조용히 틀린다"에 해당한다
    - 두 끝값 모두 사이트가 노출한 값이라 **추정이 아니다.** 잃는 것은 "언제"의 해상도뿐
  - **관측 창을 사건마다 기록한다**: `from_at` · `to_at` · `gap_snapshots` ·
    `exact_at`(결석 0 = 스냅샷 1칸으로 시점 확정). 리포트는 확정된 것만 단일 시점으로
    찍고 나머지는 `A ~ B 사이 (N시간 · 스냅샷 M개 결석)`로 낸다.
    **상한(cutoff)을 두지 않는다** — 긴 창의 사건도 사실이고, 잘라내면 다시 조용한 누락이 된다
    (실측 결석 구간: 중위 2스냅샷(60분), 72%가 90분 이내, 최대 23스냅샷(690분))
  - **밝혀야 하는 한계 2개**: 결석 구간 안에서 여러 번 변했으면 **순변화 1건으로 뭉쳐지고**,
    변했다 원래대로 돌아왔으면 **아예 잡히지 않는다**(순위권 밖은 관측 자체가 없다)
  - **할인 시점 = 감지이지 예측이 아니다**: 가격·할인율 필드가 바뀐 것을 기록한다.
    구매량 추이로 할인을 추론하지 않는다(추정 금지)
  - **순위 추이 선은 순위권 밖 구간에서 끊는다** — 이어 그으면 그 구간에도 순위가
    있었다고 주장하는 것이다. 시점 축 라벨은 날짜가 바뀔 때만 날짜를 붙이고 솎아낸다
  - **실시간 지표 추이 차트 포함**: 변동 큰 상품 5개의 `viewers_now`/`buyers_now`
    추이를 그린다. 반올림 노출값임을 각주로 명시
- **과거 소급 불가 — 확정 (2026-07-29 조사 완료)**: 서버 측 검증 결과
  **과거 데이터의 출처는 축적분뿐이다.**
  - 무신사 현행 랭킹 API: 날짜 파라미터가 전부 무시됨을 응답 대조로 확인.
    `period`는 트레일링 윈도우라 기준일 지정 불가
  - 29CM BEST API: 날짜형 필드 후보 17개가 **DTO에 존재하지 않음**을 타입 프로브로 확인
  - Wayback 아카이브: 두 사이트 랭킹 페이지 모두 CSR 껍데기라 실질 0건
  - 무신사 월간 랭킹 아카이브 API(TOP30·월 단위)가 존재하지만 **쓰지 않는다**
    (2026-07-29 사용자 결정) — 변화 분석의 재료는 축적 스냅샷으로 일원화한다
  - 부수 확인: 무신사 REALTIME 랭킹의 원본 갱신 주기가 **약 30분**이다 —
    30분 축적 주기가 원본 갱신 주기와 정확히 맞는다(더 자주 찍어도 중복일 뿐)

- **위치 고정**: 이 저장소 루트의 `data/snapshots/` — **git에는 올리지 않는다**(.gitignore).
  주기 실행이 매번 같은 곳에 쌓여야 diff가 성립하므로, 스케줄을 등록할 때는

## 6. 데이터 계약 (수집 JSON 스키마)

공통 메타: `{site, story, target, collected_at, item_count, source_total, incomplete, notes[]}`

`source_total`은 **사이트가 말한 총 개수**다. 수집 완전성 판정(±5%)의 기준이 된다.
사이트가 총계를 주지 않으면(29CM 브랜드 목록 — §7) 순회해 센 값을 담고 그 사실을 `notes`에 남긴다.

### 멀티 플랫폼은 계약을 바꾸지 않는다 (v6)

**수집 JSON은 언제나 사이트 하나짜리다.** 스토리1을 여러 플랫폼으로 돌려도 사이트마다
JSON을 따로 만들고, **합집합·매칭·통합축은 `build_report.py`가 여러 JSON을 받아 계산한다.**
수집 단계에 매칭 결과를 섞어 넣지 않는다.

이유는 §2 설계 원칙 2와 같다 — 계약이 수집(에이전트)과 처리(코드) 사이의 이식성 경계다.
매칭을 수집 쪽에 두면 플랫폼을 추가할 때마다 수집 로직이 서로를 알아야 하고, 매칭 규칙을
고칠 때 재수집이 필요해진다. 처리 쪽에 두면 **같은 원본으로 매칭 규칙만 바꿔 다시 그릴 수
있다.** 새 플랫폼은 JSON 하나를 더 넘기는 것으로 들어온다.

### 상품 레코드

| 필드 | 필수 | 설명 |
|---|---|---|
| `product_id` `name` `url` `image_url` `brand` `category` | 항상 | 결측률 <5% 기준 대상 |
| `price_original` `price_sale` `discount_rate` | 항상 | 할인 없으면 sale=original. **판매가 = 전 회원 공통 쿠폰적용가**(v8, §7) |
| `sold_out` | 항상 | 품절도 수집하되 표시한다 |
| `review_count` `rating` | 노출 시 | 미노출 `null` |
| `view_count` `purchase_count` `like_count` | 노출 시 | 미노출 `null` |
| `view_count_display` `purchase_count_display` | 구간 표기 시 | **v2 신규** — 아래 참조 |
| `viewers_now` `buyers_now` | 랭킹 목록만 | **v2 신규** — "N명이 보는 중/구매 중" |
| `rank` | 스토리3 | 랭킹 순위 |
| `attributes` `attributes_basis` | 스토리2 | 분류 결과와 그 근거(`name`/`detail`/`image`/`unknown`) |

`reviews[]`(리뷰 본문)는 **v3에서 계약에서 제외됐다.** 담겨 오면 `validate_data.py`가 경고한다.

### 구간 표기 값을 정수로 바꾸지 않는다 (v2 신규)

무신사 상품 상세의 조회수는 **`"300회 이상 (최근 1개월)"`처럼 구간으로 표기된다.**
이걸 `view_count: 300`으로 담으면 없는 정밀도를 만들어내는 것이고, 그 값으로 순위를
매기면 리포트가 조용히 틀린다.

규칙: **정확한 정수가 노출될 때만 `view_count`에 담는다. 구간 표기면 `view_count`는
`null`로 두고 원문을 `view_count_display`에 그대로 담는다.**
리포트는 구간 표기를 문구 그대로 싣고, 그 값으로는 순위 차트를 만들지 않는다.
둘 다 채워져 있으면 `validate_data.py`가 경고한다.

#### 실시간 지표는 화면(페이지)별로 갈린다 (v6 실측, 2026-07-30)

유저 스토리의 "조회수 몇 개인지"는 `view_count`(구간 표기)가 아니라
**`viewers_now`(`N명이 보는 중`)** 다. 그런데 이 값이 붙는 화면이 랭킹뿐이다.

| 화면 | `viewers_now` | `buyers_now` | `purchase_count` 배지 |
|---|---|---|---|
| 무신사 랭킹 | **노출** (`003000` 46% · `003002` 29%) | 1,019건 중 0~3건 | 노출 |
| 무신사 카테고리 목록 | **없음** (0건) | 없음 | 없음 |
| 무신사 브랜드 목록 | **없음** | 없음 | 없음 |
| 무신사 상품 상세 | 없음 | 없음 | — |

**따라서 스토리1(라인시트)·스토리2(전수조사)의 `viewers_now`/`buyers_now`는 구조적 `null`이고
리포트에 "미노출"로 찍힌다** (2026-07-30 사용자 확정). 수집 경로가 없으므로 요구에서 뺀다.
랭킹에서 교차 조인해 채우는 것도 하지 않는다 — 출처가 섞이고 랭킹 안에 든 상품만
채워져 일관성이 깨진다. `buyers_now`는 랭킹에서도 사실상 미노출이다.

#### 축약 표기는 원문을 보존한다 (v6, 2026-07-30 사용자 확정)

화면은 좋아요를 `1.2천`, 누적판매를 `판매 9만개`로 **축약**해 보여준다. 구간 표기
(`300회 이상`)를 정수로 바꾸지 않는 규칙을 **축약 표기에도 적용한다.**

- 원문은 `like_count_display` / `purchase_count_display`에 그대로 담는다
- **축약값을 정수로 파싱하지 않는다** — `1.2천`→1,200은 반올림 오차를 사이트 노출값처럼
  위장한다
- 정확값이 필요하면 **경로 A로 보완한다** — 좋아요는 무신사 하트 배치 API가 정수를 준다.
  보완했으면 `meta.notes`에 남긴다
- 보완하지 못하면 정수 칸은 `null`이고 리포트는 원문을 보여준다

### 평점 스케일 통일

`rating`은 **5점 만점**으로 통일한다. 무신사는 목록 응답의 `reviewScore`가 **0~100**,
상세의 `satisfactionScore`가 0~5로 **한 사이트 안에서 스케일이 두 개다.**
변환을 빠뜨리면 `validate_data.py`가 "평점이 0~5 범위를 벗어난다"고 경고한다.

## 7. 강건성 정책

- **속도**: 페이지 요청 간 0.5–1.5초 대기. 페이지네이션 안전 상한 200페이지
- **재시도**: 실패 시 2회 재시도(간격 증가). 3연속 실패 시 건너뛰고 `notes`에 기록
- **차단**(403/429/캡차): 즉시 중단 → 수집분까지 **부분 리포트**, `incomplete: true`와
  중단 지점 명시. **우회 금지, User-Agent 위장 금지**
- **레이아웃 변경 감지**: 필수 필드 결측률 >30%면 "사이트 구조 변경 의심" 경고를
  리포트와 대화 양쪽에 표시하고 수집을 계속하지 않는다
- **체크포인트**: 페이지 단위로 `data/raw/`에 저장 → 중단 시 이어서 재개
- **입력 검증**: 존재하지 않는 브랜드/카테고리는 0건임을 확인하고 명시적으로 보고
  (빈 리포트를 만들지 않는다). 모호한 카테고리는 세부 후보를 제시

### v5 신규 — 인코딩 (2026-07-30 실측, 실제 사고)

- **무신사 상품 상세 HTML에 `<meta charset>` 선언이 없다.** 본문은 UTF-8인데 선언이
  없으니 도구·로케일에 따라 latin-1로 디코드되고, 그러면 한글이 `ë ë/ë¼ì´ëì¤`처럼
  깨진 채로 수집된다. **숫자 필드는 멀쩡하므로 결측률 검증을 그대로 통과한다** —
  눈으로 리포트를 봐야만 드러나는 실패다.
  - **응답 바이트를 UTF-8로 명시해 디코드한다.** 도구 기본값에 맡기지 않는다
  - **깨진 문자열에 `strip()`을 걸면 안 된다** — mojibake의 끝 바이트가 `\xa0`(NBSP)나
    `\x85`(NEL)일 때가 있고 파이썬은 이걸 공백으로 보고 지운다. 그러면 역변환으로도
    복구가 불가능해진다
- **검증기가 이걸 잡는다 (v5 신규)**: `validate_data.py`가 `name`·`brand`·`category`·
  `*_display`에서 "UTF-8 선두 바이트 + 연속 바이트" 패턴을 찾아 **FAIL(exit 2)**을 낸다.
  제대로 디코드된 한글은 latin-1로 인코딩이 아예 안 되므로 오탐이 없다.
  결측률이 아니라 **문자 자체의 온전함**을 보는 첫 검사다
- 사고 기록(2026-07-29 → 07-30 복구): 인사일런스 라인시트의 `category` **564행 전부**가
  깨진 채 리포트까지 나갔다. 카테고리 37종 중 24종은 latin-1→UTF-8 역변환으로 무손실
  복구했고, 끝 바이트가 유실된 13종은 **대표 상품 PDP를 다시 받아 실측값으로** 복구했다
  (추측으로 채우지 않았다)

### v6 신규 — 29CM 브랜드 목록 (2026-07-30 실측)

- **BEST API에 브랜드 facet이 있다** — `facets.brandFacetInputs[].frontBrandNo`.
  DTO에 없는 필드는 잘못된 값을 보내도 200 + 무시로 넘어가지만, **실존 필드는 400과
  함께 필수 하위 필드명을 알려준다.** 이 성질로 필드명을 찾아냈다.
  `frontBrandNo`는 `/store/brand/{brandId}` URL의 ID와 같은 값이다
- **브랜드 ID 확증 경로가 열렸다** — 브랜드 페이지의 `__NEXT_DATA__`에
  `{"brandId":1642,"nameKor":"인사일런스","nameEng":"INSILENCE"}`가 **서버 렌더**된다.
  상품 목록은 없지만 브랜드 메타는 있으므로 ID→이름 확인이 된다.
  기존 "brandId=1642는 검색 결과 제목으로 추정"이라는 미검증 항목이 해소됐다
- **가격이 세 개다 — 판매가는 쿠폰적용가로 담는다 (v8 개정, 2026-07-30)**.
  실측: `originalPrice` 54,000 / `sellPrice` 43,200 / `displayPrice` 37,160.
  `displayPrice`가 쿠폰적용가고 **이것이 계약의 `price_sale`이다.**
  `saleRate`도 `displayPrice` 기준이라 짝이 맞으므로 재계산이 필요 없다.
  구 규칙(`sellPrice`만 쓰고 쿠폰가는 버림)은 폐기됐다 — 로우클래식 100개 중 22개가
  `displayPrice != sellPrice`이고, 그중 정가=판매가인데 쿠폰만 걸린 상품은
  `sellPrice`로 담으면 **"할인 없음"으로 기록된다**
- **이 API는 랭킹이라 창을 좁게 잡으면 카탈로그가 조용히 잘린다** — 인사일런스 유니크
  상품 수: `MONTHLY`+`CLICK` **422** / `MONTHLY`+`POPULARITY` 421 / `DAILY` 409 /
  `WEEKLY` **365** / `HOURLY` **26**. 전 조합 합집합도 422다
  (**그리고 그 422가 전량이 아니다 — 실제 카탈로그는 435개다.** 위 총계 항목 참조).
  **스토리 C 기본값인 `HOURLY`를 스토리 A에 쓰면 카탈로그의 94%가 사라진다.**
  스토리 A는 `MONTHLY`로 **정렬 종류(`POPULARITY`/`CLICK`/`ORDER`/`LIKE`)를 훑어 합집합**을
  만든다. 누락된 상품은 **"상대 플랫폼 단독 입점"으로 잘못 집계**되어 §4 스토리1의
  단독 입점 분석을 직접 오염시킨다. `MONTHS_3`·`MONTHS_6`은 HTTP 500이라 못 쓴다
- **총계를 주지 않는다** — `pagination`에 `page`/`size`/`hasNext`만 있고 총 개수가 없다.
  브랜드 페이지 `__NEXT_DATA__`에도 상품 수가 없다(`likeCount`만 있다).
- **⚠️ 그래서 쓰던 완전성 근거 두 개(`hasNext=false` 도달 · 정렬 조합 간 합집합이 더 늘지
  않음)는 완전성을 보장하지 않는다 — 브라우저 대조로 반박됐다 (2026-07-30).**
  두 근거를 **모두 만족한 422건**이 실제로는 **435건 중 422건**이었다. 누락 13건 중
  **11건이 품절**이다. 합집합이 422에서 포화되는 것은 **완전성의 근거가 아니라
  정렬들이 같은 집합을 반복해서 준다는 뜻**이었다.
  **누락 원인은 특정하지 못했다** — 품절 필터가 아니고(수집분에 품절 120건 존재)
  저반응 때문도 아니다(누락분 좋아요 4~39·후기 0~3은 수집분이 커버하는 구간).
  누락이 품절 쪽으로 3배 치우칠 뿐이다(85% vs 28%). **예측이 불가능하다는 것이
  화면 총계 대조를 유일한 근거로 만든다.**
  - **완전성 근거는 화면 총계 대조뿐이다** — 브랜드 페이지가 `435개`를 화면에 노출한다.
    `source_total`에는 **화면 총계**를 담고, 수집 건수를 넣지 않는다(넣으면 순환 검증이 된다)
  - **전량이 필요한 스토리1·2는 경로 B로 모은다** (§2). 경로 A는 정확값 보완용이다
  - 품절 누락은 §4 스토리1의 **단독 입점 분석을 직접 오염시킨다** — 상대 플랫폼에만 있는
    것처럼 집계된다. 아래 `HOURLY` 함정과 같은 종류의 사고이며 원인만 다르다
- **중복 상품이 온다** — 인사일런스 5페이지에서 422건을 받았으나 유니크 `itemId`는 421개다.
  **`product_id` 기준 dedup이 필수다** (랭킹순 페이지네이션 중 순위가 흔들리면 생기는
  현상으로 보인다). 스토리1은 중복이 경고 대상이므로 dedup 없이 넘기면 검증기가 짚는다
- **카테고리는 코드로만 온다** — `extraInfo.categories[]`에 `largeCategoryCode` /
  `mediumCategoryCode` / `smallCategoryCode`가 있고 이름이 없다. 이름은 카테고리 트리 API
  (`recommend-api.29cm.co.kr/api/v4/best/categories?categoryList=<코드,..>`)로 해석한다.
  `smallCategoryCode`가 `null`인 상품이 있어 **중분류로 폴백**해야 한다

## 8. 성공 기준 (스킬 전체)

정량:
- 트리거 테스트: should-trigger 10건 중 ≥9 로드, should-NOT-trigger 6건 중 0 로드.
  **트리거 필요조건: 요청에 플랫폼 이름(무신사/29cm) 명시** — 브랜드/카테고리만으로는
  트리거하지 않는다
- 스토리별 자연어 요청 1개로 완주 (파라미터 누락 시 질문 1회 허용,
  스토리2 범위 협의는 예외적으로 허용)
- 필수 필드 결측 <5%, 재시도로 해소되지 않은 실패 요청 0
- **스크립트 회귀 테스트 전건 통과** (`python3 tests/run_tests.py`)

정성 (DoD):
- 3개 스토리 데모: 인사일런스 라인시트 / 데님팬츠 전수조사 / 무신사 바지 랭킹 top 100
- 결과물이 HTML 페이지로 저장되고 브라우저에서 열림
- 스킬이 폴더/zip으로 배포 가능, 사용법 문서화
- 선빈 컨펌
