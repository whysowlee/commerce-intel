## 1. 배경

무신사·29CM는 공개 API를 제공하지 않는다. 이 프로젝트는 두 사이트에서 자연어 태스크를
수행하는 **강건한 스킬의 예제**를 만든다. 스킬은 Agent Skills 개방 표준을 따르며 특정
실행 환경에 국한되지 않는다.

### 접근 정책 (조사로 확인)

- 무신사 `robots.txt`는 일반 봇을 `Disallow: /`로 막지만 **`Claude-User`·`Claude-SearchBot`은
  `Allow: /`로 전면 허용**한다.
- 29CM `robots.txt`는 `*`에 `Allow: /`이고 로그인 영역만 막는다.
- 두 사이트 모두 403·캡차·봇 챌린지 없이 전 페이지 200이 확인됐다.

즉 이 스킬은 **우회 없이 사이트가 밝힌 정책 안에서** 동작한다.
User-Agent 위장은 금지한다(§7).

## 2. 실행 환경과 아키텍처

### 실행 환경 (둘 다 지원)

| 프로필 | 페이지 접근 | 후처리·리포트 생성 |
|---|---|---|
| Aside (주 환경) | 내장 에이전트가 스킬의 사이트 플레이북을 따라 수행 | 코드 실행 가능 시 `scripts/`, 불가 시 `assets/report-template.html` 구조를 따라 직접 생성 |
| Claude Code | 환경이 제공하는 웹 도구로 플레이북 수행 | `scripts/` (deterministic) |

### 설계 원칙

1. **플랫폼 중립** — SKILL.md는 어떤 에이전트든 따라할 수 있는 절차서로 쓴다.
   특정 도구 이름에 의존하는 지시를 SKILL.md에 두지 않는다.
2. **deterministic 후처리** — 수집 결과는 §6 데이터 계약대로 JSON에 담고,
   검증·집계·diff·HTML 생성은 `scripts/`가 한다.
   **데이터 계약이 수집(에이전트)과 처리(코드) 사이의 이식성 경계다.**
3. **단일 스킬 + 사이트 어댑터** — 스킬은 하나, 사이트별 상세는 `references/<site>.md`로
   분리한다(progressive disclosure). 신규 사이트는 references 추가로 확장한다.
4. **판단은 최대한 코드로 내린다** — 사람의 해석이 개입할수록 결과가 흔들린다.
   만족/불만족 판정(§4-B), 결측 판정, 변화 감지는 전부 코드가 한다.

### 수집 경로 2단 폴백 (v2 신규)

조사 결과 **페이지마다 서버 렌더 여부가 다르다.** 화면만 읽는 설계로는 랭킹과 브랜드
상품 목록이 잡히지 않는다.

| 페이지 | 무신사 | 29CM |
|---|---|---|
| 상품 상세 | 화면에 있음 | 화면에 있음 (JSON-LD) |
| 카테고리 목록 | **화면에 있음** | 껍데기만 |
| 브랜드 목록 | 껍데기만 | 껍데기만 |
| 랭킹 | 껍데기만 | (해당 없음) |

그래서 수집은 두 경로를 둔다.

- **경로 A** — 사이트가 자기 화면을 그릴 때 쓰는 JSON을 그대로 쓴다. 무신사는 브랜드
  전 상품·랭킹·리뷰 전부 비로그인 200이 확인됐다. 빠르고 파싱이 안정적이다.
- **경로 B** — 화면을 열어 눈에 보이는 값을 읽는다. 경로 A의 응답 모양이 어댑터 문서와
  다를 때 내려간다. 29CM 목록은 경로 A를 못 찾아 **처음부터 경로 B**다.

어느 경로를 썼는지 `meta.notes`에 기록한다. 경로가 바뀌어도 §6 계약은 같으므로
리포트 코드는 영향받지 않는다.

### 스킬 폴더 구조

```
commerce-research/
```

## 3. 범위 / 비범위

### 범위

- P0: 무신사에서 스토리 1·2·3 각각 자연어 요청 1개로 end-to-end 수행
- P0: 결과가 HTML 페이지로 저장됨 (이미지는 원본 URL 핫링크)
- P1: 29CM 어댑터 — 목록이 경로 B뿐이라 무신사보다 느리고 불안정하다. 무신사가 먼저다
- 비로그인 상태에서 접근 가능한 데이터만 수집
- 수치는 **사이트 노출값만**. 추정·보간하지 않는다. 미노출은 `null`("미노출"로 표기)

### 비범위

- 로그인 전용 데이터, 구매·결제 등 상태를 바꾸는 모든 행위
- 에이블리/지그재그/W컨셉/자사몰 (구조상 확장 가능하게만 설계)
- 판매량 추정 모델 (리뷰 수 기반 역산 등 일체의 추정)
- 플랫폼 간 동일 상품 매칭 (스토리1 비교는 "플랫폼별 상위 목록 나란히 표시"로 한정)
- 스킬에 내장된 스케줄러 (주기 실행 자체는 v3에서 스펙에 들어왔다 — §4 스토리3.
  단 실행 주체는 스킬 밖의 스케줄러이고, 데모 기준은 Claude Code 스케줄 기능이다)
- 이미지 다운로드·재배포 (속성 분류용 임시 다운로드는 예외)
- **리뷰 본문 수집·해석** (v3) — 만족/불만족 판단은 노출된 후기 수·평균 평점만 쓴다(§4 스토리2)

## 4. 유저 스토리별 스펙

### 스토리 1 — 브랜드 라인시트

- **트리거 예**: "무신사에서 인사일런스 상품 전체 라인시트로 정리해줘"
- **입력**: 브랜드명(필수), 사이트(**필수 — 기본값 없음**, 요청에 명시된 것만)
- **처리**: 브랜드 상품 목록 전체 순회 → 상품별 필드 수집(§6) → JSON → 검증 → HTML
- **규모 상한 (v4)**: **2,000개까지 묻지 않고 진행** (초과 시 규모를 알리고 좁힐 축 협의 —
  §4 스토리2와 같은 절차). 근거: 스토리1의 지배 비용은 목록이 아니라 **상품당 상세 방문
  1회**(조회수 구간·누적판매가 상세에만 노출)로, 예의 대기 포함 상품당 ~1.2초
  → 2,000개 ≈ 40분이 단일 요청 완주 UX의 한계선. 인사일런스는 564개 / 10페이지(실측)로
  여유 있게 통과한다. 전문 브랜드 대부분이 수백~2천 규모라 실사용에서 협의는 드물다
- **출력 리포트**: ① 헤더(브랜드, 수집 시각, 사이트, 상품 수, 결측·노출 요약)
  ② 플랫폼별 품목 인기 ③ 플랫폼별 인기 상품 ④ 전 상품 표(이미지, 상품명, 카테고리,
  정가/판매가/할인율, 후기 수, 평점, 조회수, 누적판매, 좋아요, 링크)
- **플랫폼별 품목 인기 (v3 구체화)**: "플랫폼별로 어떤 품목이 인기인가"의 답.
  품목 = 카테고리. 사이트별로 **품목 단위 하트 합·후기 합**을 집계해 나란히 보여준다
  (예: 무신사에선 니트가, 29CM에선 코트가 인기). 노출값의 합산일 뿐 추정이 아니며,
  **같은 상품을 플랫폼 간에 매칭하지 않는다**(비범위 유지). `build_report.py`가 자동 계산
- **플랫폼별 인기 상품 규칙**: 사이트마다 노출 지표가 다르므로 그리는 차트는 데이터가
  결정한다 — 정확한 정수로 노출된 지표만 상위 10 차트를 만들고, 미노출 지표는
  **차트를 만들지 않는다.** 구간 표기 값(§6)은 순위 비교에 쓰지 않는다.
  사이트별 차트 개수가 달라지는 것이 정상이다.
- **성공 기준**: 상품 수가 사이트 노출 총계의 ±5% 이내, 필수 필드 결측 <5%

### 스토리 2 — 상품군 시장 전수조사

- **트리거 예**: "무신사 데님팬츠 시장 전수조사 해줘"
- **입력**: 카테고리명(필수), 사이트(**필수 — 기본값 없음**), 성별(선택)

#### 리뷰 본문은 수집하지 않는다 (v3 — 사용자 결정)

만족/불만족 판단 재료는 사이트가 각 상품에 노출한 **후기 수와 평균 평점**뿐이다.
두 사이트 모두 이 값이 목록/상세에서 바로 보이므로 별도 수집 비용이 없다.
리뷰를 한 건씩 읽고 해석·요약하는 일은 **비범위**다.

리포트가 계산하는 것(전부 deterministic — `build_report.py`):
- 후기 수 **가중** 평균 평점 (후기 많은 상품이 더 무겁게)
- 상품 평점 분포 (~2.9 / 3.0~3.4 / 3.5~3.9 / 4.0~4.4 / 4.5~, 평점 미노출은 제외하고 건수 명시)
- 실수로 `reviews[]`가 담겨 오면 `validate_data.py`가 경고한다

#### 범위 정책 (v4 — 임계값 3,000)

조사 결과 무신사 데님팬츠(`003002`)는 **24,673개 / 412페이지**다.
목록 수집 자체는 1만 개도 감당되지만(60개/페이지 × 167회 ≈ 4~7분), **목록은 지배 비용이
아니다.** 스토리2의 실제 비용은 ① 상품당 상세 방문 1회(조회수 구간·누적판매) ~1.2초
② 핏 분류 중 **이미지 확인이 필요한 ~26%**(상품명 텍스트 분류 74% — 175개 실측) 장당
~4초로, 합쳐 상품당 ~2.3초다. 3,000개 ≈ 2시간이 단일 실행의 현실적 한계이고,
1만 개는 ~7시간이라 성립하지 않는다 (v3의 1만 기준은 목록 비용만 본 오류였다).

절차 — SKILL.md에 알고리즘으로 명시돼 있다:

1. 목록 첫 페이지에서 **사이트가 말하는 총 개수**를 읽는다 (`source_total`)
2. **0건** → 중단, "검색 0건" 보고
3. **3,000건 이하** → 묻지 않고 진행. 시작 시 개수·예상 소요 한 줄 보고
4. **3,000건 초과** → 수집을 시작하지 않는다. 좁힐 축의 **실제 개수를 조회해서**
   제시하고 사용자가 고른다. "전체로"라고 하면 전체 진행(예상 소요 먼저 보고)
5. 최종 범위를 `meta.target`에 쓴다 — "데님팬츠(남성)" 형식. 리포트 헤더에 그대로 실린다

**임의 샘플링 금지** — 묻지 않고 상위 N개만 수집하는 것이 최악의 실패다.

좁힐 수 있는 축(우선순위 순):

| 축 | 무신사 | 29CM |
|---|---|---|
| **성별** | `gf` 파라미터 (`A`/`M`/`F`) | 대분류 코드에 이미 포함 (여성의류 `268100100` / 남성의류 `272100100`) |
| 세부 카테고리 | 6자리 소분류 | 9자리 소분류 (예: 남성 데님 팬츠 `272104104`) |
| **가격대** | `minPrice`/`maxPrice` **확인** (10~20만원 5,464 실측) | 미검증 |
| 브랜드 | PLP 필터 파라미터 미검증 | 미검증 |

성별 필터의 실제 축소 효과는 §4 부록에 기록한다.

#### 처리

1. 카테고리 특정 → 규모 확인 → 범위 결정 (위 절차)
2. 상품 목록 전체 수집 — 후기 수·평점·좋아요는 목록 노출값 그대로
3. **속성 분류** — 근거 순서: ① 상품명·옵션·상세 텍스트 → ② 대표 이미지 확인 →
   ③ `unknown`. 찍지 않는다. 판단 근거를 `attributes_basis`에 남긴다
4. 검증 → 리포트

#### 조사 칼럼 구성 (2026-07-29 확정)

- **표 칼럼**: 상품명(링크) · 브랜드 · 카테고리 · 정가/판매가/할인율 · 후기 수 · 평점 ·
  조회수(구간 문구) · 누적판매 · 좋아요 · 품절 + 분류 속성. **이미지 열은 없다**(스토리2만)
- **분류 속성은 핏만 P0** — 부츠컷/와이드/스트레이트/슬림/테이퍼드/unknown.
  상품명 텍스트로 74%가 해결되고(175개 실측) 나머지 ~26%만 이미지 확인이라
  상한 3,000 규모에서 감당된다
- 워싱 톤·기장·소재 등 추가 속성은 **사용자가 명시적으로 요청할 때만** 수행한다.
  이미지 전수 확인이 필요한 속성은 예상 소요를 먼저 알린다

- **출력 리포트**: ① 시장 요약(상품 수, 후기 합계, 중위 가격, 가중 평균 평점, 가격 분포,
  상품 평점 분포, 속성 분포) ② 전 상품 표(이미지 열 없이 전 행, 속성 컬럼 포함)
- **성공 기준**: 합의된 범위 완주(중단 시 부분 리포트에 명시), 속성 분류율 ≥80%,
  후기 수·평점 결측이 실제 미노출과 일치(추정·보간 0건)

### 스토리 3 — 카테고리 랭킹 모니터링

- **트리거 예**: "무신사 바지 랭킹 top 100, 지난 일주일 변화 보여줘"
- **입력**: 카테고리(필수), 사이트(**필수 — 기본값 없음**), **기간(필수)**
- **기간 미입력 시**: 변화 분석을 트리거하지 않는다. 현재 스냅샷만 수집하고 안내한다
- **처리**: 현재 top 100 스냅샷 → `data/snapshots/` 축적 → 기간 내 스냅샷 diff → 변화 리포트
- **수집 규모 (조사 확인)**: 무신사 랭킹 API는 한 번에 102개를 준다.
  **top 100은 1페이지로 끝난다** — 순회 부담이 없다.
  29CM BEST API도 100개/페이지라 top 100은 요청 1번이다
- **29CM 랭킹 기준 (v3 확정, 2026-07-29 검증)**: 소분류 랭킹은 중분류를 필터한 것이
  아니라 **독립 랭킹**이다(데님 top 100의 84%가 바지 top 100에 없음을 대조로 확인).
  기본 기준은 **실시간(HOURLY) + 인기순(POPULARITY) + 세그먼트 전체**.
  **폴백**: BEST API 불가 시 중분류('바지')로 낮춰 수집하되 리포트에 명시하고,
  `target`을 중분류 이름으로 저장해 **기존 소분류 스냅샷과는 비교하지 않는다**
  (다른 랭킹이라 diff가 성립하지 않는다)
- **실시간 지표 (v2 신규)**: 무신사 랭킹 목록에는 `"1.2천명이 보는 중"`,
  `"48명이 구매 중"`이 붙는다(바지 랭킹 102건 중 98건에 존재).
  이것이 유저 스토리가 요구한 "몇 명이 보고 있음, 구매함"이다.
  `viewers_now`/`buyers_now`에 담는다. **랭킹 목록에만 있고 상품 상세에는 없다.**
  사이트가 반올림해 보여준 값이므로 정밀한 수치로 다루지 않는다
- **출력 리포트**: ① 기간·스냅샷 목록 ② 변동 요약(신규 진입/이탈/급상승/급하락)
  ③ 가격·할인 변화 표(할인 시작 시점 추적) ④ 상품별 순위 추이.
  **모든 상품 표에 이미지 열 포함** (v3 — 이미지 제외는 스토리2뿐이다)
- **성공 기준**: 스냅샷 2개 이상이면 diff 리포트 생성. 1개 이하면 "비교 대상 부족"을
  명시하고 현재 스냅샷 리포트만 (빈 diff를 만들지 않는다)
- **주기 실행 (v3 확정)**: **30분에 1번** 랭킹을 확인해 스냅샷을 축적한다.
  1회 실행 = 스냅샷 1개.
  - **실행 주체: Claude Code 스케줄 기능**(cron 등록)이 데모 기준이다.
    30분 주기로 "무신사 바지 랭킹 스냅샷 찍어놔" 요청이 이 저장소에서 실행되도록
    등록한다. 스냅샷은 §5의 고정 폴더에 쌓인다
  - 스킬 자체는 여전히 스케줄러를 내장하지 않는다 — 어느 환경에서든
    "1회 실행 = 스냅샷 1개"만 보장하고, 주기는 바깥 스케줄러가 만든다
- **과거 소급 불가 — 확정 (2026-07-29 조사 완료)**: 서버 측 검증 결과
  **과거 데이터의 출처는 30분 축적분뿐이다.**
  - 무신사 현행 랭킹 API: 날짜 파라미터가 전부 무시됨을 응답 대조로 확인.
    `period`는 트레일링 윈도우라 기준일 지정 불가
  - 29CM BEST API: 날짜형 필드 후보 17개가 **DTO에 존재하지 않음**을 타입 프로브로 확인
  - Wayback 아카이브: 두 사이트 랭킹 페이지 모두 CSR 껍데기라 실질 0건
  - 무신사 월간 랭킹 아카이브 API(TOP30·월 단위)가 존재하지만 **쓰지 않는다**
    (2026-07-29 사용자 결정) — 변화 분석의 재료는 축적 스냅샷으로 일원화한다
  - 부수 확인: 무신사 REALTIME 랭킹의 원본 갱신 주기가 **약 30분**이다 —
    30분 축적 주기가 원본 갱신 주기와 정확히 맞는다(더 자주 찍어도 중복일 뿐)

### §4 부록 — 성별 필터 축소 효과 (2026-07-29 실측 완료)

| 대상 | 전체 | 남성 | 여성 |
|---|---|---|---|
| 무신사 데님팬츠 `003002` | 24,673~24,692* | **14,275** (`gf=M`) | **14,767** (`gf=F`) |
| 29CM 데님 팬츠 | — | `272104104` **694** (7페이지 실측) | `268106104` **2,580** (26페이지 실측) |

\* 실시간 변동 — 같은 날 두 번 조회한 값의 범위다.

**발견 — 무신사는 성별 축의 축소 효과가 제한적이다**: 남(14,275)+여(14,767)=29,042 >
전체(24,692). **유니섹스 상품이 양쪽에 중복 집계**되기 때문에 성별로 좁혀도 절반이 아니라
~40%만 줄어든다. 무신사 데님팬츠는 성별로 좁혀도 1.4만이라 상한(3,000)을 넘으므로,
**세부 카테고리 축과 병행**해야 상한 아래로 내려온다.

29CM는 성별이 카테고리 트리에 내장돼 있어 소분류를 고르면 규모가 바로 작아진다 —
여성 데님 2,580개·남성 694개는 협의 없이 진행 가능한 규모다.

### 스냅샷 축적 공간 (v3 확정, 2026-07-29)

- **위치 고정**: 이 저장소 루트의 `data/snapshots/` — **git에는 올리지 않는다**(.gitignore).
  주기 실행이 매번 같은 곳에 쌓여야 diff가 성립하므로, 스케줄을 등록할 때는
  이 폴더의 **절대 경로**로 고정한다
- **보존**: 데모 단계에서는 전부 보존한다. 정리·압축 정책 없음.
  (30분 주기 기준 하루 48개 ≈ 2~3MB/카테고리 — 당분간 문제없는 규모)
- 폴더의 무결성은 읽기 시점에 코드가 보장한다 — `diff_snapshots.py`가 meta 기준으로
  site/target/기간을 걸러내므로, 폴더에 다른 스냅샷이 섞여 있어도 안전하다

## 6. 데이터 계약 (수집 JSON 스키마)

공통 메타: `{site, story, target, collected_at, item_count, source_total, incomplete, notes[]}`

`source_total`은 **사이트가 말한 총 개수**다. 수집 완전성 판정(±5%)의 기준이 된다.

### 상품 레코드

| 필드 | 필수 | 설명 |
|---|---|---|
| `product_id` `name` `url` `image_url` `brand` `category` | 항상 | 결측률 <5% 기준 대상 |
| `price_original` `price_sale` `discount_rate` | 항상 | 할인 없으면 sale=original. **쿠폰가는 판매가로 치지 않는다** |
| `sold_out` | 항상 | 품절도 수집하되 표시한다 |
| `review_count` `rating` | 노출 시 | 미노출 `null` |
| `view_count` `purchase_count` `like_count` | 노출 시 | 미노출 `null` |
| `view_count_display` `purchase_count_display` | 구간 표기 시 | **v2 신규** — 아래 참조 |
| `viewers_now` `buyers_now` | 랭킹 목록만 | **v2 신규** — "N명이 보는 중/구매 중" |
| `rank` | 스토리3 | 랭킹 순위 |
| `attributes` `attributes_basis` | 스토리2 | 분류 결과와 그 근거(`name`/`detail`/`image`/`unknown`) |

`reviews[]`(리뷰 본문)는 **v3에서 계약에서 제외됐다.** 담겨 오면 `validate_data.py`가 경고한다.

### 구간 표기 값을 정수로 바꾸지 않는다 (v2 신규)

무신사 상품 상세의 조회수는 **`"300회 이상 (최근 1개월)"`처럼 구간으로 표기된다.**
이걸 `view_count: 300`으로 담으면 없는 정밀도를 만들어내는 것이고, 그 값으로 순위를
매기면 리포트가 조용히 틀린다.

규칙: **정확한 정수가 노출될 때만 `view_count`에 담는다. 구간 표기면 `view_count`는
`null`로 두고 원문을 `view_count_display`에 그대로 담는다.**
리포트는 구간 표기를 문구 그대로 싣고, 그 값으로는 순위 차트를 만들지 않는다.
둘 다 채워져 있으면 `validate_data.py`가 경고한다.

### 사이트별 노출 지표 (v2 — v1 가정 정정)

| 지표 | 무신사 | 29CM |
|---|---|---|
| 후기 수 / 평점 | 노출 | 노출 |
| **좋아요(하트)** | **노출** (상품 하트 수) | **노출** (`heartCount`) |
| **조회수** | **구간 표기로 노출** (`300회 이상 (최근 1개월)`) | **미노출** (필드 자체 없음) |
| 누적 판매량 | 랭킹 목록 배지 (`판매 5.5천개`) | 기본 꺼짐 (`isDisplaySellQty: false`) |
| 실시간 "보는 중/구매 중" | **노출** (랭킹 목록만) | 없음 |

> v1은 "29cm는 조회수 미노출"만 가정했고 무신사는 조회수·좋아요가 정수로 다 있다고 봤다.
> 실제로는 무신사 조회수가 구간 표기이고, 좋아요는 양쪽 다 노출한다.
> 사이트별 상세는 `references/<site>.md`의 매핑 표에서 관리한다.

### 평점 스케일 통일

`rating`은 **5점 만점**으로 통일한다. 무신사는 목록 응답의 `reviewScore`가 **0~100**,
상세의 `satisfactionScore`가 0~5로 **한 사이트 안에서 스케일이 두 개다.**
변환을 빠뜨리면 `validate_data.py`가 "평점이 0~5 범위를 벗어난다"고 경고한다.

## 7. 강건성 정책

- **속도**: 페이지 요청 간 0.5–1.5초 대기. 페이지네이션 안전 상한 200페이지
- **재시도**: 실패 시 2회 재시도(간격 증가). 3연속 실패 시 건너뛰고 `notes`에 기록
- **차단**(403/429/캡차): 즉시 중단 → 수집분까지 **부분 리포트**, `incomplete: true`와
  중단 지점 명시. **우회 금지, User-Agent 위장 금지**
- **레이아웃 변경 감지**: 필수 필드 결측률 >30%면 "사이트 구조 변경 의심" 경고를
  리포트와 대화 양쪽에 표시하고 수집을 계속하지 않는다
- **체크포인트**: 페이지 단위로 `data/raw/`에 저장 → 중단 시 이어서 재개
- **입력 검증**: 존재하지 않는 브랜드/카테고리는 0건임을 확인하고 명시적으로 보고
  (빈 리포트를 만들지 않는다). 모호한 카테고리는 세부 후보를 제시

### v2 신규 — 조사에서 나온 함정들

- **평점 스케일이 사이트 안에서 두 개** — 목록 0~100 / 상세 0~5 (무신사). 5점으로 통일
- **`totalPages`를 믿지 않는다** — 무신사 리뷰 212건이 `totalPages=22`로 오지만 실제로는
  21페이지에서 끝난다. **빈 결과가 나올 때까지** 돌아 종료를 판정한다
- **리뷰 페이지 시작 번호가 사이트마다 다르다** — 무신사 1부터, 29CM **0부터**
- **`pageSize` 상한** — 무신사 리뷰는 20이 상한, 21 이상은 400
- **잘못된 파라미터가 조용히 무시된다** — 무신사 `sortCode`는 모르는 값을 넣어도 400 없이
  기본 정렬로 폴백한다. 정렬을 바꿨으면 결과가 실제로 달라졌는지 확인한다.
  반대로 `caller`는 **없으면 400**이다(브랜드 `BRAND` / 카테고리 `CATEGORY`)
- **스냅 지표를 상품 지표로 읽지 않는다** — 무신사 상품 상세의 `snapReviews.aggregations`에
  `viewCount`/`likeCount`가 있으나 **스냅 게시물 지표**다. 상품 조회수가 아니다
- **마크다운 변환 결과로 "데이터 없음"을 판정하지 않는다** — 29CM 상품 상세는 변환기를
  거치면 빈 껍데기로 보이지만 원본 HTML에는 JSON-LD가 들어 있다. 원본을 확인한다
- **죽은 URL** — `store.musinsa.com/app/contents/bestranking`,
  `search.musinsa.com/ranking/best`, `/brands/`(복수형)는 전부 실패한다

### v4 신규 — 조사에서 나온 함정

- **무신사 카테고리 PLP API의 page≥2는 서명이 필요하다** — page 번호를 직접 조립해
  요청하면 403 "잘못된 접근입니다"이지만, **page=1 응답의 `nextPageUrl`(hmacId 서명 포함)을
  그대로 따라가면 200이다** (2026-07-29 실측). 브랜드 PLP와 같은 규칙이 카테고리에도
  적용된다: **페이지 URL을 조립하지 말고 항상 `nextPageUrl` 체인을 따른다.**
  부가 확인: 화면 URL(`/category/{code}/goods`)은 `page` 파라미터를 무시하고 항상
  1페이지를 렌더한다(무한 스크롤) — 경로 B 순회도 브라우저 없이는 안 되므로,
  비브라우저 환경에서 카테고리 전량 수집은 경로 A 체인이 유일한 길이다.
  가격 필터 `minPrice`/`maxPrice`는 API·화면 모두 동작 확인(총계가 실제로 줄어든다)
