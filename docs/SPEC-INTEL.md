## 이 문서를 고치는 규칙 (2026-08-03 사용자 지시로 개정)

**이 스펙은 동결 문서가 아니다. 구현이 바뀌면 스펙을 그에 맞춰 갱신한다.**
구 규칙("스펙을 고치지 말고 어긋난다는 사실을 보고하고 지시를 기다린다")은 폐기됐다 —
문서가 구현보다 낡으면 다음 세션이 낡은 쪽을 사실로 읽는 것이 더 큰 해악이다.

지킬 것은 셋뿐이다.

1. **구현과 함께 고친다** — 코드를 바꾼 커밋에서 스펙도 같이 바꾼다. 나중에 몰아 쓰지 않는다.
2. **왜 바뀌었는지 남긴다** — 결정 기록(§1)에 한 줄, 날짜와 근거(사용자 지시/실측)를 적는다.
   기각된 대안도 적는다. 그게 다음 사람이 되돌리지 않게 하는 장치다.
3. **실측과 판단을 섞지 않는다** — 잰 값은 잰 값으로, 결정은 결정으로 적는다.
   미검증 추정을 사실처럼 적는 것은 이 프로젝트의 제1원칙 위반이고 이 규칙에도 예외가 없다.

## §0 기본 예제와의 차이 (요구 원문)

1. raw data가 하드코딩이 아니라 **구글 시트 형태로 저장**되어야 한다(업데이트 가능).
   이미 저장된 레코드는 **재조사/재저장하지 않는** 재사용 가능한 DB 설계가 필요하다.
2. 리포트는 **interactive 산점도를 포함**해 가격 탄력성에 대한 가설을 사용자가 직접
   도출할 수 있어야 한다. **변인통제**가 가능해야 한다(단순 data summary 금지).
3. 입점처를 하드코딩하지 않는다 — **입점처 자체를 리서치하는 서브 에이전트**와,
   처음 접하는 플랫폼의 스킬을 만드는 **skill-maker 스킬**이 필요하다.
   단 중요 플랫폼(무신사·29CM·자사몰)은 제네릭과 **따로** 전용 스킬로 만든다.
4. 유저 스토리는 3개 고정이 아니다 — 실무자 관점에서 파생되는 요구를 모두 다룬다.
   궁극 목적은 **시장 조사와 가격 탄력성 분석**이다.

## §2 저장 계층 — 로컬 DB 정본

### 2-1 스키마 (SQLite: `data/intel.db`)

DB를 읽고 쓰는 것은 **오케스트레이터 스킬 하나뿐이다**(§5 역할 경계). 그래서 도구도
`skills/commerce-intel/scripts/intel_db.py`에 둔다 — 플랫폼 스킬은 DB를 모른다.
DB 파일 경로는 **작업 폴더 기준 `data/intel.db`**이고 `INTEL_DB`로 덮을 수 있다.


정적(비싼 판단·거의 안 변함)과 시변(관측마다 변함)을 **테이블로 분리**한다.
수집 JSON(기존 데이터 계약, SPEC v16 §6)은 그대로 유지되고, DB 적재는 그 뒤에 온다 —
**수집 → raw JSON → 검증 → DB 적재 → 시트 미러** 순서다.

| 테이블 | 무엇 | 키 | 갱신 방식 |
|---|---|---|---|
| `products` | 정적 속성: 이름·URL·이미지·브랜드·카테고리·attributes(핏 등)·basis | `(site, product_id)` | upsert. `static_verified_at`으로 TTL 관리 |
| `observations` | 시변 값: 가격·할인·후기·평점·하트·판매·조회·실시간 지표·품절·순위 | `(site, product_id, observed_at, context)` | **append only. 갱신·삭제하지 않는다** |
| `platforms` | 입점처 리서치 결과: 플랫폼명·URL·엔진·정찰 JSON·스킬 상태 | `platform_key` | upsert |
| `runs` | 수집 실행 이력: story·target·건수·source_total·incomplete·notes·raw 파일 경로 | `run_id` | append |
| `sync_state` | 시트 미러 진행 상태(테이블별 마지막 동기 지점) | 테이블명 | 내부용 |

- `observations.context`는 관측이 나온 화면이다(`ranking:바지` · `brand:인사일런스` ·
  `market:데님팬츠(남성)`). **랭킹에서 온 `viewers_now`를 다른 문맥에 섞지 않는다** —
  SPEC v16의 "출처가 섞이면 일관성이 깨진다" 원칙을 DB에서도 유지한다.
- 미노출 값은 `NULL`이다. 0과 구분한다(기존 원칙 그대로).
- 기존 축적 스냅샷 47개+는 `intel_db.py import`로 소급 적재할 수 있다 — 과거를
  버리지 않는다.

### 2-2 재사용 판정 (요구 1-1)

수집을 시작하기 전에 DB에 물어본다. 판정은 `intel_db.py`가 하고, 기준은 이렇다.

| 대상 | 규칙 |
|---|---|
| **정적 속성** | `static_verified_at`이 **90일(D7)** 이내면 재확인하지 않는다. 특히 이미지 판단이 필요한 핏 분류는 DB 값을 그대로 쓴다. 90일이 지났으면 다음 수집에서 재확인 대상으로 보고한다 |
| **시변 값** | 같은 `(site, context)`의 최신 관측이 **사이트 원본 갱신 주기(D8)** 이내면 수집을 생략하고 기존 관측을 쓴다. 주기는 플랫폼 스킬에 명시된 값(무신사 실시간 랭킹 30분, 29CM 랭킹 1시간)이고, 명시가 없으면 24시간이다 |
| **팀원 수집분** (D32) | `--team`을 주면 로컬에 신선한 관측이 **없을 때만** 시트 `runs` 탭을 추가로 본다. 같은 `(site, context)`를 팀원이 위 시변 규칙의 주기 안에 이미 수집했으면 중복이라고 알린다. 주기 밖이면 이력만 보고하고 통과시킨다 |
| **사용자 명시 재수집** | "새로 받아", "다시 조사해"라고 하면 두 규칙 모두 무시하고 재수집한다 |

스킵했으면 **스킵했다는 사실과 기존 관측 시각을 사용자에게 보고한다** — 조용히
옛 데이터를 새것처럼 내지 않는다.

팀 조회에는 한계가 둘 있고, 둘 다 사용자에게 그대로 말한다(D32):

- 시트는 **완료된 수집만** 안다. `runs` 행은 적재 뒤에 생기고 그 다음 미러 때 올라가므로,
  "지금 팀원이 수집 중"인 건은 잡히지 않는다 — 중복 창이 미러 주기만큼 남는다.
- 조회에 실패해도(키 없음·쿼터·네트워크) **수집을 막지 않는다.** `consulted: false`로
  떨어뜨리고 로컬 판정만으로 진행하되, 판정 근거에 "팀 커버리지 미확인"을 남긴다.

## §3 구글 시트 미러

- 방향은 **로컬 → 시트 단방향**이다. 시트는 사람이 보고·공유하는 창구다.
  시트에서 손으로 고친 값은 정본에 반영되지 않는다(다음 미러에서 덮일 수 있다) —
  이 사실을 시트 첫 탭 안내문에 명시한다.
- **읽기는 딱 한 곳뿐이다** — 팀 커버리지 판정(D32)이 `runs` 탭을 조회한다.
  이건 단방향 원칙의 예외가 아니다: 읽은 값을 정본에 쓰지 않고 "이미 수집됐나"
  판정에만 쓴다. 시트로 정본을 갱신하는 경로는 여전히 없다.
- 스프레드시트 1개, 탭 = 테이블(`products` · `observations` · `platforms` · `runs`).
- `products`·`platforms`·`runs`는 전체 다시 쓰기, `observations`는 **증분 append**
  (`sync_state` 기준). 시트 셀 한도(1,000만)에 접근하면 오래된 관측 탭을 연도별로
  분리한다 — 정본은 로컬이므로 시트 분리가 데이터 손실이 아니다.
- 인증은 서비스 계정 JSON 키다. 설정 절차는 `docs/SHEETS-SETUP.md`. 키 파일 경로는
  환경변수 `INTEL_SHEETS_CREDENTIALS`(기본 `~/.config/intel/service-account.json`),
  스프레드시트 ID는 `data/sheets_config.json`에 둔다. **키 파일은 git에 넣지 않는다.**
- 시트 인증이 없거나 실패해도 **수집·DB 적재는 진행한다.** 미러만 밀린 상태가 되고,
  다음 성공 시 `sync_state`부터 따라잡는다. 실패 사실은 사용자에게 보고한다.
- **쓰는 사람은 1명이다**(D31 전원 풀 배포의 귀결). `products`·`runs` 등은 전체 다시
  쓰기이므로, 팀원이 편집자 권한으로 미러를 돌리면 자기 로컬 DB 내용으로 팀 축적을
  덮고 자기 DB에 없는 탭은 지운다. **팀원 서비스 계정은 뷰어**로 준다 — 그래야
  `check --team`(D32) 읽기는 되고 덮어쓰기는 불가능하다. 팀원 데이터는 시트가 아니라
  `.db` 파일로 받아 `merge`한다. 절차는 `docs/SHEETS-SETUP.md` §5.

## §4 분석 리포트 — 가설 도출 도구

리포트는 요약이 아니라 **가설 도출 도구**다(요구 2). 생성물은 로컬 단일 HTML
(외부 네트워크 불필요)이고, 다음을 갖춘다.

**리포트는 모듈의 조합이다**(D25). 아래 요소는 모듈로 존재하고 사용자가 고른 것만 한
리포트로 조립된다 — 필요한 것을 고르는 것이지 종류를 고르는 것이 아니다.

| 모듈 | 내용 | 나오는 조건 |
|---|---|---|
| `kpi` | n·중위 판매가·중위 할인율·품절·평균 옵션 품절률 | 항상 |
| `scatter` | 축 선택형 산점도 (X·Y·**색 기준**·로그) | 수치 축 1개 이상 |
| `dist` | 히스토그램(중위선·구간 하한 명시) | 수치 축 1개 이상 |
| `group` | 그룹별 박스 플롯 — **심슨의 역설 확인 장치** | 수치 축 1개 이상 |
| `variants` | 사이즈별 재고 (§6-6) | 옵션 관측 있음 |
| `timeseries` | 시계열 추이 (D24) | 시점 2개 이상 |
| `events` | 가격 변경 사건과 관측 창 증분 | 변경 감지분 있음 |
| `linesheet` | 플랫폼 합집합 표 (입점·가격 차이·묶어 보기) | 플랫폼 2개 이상 |
| `table` | 상품 표 (전 행 유지) | 항상 |

- 기본은 전 모듈이다. 못 만든 모듈은 이유와 함께 리포트에 적는다.
- `linesheet` 모듈의 상품 매칭은 **스토리 리포트와 같은 규칙 하나**를 쓴다
  (`build_report.match_key` — 정규화 상품명 완전일치). 두 곳에 규칙을 적으면 같은
  데이터에서 다른 합집합이 나온다.
- **색만으로 계열을 구분하지 않는다** — 색 기준 축을 고르면 색과 **마커 모양**이 함께
  바뀐다. 색은 점이 많은 값 5개에 주고 나머지는 회색 + 종수를 적는다(가나다순으로 자르면
  어느 값이 색을 받을지가 이름 순서로 정해진다).

1. **변인통제 패널** — 카테고리·핏·브랜드·가격대·품절·플랫폼을 조건으로 고정/제외.
   모든 차트가 같은 필터를 공유한다. 현재 조건과 표본 수(n)가 항상 화면에 보인다 —
   **n이 작아진 채 결론을 읽는 사고를 막는다.**
2. **축 선택형 산점도** — X·Y를 수집된 수치 필드 중에서 고른다(가격·할인율·하트·
   후기 수·평점·누적판매·조회·실시간 지표·순위 변동 등). 로그 스케일 토글, 점 호버에
   상품 정보, 클릭하면 상품 URL.
3. **프록시별 적합 그래프** — 축 형태는 열려 있다(D3). 분포 비교(히스토그램·박스),
   시계열(축적 관측이 있는 상품의 지표 추이 — 순위 반전·순위권 밖 선 끊김·이동평균),
   순위 추이 등 feature 속성에 맞는 형태를 쓴다. 산점도는 방법 중 하나다.
   **시계열 뷰는 범용 대시보드에 상시 붙는다**(시점 2개 이상이면 자동 표시, D24).
4. **정직성 규칙** — 이 도구가 보여주는 것은 **가격-반응의 상관 탐색이지 엄밀한
   가격 탄력성이 아니다.** 리포트에 명시한다. 구간 표기(`300회 이상`)에서 온 값은
   축으로 쓰지 않고, 축약 파싱 값은 각주로 밝힌다(SPEC v16 §6 오차 규칙 준수).
   미노출(`NULL`)은 0으로 그리지 않는다 — 그 점은 차트에서 뺀 뒤 제외 건수를 밝힌다.

  결과는 `platforms` 테이블에 적재된다.

  미검증 항목을 사실처럼 적으면 이 프로젝트의 제1원칙 위반이다. 초안 상태는

  겹쳐 **어느 스킬이 뜰지 모호해지는 것**이 실제 해악이고, 원본 보존은 git 이력이
  이미 하고 있다. **순서를 지킨다** — 어댑터를 `platform-*`로, 스크립트를
  `commerce-intel/scripts/`로 옮긴 뒤에 삭제한다.
- `docs/SPEC.md`·`docs/TEST-CASES.md`는 **근거 아카이브**로 남긴다. 런타임에 읽히지
  않고(스킬이 아니다) 트리거에도 관여하지 않는다. 실측 근거(§7 함정 카탈로그 등)를
  다시 얻으려면 브라우저 실측을 되풀이해야 하므로 지우지 않는다.
  **intel 작업의 판단 기준은 이 문서(SPEC-INTEL)다.**

### 5-1 자사몰은 엔진에 매이지 않는다 (D9)

자사몰의 **70~80%가 Cafe24지만 예외가 있다**(Shopify 등, 2026-07-31 사용자 지적).
엔진 이름을 스킬 이름에 박으면 예외를 만났을 때 스킬 자체가 무력해진다.

```
platform-ownmall/
├── SKILL.md                  엔진 무관 절차 — 도메인 확정 → 엔진 판별 → 분기 → 수집
└── references/
    ├── engine-detect.md      판별식 카탈로그 (cafe24 · shopify · 고도몰 · 임웹 · 자체구축)
    ├── engine-cafe24.md      ← 기존 cafe24.md 승계 (실측 완료)
    ├── engine-shopify.md     신규 — 실측 전까지 전 항목 「미검증」 표기
    └── engine-unknown.md     판별 실패·미지원 → platform-generic 정찰로 인계하는 절차
```

**엔진과 무관한 것**(SKILL.md가 갖는다) — 도메인을 지어내지 않고 검색·진위 확인·
사용자 선택으로 확정한다 · 브랜드 페이지 하나로 끝나지 않으니 카테고리를 전수 순회한다 ·
반응 지표(후기·평점·좋아요)가 아예 없을 수 있고 그때는 `null`이며 우회하지 않는다 ·
화면 총계가 없을 수 있고 그때 `source_total`은 `null`이며 완전성 근거를 따로 세운다.

**엔진에 매인 것**(`references/engine-*.md`가 갖는다) — 목록 URL 형식 · 페이지 넘김
종료 신호 · 품절 판정 위치 · 카테고리 누락 같은 실측 수치.
**Cafe24에서 잰 값을 다른 엔진에 옮겨 적지 않는다**(`ALL` 23% 누락은 Cafe24 실측이다).

미지원 엔진을 만나도 **비범위로 거절하지 않는다** — `platform-generic` 정찰로 넘겨
1회성 수집을 시도하고, 반복 대상이면 `platform-skill-maker`로 `engine-*.md`를 늘린다.

## §6 옵션(컬러·사이즈) 정교화 — 라인시트 심화 (2026-07-31 신설)

라인시트를 상품 단위에서 **옵션(SKU) 단위**로 내린다. 얻으려는 것은 옵션 구성 ·
옵션별 재고 · 옵션별 판매수량이다.

### 6-1 재고 프로브 계층 (D18로 재개정 — 2026-07-31)

**아래 순서를 지킨다 — 허용의 문제가 아니라 비용의 문제다. 위 단계로 얻히면
아래로 내려가지 않는다.**

| 층 | 방법 | 상태 변경 |
|---|---|---|
| **L1 무료** | 이미 응답에 있는 옵션별 품절 상태 — 자사몰 JSON-LD `offers[].availability`, 무신사 `goodsOption`·`isSoonOutOfStock`·`isRestock`, 29CM 옵션 응답 | 없음 |
| **L2 읽기 전용 프로브** | PDP·옵션 API에 수량을 실어 **사이트가 돌려주는 재고 검증 응답·안내 문구**를 읽는다("최대 N개 구매 가능" 등) | 없음 |
| **L3 상태 변경 프로브** | 장바구니 담기·수량 변경·**결제 페이지 진입까지** 포함해 성공/실패 경계와 화면 노출 값을 읽고, **가역 조치(비우기 등)를 한다**. 승인 불요(D18) — 대신 무엇을 했고 되돌렸는지 보고한다 | 있음(가역) |

**절대 금지 (D18에서도 유지)**: **실제 결제 실행**(주문 완료·결제 수단 입력 제출),
로그인 실계정 사용(비로그인으로 안 되면 거기까지 — 필요하면 사용자에게 묻는다),
장바구니 등 변경 상태를 되돌리지 않고 남기는 것, 차단(403/429/캡차) 상태에서의 계속.

- **L3는 실패해도 되돌린다** — 담기에 성공한 뒤 예외가 나도 비우기를 반드시 시도하고,
  못 비웠으면 `meta.notes`에 남기고 사용자에게 보고한다. L3를 썼다는 사실 자체도
  보고에 포함한다(승인은 불요하지만 조용히 하지 않는다).
- 프로브는 **일반 수집보다 더 느리게** 한다(요청 간격 하한을 2배로) — 같은 상품에
  연속 요청이 몰리는 성격이라 부하가 집중된다.
- 어느 층으로 얻었는지를 **옵션마다 `stock_basis`에 남긴다**(`option_api`/`probe_read`/
  `probe_cart`/`unknown`). 층이 다르면 값의 성격도 다르다.

### 6-2 재고 정밀도 (D15)

- **이진 탐색**으로 정확한 수량을 찾는다. 상한 `N`(기본 100)까지만 보고 초과는
  `stock_qty: null` + `stock_display: "100+"`로 기록한다 — 상한을 넘긴 것과 모르는 것을
  구분한다.
- 옵션당 요청 수는 `log2(N)` 수준(N=100이면 약 7회)이다. 프로브 전에 **예상 요청 수와
  소요를 계산해 보고**한다.

### 6-3 적용 범위 (D16)

| 단계 | 대상 | 비용 |
|---|---|---|
| **기본(전체)** | 라인시트 전 상품의 **옵션 구성 + 옵션별 품절 상태**(L1) | 무료~상세 1회 |
| **심화(선택)** | 사용자가 지정한 상품 또는 하트·랭킹 상위 N개의 **재고 수량**(L2/L3) | 상품×옵션×log2(N) |

심화는 **묻지 않고 시작하지 않는다** — 대상 수·예상 요청 수·소요를 알리고 승인받는다.
전 상품 프로브를 요청받으면 규모를 계산해 보여주고 그래도 원하면 진행한다.

### 6-4 옵션별 판매수량 = 재고 시계열 감소분 (D17)

옵션별 판매수량을 노출하는 사이트는 없다. **관측된 재고의 감소분**으로 얻는다 —
관측 두 개의 차이이므로 추정이 아니다(가격 변화 감지와 같은 성격, EVIDENCE §8).

- 관측 주기는 **기존 랭킹 주기에 편승**한다(무신사 30분 · 29CM 1시간). 별도 잡을
  만들지 않고 랭킹 스냅샷 잡에 옵션 재고 관측을 얹는다.
- `stock_qty`가 줄었으면 그 차이가 **최소 판매량**이다. 늘었으면 **재입고**이고
  그 구간의 판매량은 알 수 없다.
- **밝혀야 하는 한계 2개**: ① 재입고가 섞인 구간은 **과소 집계**된다(재입고 전에 팔린
  수량이 가려진다) ② 축적이 쌓이기 전에는 값이 없다 — 첫 관측만으로는 판매량이 `null`이다.
- 리포트에는 **"최소 판매량(관측 구간 N시간, 재입고 M회 감지)"**로 표기한다.
  "판매량"이라고만 쓰면 실제보다 작은 수를 진짜 판매량으로 읽는다.

### 6-5 데이터 계약 확장

상품 레코드에 `variants[]`를 **선택 필드로** 추가한다(없으면 기존과 동일 — 하위 호환).

```json
"variants": [{
  "option_id": "4297589-BLACK-M",
  "color": "BLACK", "size": "M",
  "sold_out": false,
  "stock_qty": 7, "stock_display": null,
  "stock_basis": "probe_read",
  "observed_at": "2026-07-31 14:00:00"
}]
```

- `color`/`size`는 **사이트가 준 옵션 문자열을 파싱**해 담고, 축이 두 개가 아닌 사이트
  (단일 옵션·3축 이상)면 `option_name` 원문을 그대로 둔다. **없는 축을 지어내지 않는다.**
- DB에서는 `variants`(정적: 옵션 구성)와 `variant_observations`(시변: 재고)로 나눈다 —
  §2 products/observations 분리와 같은 이유다. 옵션별 판매수량은 저장하지 않고
  **관측 감소분으로 계산한다**(중복 저장하면 관측과 어긋날 수 있다).
- 옵션을 수집하지 않았으면 `variants`는 **없거나 `null`**이다 — 빈 배열(`[]`)은
  "옵션이 없는 상품"을 뜻하므로 구분한다.

### 6-6 사이즈별 재고 — 분석 반영 (2026-08-03 신설)

수집·적재는 되고 있었는데 **분석이 그 테이블을 읽지 않고 있었다**(2026-08-03 사용자 지적).
`variants`·`variant_observations`에서 옵션마다 마지막 관측을 가져와 상품에 붙인다.

| 필드 | 뜻 | 주의 |
|---|---|---|
| `opt_total` `opt_live` `opt_out` | 옵션 수 · 판매 중 · 품절 | 옵션 **개수**다 |
| `opt_out_rate` | 품절 옵션 비율(%) | **수량 비율이 아니다** — L1만 수집되면 수량이 없다 |
| `stock_sum` | 재고 수량 합 | 수량을 관측한 옵션만 더한다(L2/L3) |
| `sold_min` | 최소 판매량 = 재고 감소분 | §6-4. 관측 2개의 차이라 추정이 아니다 |
| `sizes[]` | `[사이즈, 품절여부, 수량]` | 사이트가 준 문자열 그대로 — 표기가 다른 사이트를 합치지 않는다 |

- 이 필드들은 산점도 축·그룹 기준·표 열로 그대로 쓰인다. 사이즈별 패널은 **자연 순서**
  (XS→S→M→L→XL→FREE→수치)로 세운다 — 가나다순 정렬 금지의 예외다.
- **`sold_min`은 없으면 만들지 않는다.** 같은 옵션을 수량까지 두 번 이상 관측해야 차이가
  생긴다. 2026-08-03 실측: 수량 관측 1,850건이 있으나 **옵션당 시점이 1개뿐**이라 아직
  산출되지 않는다. 그 사실을 화면에 적는다("한 번 더 관측해야 성립한다").
- 재입고가 섞인 구간은 **과소 집계**되므로 이름이 `sold`가 아니라 `sold_min`이다.
  화면에도 "최소 판매량 · 재입고 N회 감지 · 관측 창 from~to"로 적는다.

## §7 파생 프록시 — 수집은 풍부하게, 추출은 리포트에서 (D19)

가설 도출에는 계약 필드 밖의 신호가 필요하다 — 예: 썸네일에 모델이 있는가(스튜디오
컷인가 일반 착용 컷인가, 모델의 외형 특성), `[00 착용]`·`[00 PICK]` 같은 셀럽·인플루언서
배지가 있는가, 상품명이 영문인가 한국어인가. **이런 신호는 예시일 뿐이고, 요청마다
새로 정의될 수 있어야 한다 — 하드코딩하지 않는다.**

### 7-1 계층 분리

| 계층 | 원칙 |
|---|---|
| **수집 (재료 보존)** | 화면에 노출된 부가 표시물(배지·라벨·마크 문자열)을 `raw_extras`에 **원문 그대로** 담는다. 해석하지 않는다 — 재료가 남아 있으면 프록시는 나중에 얼마든지 뽑는다. 이미지는 URL로 이미 보존된다 |
| **정의 (제네릭)** | 프록시는 `proxy_defs`에 등록되는 **정의 카드**다: 이름 · 판정 질문 · 재료(name/image/badge/detail) · 값 공간 · 판정 방법(rule/vision/llm). 요청 맥락에서 **AI가 자동으로 제안·정의·등록**하고 정의 카드를 보고한다(D23 — 예외 없음, 사전 확인 절차 없음). 한 번 정의된 프록시는 다음 요청에서 재사용된다 |
| **추출 (리포트 단계)** | DB 관측 테이블에 차원을 늘리지 않는다. 리포트 생성기가 proxy_cache를 읽어 상품에 `px_*` 열로 주입하고, 대시보드가 **자동으로 필터·축을 만든다** |
| **판정 캐시 (재사용)** | 비싼 판정(비전·LLM)은 `proxy_cache`에 (프록시, 상품, **재료 지문**) 키로 저장한다. 지문 = 판정 재료의 식별자(이미지 프록시는 image_url, 이름 프록시는 name). **재료가 안 바뀌면 재판정하지 않는다** — 이미지가 교체되면 지문이 달라져 자동 무효화된다 |

### 7-2 정직성 규칙

- 프록시 값은 **판정이지 사실이 아니다** — 대시보드에서 프록시 축·필터에는
  "AI 판정" 표기와 미판정 건수가 붙는다. 미판정은 별도 값 `(미판정)`으로 구분한다
  (0도 unknown도 아니다).
- 판정 불확실하면 `unknown` — 찍지 않는다(핏 분류와 같은 원칙). 판정 근거(basis)를
  캐시에 함께 남긴다.
- 사람 외형에 대한 판정(모델 특성 등)은 **이미지에 보이는 인상의 분류이지 실제 국적·
  정체성 추정이 아니다** — 값 이름과 리포트 각주에 이를 명시하고, 확신 없으면 unknown.
- 룰 기반(정규식— 영문/한글 판별, 배지 매칭)은 싸므로 리포트 생성 시 즉석 계산해도
  되지만, 비전·LLM 판정은 **반드시 캐시를 먼저 조회**하고 미캐시분만 판정한다.

### 7-3 실행 주체

- 절차 정본: `skills/commerce-intel/references/proxy-extraction.md`
- 배치 판정: `proxy-extractor` 서브 에이전트 — 이미지 묶음을 받아 정의 카드의 값
  공간 안에서만 판정한다(전수조사 핏 분류의 비전 서브에이전트 분담 전례를 일반화)

## §8 유저 스토리 개방 원칙 (요구 4)

- 스토리 A/B/C(SPEC v16)는 **폐기가 아니라 부분집합**이다 — 검증된 절차로 계속 쓴다.
- 그 밖의 요구(예: "이 브랜드 어디에 입점해 있어?", "핏별 가격대가 어떻게 달라?",
  "지난달 할인 들어간 상품들 반응 어땠어?")는 고정 절차가 없어도 **공통 원칙 안에서**
  조합해 수행한다: 추정 금지 · 노출값만 · 차단 시 중단 · DB 재사용 판정 선행 ·
  결과는 DB 적재 후 리포트.
- 절차가 3회 이상 반복되면 스킬에 스토리로 승격하는 것을 사용자에게 제안한다 —
  임의로 스펙화하지 않는다.

## §9 성공 기준

1. 같은 대상을 두 번 요청하면 두 번째는 **재사용 판정이 먼저** 일어나고, 스킵 여부와
   근거(마지막 관측 시각·TTL)가 보고된다.
2. 수집 완료 후 구글 시트에서 사람이 최신 데이터를 볼 수 있다(미러 실패 시 그 사실이
   보고되고 다음 성공 때 따라잡힌다).
3. 리포트에서 사용자가 변인을 고정하고 축을 바꿔가며 **스스로 가설을 만들 수 있다** —
   요약 수치만 있는 리포트는 이 기준 미달이다.
4. 처음 보는 플랫폼 이름이 나오면: channel-scout 정찰 → generic 절차로 1회성 수집,
   또는 skill-maker로 스킬 초안 — 어느 쪽이든 **하드코딩된 입점처 목록에 없다는 이유로
   거절하지 않는다.**
5. 기존 원칙(추정 금지·미노출=null·차단 중단·완전일치 매칭)은 전부 계승된다.
6. 옵션 심화를 요청하면 **예상 요청 수·소요를 먼저 보고**하고, L3(장바구니)를 쓸 때는
   승인을 받으며, 판매수량은 **"최소 판매량 + 한계"**로 표기된다. 프로브 후 장바구니가
   비워졌음이 확인된다.
