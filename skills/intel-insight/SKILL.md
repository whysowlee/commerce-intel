# intel-insight — 분석·인사이트 단

> **이 단계는 `insight-analyst` 서브에이전트로 위임된다.**
> 수집·적재 컨텍스트가 분석 품질을 떨어뜨리는 문제를 해결하기 위해,
> 도메인 규칙이 시스템 프롬프트에 포함된 서브에이전트가 깨끗한 컨텍스트에서 실행한다.
> 정의: `.claude/agents/insight-analyst.md`. 아래 내용은 참고용 문서로 유지된다.

파이프라인 마지막이다. **DB만 보고, 수집하지 않는다.**

```
intel-collect → intel-store → intel-explore → [intel-analyze → intel-insight]
                                                방법론·검정      선별·PDF
```

분석과 인사이트는 스크립트 두 개로 갈라져 있다. 경계를 흐리면 "왜 이 분석을 했는가"와
"왜 이걸 실었는가"가 뒤섞여 어느 쪽도 추적할 수 없다.

## 0. 먼저 — 프록시를 여러 개 만든다 (D19·D23·**D43**)

**분석 요청이 프록시를 만든다.** 수집이 아니라 여기가 트리거다. **AI가 프록시를 스스로
정의한다** — 사용자에게 프록시를 고르라고 묻지 않는다(D23). **판정은 lazy다**(D65-8·D66):
rule은 분석이 캐시 miss를 즉석 판정하고, vision은 분석이 그 축을 요구할 때 협의 후
배치로 돈다 — 정의 시점에 전량 판정하지 않는다.

> **기본값은 「만든다」다** (D43, 2026-08-04 사용자 결정 — 이전 규칙을 뒤집었다).
> 옛 규칙은 "요청이 기존 축으로 답해지면 만들지 않는다"였고, 그 결과 프록시가 거의
> 안 생겼다(스커트 리포트 판정 0건). 목적은 **사용자가 묻지 않아도 뽑을 수 있는
> 인사이트를 다 뽑는 것**이다. 그러니 요청이 좁아도 축은 넓게 만든다.
>
> 사용자가 특정 항목을 지목하면(예: "썸네일 배경색에 따라 차이 있어?") 그 카드를
> **기본 묶음에 더해서** 함께 돌린다 — 그것만 하고 나머지를 버리지 않는다.

절차 정본은 `../commerce-intel/references/proxy-extraction.md`, 실행기는
`../commerce-intel/scripts/proxy_auto.py`, 출발 카드 묶음은
`../commerce-intel/references/proxy-cards-default.json`이다.

1. **기존 것부터 본다** — `intel_db.py export --table proxy_defs --format json`.
   비슷한 프록시가 있으면 그것을 쓴다(이름만 다른 중복 정의를 만들지 않는다)
2. **카드 묶음을 짠다** — 기본 묶음을 출발점으로 삼되 **이 상품군·이 요청에 맞게
   더하고 뺀다.** 기본 묶음은 정본이 아니다(D19: 하드코딩하지 않는다).
   - `rule` — 상품명·브랜드명에서 규칙으로 뽑는 축. 비용 0이라 아낄 이유가 없다
   - `vision` — **이미지에서만 나오는 축.** 배경·로고 노출·모델 수·색상 수·패턴·
     촬영 각도·연출 소품·실루엣·기장… 값 공간은 넓다. **정의 전에 분석 대상의
     실물 썸네일을 임의로 1~2장 열람해 접지한다**(D66) — 그 몰의 썸네일에 애초에
     없는 축을 정의하는 낭비를 막는다. 샘플 열람은 접지이지 판정이 아니다(샘플에
     값을 매겨 캐시에 넣지 않는다 — 1~2건으로는 그룹 비교의 n이 성립하지 않는다)
3. **정의를 등록한다** — 기본은 lazy라 지금 판정하지 않는다

   ```bash
   python3 ../commerce-intel/scripts/proxy_auto.py --db data/intel.db \
       --context "<context>" --cards <카드 JSON> --out data/px-defs.json
   python3 ../commerce-intel/scripts/intel_db.py proxy-load data/px-defs.json
   ```

   - rule 카드는 본문(rules)까지 `proxy_defs`에 저장돼 **분석이 캐시 miss를 즉석
     판정한다**(D65-8). 지금 전량 판정하고 싶으면 `--eager`(커버리지 낮거나 값
     1종뿐인 카드를 걸러 주는 필터는 eager에만 있다)
   - vision 카드는 정의만 등록된다 — 판정은 4번이 필요해질 때다
4. **vision 판정은 분석이 요구할 때 한다** (D66) — 분석을 돌리면 `meta.proxies[].unjudged`로
   미캐시 규모가 드러난다. **비용을 보고하고(전량 미캐시 + 대규모면 범위 협의)**
   `proxy_auto.py --batch-dir data/px-batches --batch-size 40`으로 배치를 뽑아
   `proxy-extractor` 서브 에이전트 여러 개에 **병렬로** 분담시킨다. **캐시된 것과 같은
   이미지를 쓰는 상품은 이미 빠져 있고, 재료가 같은 카드는 한 배치에 묶여 있다** —
   이미지 하나에 질문 여러 개를 던진다(카드마다 배치를 만들면 같은 사진을 축 수만큼
   다시 본다). 각 배치의 `ask` 목록에 있는 카드만 판정하면 된다
5. **적재** — `intel_db.py proxy-load <파일>`. 값 공간 밖 판정은 거부되고, `numeric`은
   float 강제 캐스팅된다. **`unknown`은 넣지 않는다**(TTL 안에 재시도가 막힌다)
6. **정의 카드를 사용자에게 보고한다** — 선택지로 묻는 게 아니라, 무엇을 어떤 값 공간으로
   판정했는지 알려 사후에 바로잡을 수 있게 한다. **비전 판정을 미뤘거나 범위를 좁혔으면
   그 사실도 적는다**(리포트에서 그 축은 미판정 결측으로 보인다)

이렇게 등록된 프록시는 **다음 단계에서 자동으로 검정 축이 된다**(D39) — `cat_axes`/`num_axes`가
`meta.proxies`를 읽어 그룹 비교·상관에 넣는다. 별도 설정이 필요 없다.

**다중비교는 어떻게 되나**: 축이 늘면 우연한 패턴도 는다. 그건 **BH 보정과 5관문이
막는다** — 축을 적게 만들어서 막는 방식은 "안 본 것"을 "없는 것"으로 만들 뿐이다.
다만 비전 판정은 비싸다. 카드를 늘릴 때는 그 질문이 실제로 결정을 바꾸는지 보고 늘린다.

## 0-b. 분석 맥락을 먼저 읽는다 (D47·D48)

`../commerce-intel/references/analysis-context.md` — **무엇을 Y로 놓고 무엇을 믿지
않을 것인가**. 플랫폼 무관한 방법론이다.

특히 이 셋은 검정을 짜기 전에 봐야 한다:

- **공급자가 정한 값(가격·할인)은 Y가 아니다** — 상관 방향이 거꾸로 잡힌다
- **절대값이 아니라 비율**, 단 **구간 표기로는 비율을 만들지 않는다**(하한이라 부풀려진다)
- **랭킹 상위 = 상품력이 아니다** — 노출↔판매 되먹임이 있다

## 1. 방법론을 먼저 정한다 (2단계)

```bash
# ① 계획만 세운다 — 0.6초. 이걸 읽고 예외를 판단한다
python3 ../commerce-intel/scripts/analyze.py --db data/intel.db \
    --context "brand:로우클래식" --plan-only --out data/plan.json
```

계획서에 기법 6종의 **채택·기각이 사유와 함께** 나온다. 읽고 **규칙은 통과했지만 이
데이터엔 부적절한 것**을 골라낸다. 대표적인 것:

- 카테고리 값에 상위 분류와 하위 분류가 섞여 있다(`하의` 대 `미니`) → 대등한 비교가 아니다
- 브랜드 값이 같은 브랜드의 표기 차이다(`로우클래식` 대 `LOW CLASSIC`) → 사실상 플랫폼 비교다
- 관측 창이 상품마다 크게 다르다 → 증분을 나란히 놓을 수 없다

```json
{"exclude": [{"method": "group_compare",
              "reason": "카테고리 값에 상위·하위가 섞여 대등한 비교가 아니다"}],
 "warn":    [{"method": "did", "note": "관측 간격 편차가 커 구간 길이가 고르지 않다"}]}
```

```bash
# ② 예외를 반영해 리포트까지 만든다
python3 ../commerce-intel/scripts/insight.py --db data/intel.db \
    --context "brand:로우클래식" --target "로우클래식" \
    --ai-notes data/ai-notes.json --out output/
```

예외가 없으면 `--ai-notes` 없이 바로 실행해도 된다. **다만 계획서는 반드시 한 번
읽는다** — 기각 사유에 "축적이 얕다" 같은 게 있으면 사용자에게 알려야 할 사실이다.

### ③ 액션 플랜은 네가 쓴다 — 2회 실행이 정석이다 (D64)

**엔진의 템플릿 액션은 폴백이지 최종본이 아니다.** {값} 치환으로는 "옵션 통합 등록으로
전환해 하트·후기가 한 곳에 쌓이게 유도" 같은 문장이 나오지 않는다 — 그건 발견의 기전을
읽고 추론해야 나온다(2026-08-04 사용자가 실물 예시로 확정). 절차:

1. **1차 실행**으로 강한 주장·차이 없음 목록을 얻는다 (분석은 고정 시드라 재현된다)
2. 발견마다 액션을 **직접 쓴다** — `{주장 문장 그대로: [줄, …]}` JSON.
   첫 줄은 발견의 평문 부연, 이후 줄은 `**[마케팅]**`·`**[디자인]**`·`**[판매전략]**`
   배지를 앞에 붙인 구체 액션. **모든 줄에 그 발견의 실제 값·기전이 들어가야 하고**,
   추측은 허용되며("검색에 더 잘 걸리기 때문일 수 있으므로"), 청중당 1개 이상을 목표로 한다
3. **2차 실행**에 `--ai-actions actions.json`을 넘겨 최종 PDF를 굽는다

```bash
python3 ../commerce-intel/scripts/insight.py --db data/intel.db \
    --context "..." --target "..." --ai-actions data/actions.json --out output/
```

시간이 없어 1회만 돌린다면 그 사실을 사용자에게 밝힌다 — 템플릿 액션은 사용자가
"당연한 말들"이라고 기각한 수준이다.

## 2. 기법 6종 (규칙표)

| 기법 | 답하는 질문 |
|---|---|
| 그룹 비교 | 범주(플랫폼·카테고리·핏·브랜드·품절)에 따라 지표가 다른가 |
| 순위 상관 | 두 수치가 같이 움직이는가 (+ 구간별 추세) |
| **이중차분** | 가격을 내린 것이 반응을 늘렸는가 — 시즌 같은 공통 요인을 걷어내고 |
| **용량-반응** | 할인을 **얼마나** 주면 반응이 얼마나 오는가 |
| **쌍체 비교** | 같은 상품이 플랫폼마다 가격·할인이 다른가 |
| **소진 속도** | 무엇이 빨리 팔리는가 — 리오더 판단의 본체 |

새 기법이 필요하면 `stat_playbook.py`에 추가하고 **왜 그 기법인지 적는다.** 리포트
코드에 검정을 직접 박아 넣지 않는다.

## 3. 5관문 — 강한 주장의 자격

① 효과 크기 ② 표본 ③ 다중비교 보정(BH) ④ 세그먼트 역전 없음 ⑤ 홀드아웃 재현

- **5개가 안 나오면 억지로 채우지 않는다.** 3개면 3개로 내고 그 사실을 말한다.
  빈자리를 약한 것으로 승격시키면 이 구분 자체가 무의미해진다
- **약한 단서에는 어느 관문을 왜 못 넘었는지와 재확인 방법**이 반드시 붙는다.
  이유 없는 단서는 단서가 아니라 잡음이다. 재확인 방법은 **그 카드의 값으로,
  종료 조건까지** 쓴다(D62) — "다음 관측으로 재확인" 같은 일반론은 금지
- 홀드아웃에서 **방향이 반대로** 재현되면 기각으로 따로 남긴다 — 같은 막다른 길을
  다시 파지 않기 위해서다
- 표본이 작아 홀드아웃을 나눌 수 없으면 "확인 불가"이지 실패가 아니다. 자격은 주되
  **선별에서 뒤로 민다** — 재현이 확인된 것이 먼저 실린다

## 4. 산출물

| 파일 | 무엇 |
|---|---|
| `output/insight-<대상>-<ts>.pdf` | 강한 주장 5 + 약한 단서 20 + 기각 목록. 3~6쪽 |
| `output/detail-<대상>-<ts>.pdf` | **분석 계획서** + EDA 프로파일 + 가설별 판정 근거 |
| `insights` 테이블 | 시트 미러가 팀에 전달한다 — PDF는 만든 사람 손에만 있다 |

**HTML은 만들지 않는다**(D27). 인사이트의 각 항목이 상세의 쪽 번호를 가리킨다.

## 4-b. 리포트를 내보내기 전에 수치를 재검증한다 (D52)

여기가 **산출(§4) 다음**인 이유: 입력인 `output/claims-<대상>-<날짜>.json`은
리포트에 실을 수치가 정해진 뒤에야 만들 수 있다. 전에는 §1 앞(0-c)에 있어서
순서대로 읽으면 claims 파일이 없는 시점에 돌리라는 말이 됐다(PR #12 리뷰).

**5관문은 "이 발견이 우연인가"를 본다. 수치가 맞는지는 안 본다.** 둘은 다른 질문이다
— 계산이 틀려도 5관문은 통과한다(틀린 값으로 일관되게 계산하면 그렇다).

`../intel-fashion-md/scripts/sanity_check.py`가 **DB에서 다시 계산해 대조**한다.
AI·난수·네트워크를 쓰지 않아서 같은 DB면 언제 돌려도 같은 답이 나온다 — clean
세션 재현 검증도 이 스크립트 재실행이다.

```bash
python3 ../intel-fashion-md/scripts/sanity_check.py \
    --db data/intel.db --claims output/claims-<대상>-<날짜>.json
```

    exit 0  전 claim 일치 → 리포트 내보내도 된다
    exit 1  일치하되 경고(n<30 등) → 경고를 리포트에 병기한다
    exit 2  하나라도 불일치·해석 불가 → **내보내지 마라.** 원인부터 본다

claims 형식은 `../intel-fashion-md/references/claims-example.json`.
**리포트에 싣는 수치만 claim으로 만든다** — 전부 만들면 아무도 안 쓴다.

## 5. 어조 — 관측 진술이지 실행 지시가 아니다

MD가 "정성적·참고용으로 활용할 계획"이라고 못박았다(2026-08-03 인터뷰).

- ○ "할인 20% 구간에서 하트 증분이 3배였다 (n=42, 7/1~7/28)"
- × "20% 할인하라"

강한 주장도 마찬가지다. 단정형은 신뢰를 잃는 가장 빠른 길이다.

## 6. 청중을 나눠 낸다

가설마다 **판매전략 / 디자인 / 마케팅** 중 하나가 붙는다. 한 청중이 요약을 독점하지
못하게 상한을 건다 — MD가 원한 건 역할별로 나뉘어 나오는 것이지 한 종류 5개가 아니다.

## 7. 데이터가 부족하면

DB에 관측이 없거나 시점이 하나뿐이면 **분석을 만들어내지 않는다.** 무엇이 없어서 못
하는지 말하고, 필요한 수집을 제안한다(`intel-collect`). 상세 스펙은
`../commerce-intel/references/insight-spec.md`.
