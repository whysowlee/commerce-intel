# commerce-intel

커머스 사이트에서 **화면에 노출된 값만** 모아 정본 DB에 축적하고, 시트로 미러하고,
EDA를 돌린 뒤 **검증된 가설을 PDF로** 낸다. 판단 기준은 `docs/SPEC-INTEL.md`다.

## 이 스킬은 진입점이고, 일은 단계 스킬이 한다 (D29·D33)

파이프라인은 4단이고 각 단은 **앞 단의 산출물만 알고 뒷 단을 모른다.**

| 단 | 스킬 | 산출 | 아는 것 / 모르는 것 |
|---|---|---|---|
| 수집 | `intel-collect` | 계약 JSON | 플랫폼 어댑터를 안다 · **DB를 모른다** |
| 적재·공유 | `intel-store` | `intel.db` · 시트 | 스키마·미러·재사용을 안다 · **수집 방법을 모른다** |
| EDA | `intel-explore` | `signals[]` | 데이터 상태를 본다 · **가설을 만들지 않는다** |
| 분석·인사이트 | `intel-insight` | PDF 2층 · `insights` | 방법론·검정·선별 · **수집을 모른다** |

**사용자 요청은 언제나 이 스킬로 들어온다.** 단계 스킬은 발화 예시를 갖지 않는다 —
여러 스킬이 같은 말에 반응하면 재사용 판정·팀 커버리지·DB 적재를 하는 오케스트레이터가
조용히 우회된다. 요청을 읽고 **어느 단부터 필요한지 판단해 그 스킬을 읽고 따른다.**

    "로우클래식 다 모아줘"           → collect → store            (여기서 끝)
    "핏별 가격 비교해줘"             → explore → insight          (DB에 있으면 수집 생략)
    "로우클래식 인사이트 뽑아줘"      → 재사용 판정 → (필요하면 collect·store) → explore → insight

한 단만 원한다고 명시하면(예: "수집만 해줘") 거기서 멈춘다. 아래 공통 워크플로우는
각 단계 스킬의 요약이다 — **세부는 해당 스킬을 읽는다.**

## 원칙 (전부 계승)

1. **추정하지 않는다.** 미노출 값은 `null`이고 리포트에 "미노출"로 찍힌다.
   리뷰 수로 판매량을 역산하는 식의 추정은 사용자가 요청해도 하지 않는다.
2. **수집과 처리를 나눈다.** 수집 결과는 §데이터 계약 JSON에 담고, 검증·적재·집계·리포트는
   `scripts/`가 한다. 수집 방식이 바뀌어도 하류는 그대로다.
3. **막히면 멈추고 보고한다.** 차단(403/429/캡차)을 우회하지 않는다.
4. **수집 전에 DB와 시트에 먼저 묻는다.** 이미 있는 것을, 남이 이미 한 것을 다시
   조사하지 않는다(§재사용 판정).

## 아키텍처 — 이 스킬이 지휘하는 것

**수집과 분석은 분리된 요청이다**: ① 수집 요청 → ② 수집·DB 적재·시트 미러(여기서
끝나도 된다) → ③ 분석 요청 → ④ EDA → ⑤ 인사이트 PDF. 한 요청에 둘 다 있으면 이어서 한다.

```
[수집 요청] → 재사용 판정(내 DB + 팀 시트) → 수집(플랫폼 스킬 위임) → 검증 → DB 적재 → 시트 미러
[분석 요청] → DB 조회(부족하면 수집 협의) → EDA(signals) → 가설 생성·검정 → PDF 2층
```

- **수집 방법은 이 스킬이 모른다.** 사이트별 방법은 플랫폼 스킬이 갖는다:
  무신사 → `platform-musinsa` · 무신사 글로벌 → `platform-musinsa-global` ·
  29CM → `platform-29cm` · W컨셉 → `platform-wconcept` · EQL → `platform-eql` ·
  SSF샵 → `platform-ssf` · 자사몰 → `platform-ownmall` ·
  처음 보는 플랫폼 → `platform-generic`. 플랫폼 스킬의 산출물은 언제나
  §데이터 계약 JSON이고, 그 뒤는 전부 이 스킬의 일이다.
  ※ W컨셉·EQL·SSF·무신사 글로벌은 **건별 수집만**(D30)이고 일부는 `draft`(브랜드 모드 등
  미검증) — 어댑터를 먼저 읽는다.
- **입점처 리서치**는 `channel-scout` 서브 에이전트를 스폰한다(있으면). **스폰 전에
  `platforms` 테이블에서 기존 정찰을 꺼내 프롬프트에 넘긴다** — 90일(D7 준용) 이내
  정찰이 있는 플랫폼은 재정찰하지 않고, 이번에 새로 볼 것은 그 브랜드의 입점 여부뿐이다:
  ```bash
  python3 scripts/intel_db.py export --table platforms --format json
  ```
  결과 보고서는 `platforms`에 적재하고(`updated_at`이 정찰 신선도 기준),
  어떤 플랫폼 정찰을 재사용했는지 사용자 보고에 포함한다.
  반복 수집할 새 플랫폼이면 `platform-skill-maker`로 스킬 초안을 만든다.
- **에이전트 산출물은 검수 후 수용한다** (evaluator 패턴): 산출물을 받으면 기준표로
  항목별 PASS/FAIL을 매긴다 — channel-scout 보고서라면 ① 모든 입점처에 확인 근거·
  신뢰도가 붙었는가 ② 미검증이 「미검증」으로 구분됐는가 ③ 불일치 섹션이 있는가.
  FAIL 항목은 그 항목만 짚어 **1회 재요청**하고, 그래도 미달이면 미달 사실과 함께
  사용자에게 그대로 전달한다(억지로 고쳐 쓰지 않는다). 검수 결과는 조용히 버리지
  말고 무엇을 왜 반려했는지 남긴다.
- 유저 스토리는 고정이 아니다 — 검증된 절차(라인시트·전수조사·랭킹 모니터링,
  `references/story-catalog.md`)는 그대로 쓰고, 그 밖의 요구는 위 원칙 안에서 조합해
  수행한다. 같은 조합이 3회 이상 반복되면 스토리 승격을 사용자에게 제안한다.

## 시작하기 전에 확정할 것

요청에서 뽑아낸다. **추론하지 말고, 빠진 게 있으면 한 번 물어본다.**

| 항목 | 설명 |
|---|---|
| 무엇을 | 브랜드명 / 카테고리명 / "입점처" 자체 |
| 사이트 | 명시됐으면 그것만 수집한다(친절하게 더 붙이지 않는다). **플랫폼 없이 브랜드만 오면**(예: "로우클래식 전체 라인시트") `channel-scout` **브랜드 모드**로 입점처를 발견하고, **확인된 입점처(신뢰도 높음) 전부**가 수집 대상이다 — 시작 전에 판매처 목록·플랫폼별 규모·예상 소요를 한 번 보고하고 진행하며, 상한 초과 플랫폼만 좁힘 협의를 한다. **플랫폼 없이 카테고리만 오면** `channel-scout` **카테고리 모드**: 누적 카탈로그 + 특화 채널 탐색 → 규모와 함께 제시 → 사용자가 고른다(상품군은 후보가 사실상 전 플랫폼이라 선택이 필요하고, 브랜드는 입점처가 유한한 사실이라 전부가 기본이다). 범용 카탈로그 전면 재검은 첫 실행·90일 주기에만 |
| 기간 | 변화 분석에서만, 그리고 필수. 절대 날짜로 바꿔 기록한다(`date +%Y-%m-%d`로 확인) |
| 재수집 여부 | "새로 받아"·"다시 조사해"가 있으면 재사용 판정을 건너뛴다 |

## 재사용 판정 — 수집 전에 반드시

정책은 SPEC-INTEL §2-2다: **정적 속성 TTL 90일 · 시변 값 스킵 창 = 사이트 갱신 주기**
(플랫폼 스킬 frontmatter의 `refresh-cycle`, 미상이면 24시간).

각자 로컬 DB를 갖는 배포(D31)라, 내 DB에 없다고 아무도 안 한 것은 아니다.
**`--team`을 항상 붙인다** — 시트 `runs` 탭을 봐서 팀원이 이미 수집했는지 확인한다(D32).
랭킹뿐 아니라 브랜드 라인시트·전수조사도 똑같이 이 관문을 지난다.

```bash
# 1) 시변 값 + 팀 커버리지: 신선한 관측이 있으면 수집 자체를 생략한다 (exit 0 = 스킵 가능)
python3 scripts/intel_db.py check --site musinsa --context "ranking:바지" \
        --cycle-minutes 30 --team

# 2) 수집했다면: 비싼 정적 판단(핏 분류 등)은 DB에서 재사용한다
python3 scripts/intel_db.py reuse-attrs data/raw/<수집>.json
```

- 스킵했으면 **스킵 사실과 마지막 관측 시각을 사용자에게 보고한다.** 옛 데이터를
  새것처럼 조용히 내지 않는다. 출력의 `source`가 `local`인지 `team`인지도 함께 말한다 —
  "내가 어제 받아뒀다"와 "팀원이 20분 전에 받았다"는 사용자가 할 일이 다르다
  (후자는 `sync_sheets.py`로 시트를 보거나 팀원 DB를 `merge` 받는다).
- **팀 조회 실패는 수집을 막지 않는다.** `team.consulted: false`면 로컬 판정만으로
  진행하되, 그 사실을 보고에 포함한다 — 중복일 수도 있다는 뜻이기 때문이다.
- **시트는 완료분만 안다.** 팀원이 *지금* 같은 걸 수집 중이면 잡히지 않는다(D32 한계 ⓐ).
  긴 수집을 시작하기 전이라면 사용자에게 한마디 해두는 편이 낫다.
- `context`는 `ranking:바지` · `brand:인사일런스` · `market:데님팬츠(남성)` 형식이다.
  랭킹에서 온 실시간 지표를 다른 문맥에 섞지 않는다.
- TTL이 만료된 정적 속성은 `stale-static`으로 뽑아 다음 수집에서 재확인한다.

## 공통 워크플로우

### 1단계 — 플랫폼 스킬을 따라 수집한다

작업할 사이트의 플랫폼 스킬을 읽고 그 절차대로 **데이터 계약 JSON**을 만든다.
플랫폼 스킬이 없는 사이트는 `platform-generic`으로 정찰부터 한다.
수집하면서 **페이지 단위로** `data/raw/`에 저장한다(중단 시 이어서).

### 2단계 — 검증한다

```bash
python3 scripts/validate_data.py data/raw/<파일>.json --json data/validation.json
```

- `0` 진행 · `1` 진행하되 경고를 사용자에게 전달 · `2` **적재·리포트 금지, 원인부터.**
  결측 30% 초과는 사이트 구조 변경 신호다 — 플랫폼 스킬의 어댑터 매핑을 확인한다.

### 3단계 — DB에 적재한다

```bash
python3 scripts/intel_db.py load data/raw/<파일>.json
```

관측은 append only다 — 같은 (site, product_id, observed_at, context)는 중복으로 스킵된다.
검증이 `2`인 파일은 적재하지 않는다.

### 4단계 — 구글 시트로 미러한다

```bash
python3 scripts/sync_sheets.py          # data/sheets_config.json + 서비스 계정 키 사용
```

- 방향은 **로컬 → 시트 단방향**이다. 시트는 보는 창구이고 정본은 `data/intel.db`다.
- **인증이 없거나 실패해도 수집·적재는 유효하다.** 미러만 밀린 것이고 다음 성공 때
  `sync_state`부터 따라잡는다. 실패 사실을 사용자에게 보고한다.
- 최초 설정(서비스 계정 발급)은 `docs/SHEETS-SETUP.md` — 사용자가 1회 수행한다.

### 5단계 — EDA를 돌린다

분석·인사이트 **전에** 데이터가 무엇인지부터 본다. 도메인이 고정이라 기법도 고정이다(D29).

```bash
python3 scripts/eda.py --db data/intel.db --context "<context>" --out data/eda.json
```

7종을 본다: 그레인 · 결측 지도 · 분포/이상치 · 축 카디널리티 · **상관 + 세그먼트 재확인** ·
시계열 커버리지 · 생존편향. 산출은 사람이 읽는 리포트가 **아니라** 인사이트 엔진이 먹는
`signals[]`다 — "어느 축에 신호가 있는지"를 판정해 가설 생성 범위를 좁힌다.

SLA는 10분인데 실측은 34,489건 전체가 6초다. 이 단계를 건너뛰지 마라 —
**결측·표본·생존편향을 모르고 낸 인사이트는 틀린 자신감을 준다.**

### 6단계 — 인사이트를 만든다 (PDF 2층)

**먼저 이 요청에 프록시가 필요한지 본다**(D19·D23). 기존 축(가격·하트·핏)으로 답할 수
없는 질문이면 **AI가 프록시를 스스로 정의·판정해 등록한다** — 사용자에게 묻지 않고,
등록한 정의 카드를 보고한다. 절차는 `references/proxy-extraction.md`, 요약은
`../intel-insight/SKILL.md` §0. 등록된 프록시는 검정 축에 자동으로 들어간다(D39).

**산출물은 PDF뿐이다. HTML 리포트는 폐기됐다**(D27 — 읽는 자리가 모바일이고 보고·공유에
쓰인다). 조건을 바꿔가며 확인하는 일은 사람 손이 아니라 **엔진이 미리 돌린다.**

```bash
python3 scripts/insight.py --db data/intel.db --context "<context>" \
    --target "<대상 이름>" --out output/
```

두 파일이 나온다.

| 파일 | 무엇 | 누가 |
|---|---|---|
| `insight-<대상>-<ts>.pdf` | **강한 주장 5 + 약한 단서 20.** 짧다. 매일 본다 | 전원 |
| `detail-<대상>-<ts>.pdf` | 가설별 판정 근거·EDA 프로파일·구간별 추이 | 근거를 볼 사람 |

인사이트의 각 항목이 상세의 쪽 번호를 가리킨다.

**강한 주장은 5관문을 전부 통과한 것만이다**(D28): ①효과 크기 ②표본 ③다중비교 보정(BH)
④세그먼트 역전 없음 ⑤홀드아웃 재현. **5개가 안 나오면 억지로 채우지 않는다** — 빈자리를
약한 것으로 승격시키면 구분 자체가 무의미해진다. 3개면 3개로 내고 그 사실을 말한다.

약한 단서에는 **어느 관문을 왜 못 넘었는지와 재확인 방법**이 반드시 붙는다. 방향이 반대로
재현되면 기각으로 따로 남긴다 — 같은 막다른 길을 다시 파지 않기 위해서다.

각 항목에 **청중**(판매전략/디자인/마케팅)이 붙는다. 한 청중이 요약을 독점하지 못하게
상한을 건다 — MD가 원한 건 역할별로 나뉘어 나오는 것이지 한 종류 5개가 아니다.

**어조는 관측 진술이다.** "20% 할인하라"가 아니라 "20% 구간에서 증분이 3배였다".
MD가 "참고용·정성적"이라고 못박았다(2026-08-03 인터뷰).

#### 통계는 플레이북에서 꺼내 쓴다

`scripts/stat_playbook.py`에 데이터 형태 → 기법 매핑이 고정돼 있다. 요청마다 설계를 새로
짜지 않는다(예산 30~60분을 못 지킨다). 순열검정을 쓰고 scipy에 의존하지 않는다 —
하트·판매량은 왜도가 5를 넘는 일이 흔해 정규분포 전제 검정이 애초에 안 맞는다.

**새 통계 기법이 필요하면 플레이북에 추가하고 왜 그 기법인지 적는다.** 리포트 코드에
직접 검정을 박아 넣지 않는다.

## 지켜야 할 규칙

- **요청 속도** — 페이지 사이 0.5~1.5초. 병렬로 몰아치지 않는다.
- **규모 상한 없음** (D22) — 규모와 무관하게 진행하되 **예상 소요를 먼저 보고**한다.
  0건이면 중단 보고, 무한 루프 방지(3연속 무증가)는 유지. 랭킹 top 100은 상한이 아니라
  diff 연속성 규격이다. **임의 샘플링 금지**(표본은 명시 요청 시에만 — D21).
- **재시도** — 2회(간격 증가), 3연속 실패면 건너뛰고 `meta.notes`에 기록.
- **차단** — 403/429/캡차는 즉시 중단. `meta.incomplete: true` + 부분 리포트.
- **로그인** — 비로그인으로 보이는 것만.
- **상태 변경** (D18) — 정보 획득에 필요한 상태 변경은 **실제 결제 실행만 빼고
  허용**된다(결제 페이지 진입은 허용, 주문 완료·결제수단 제출은 절대 금지).
  순서는 비용 순서다: L1 무료 → L2 읽기 전용 → L3 상태 변경(`references/variant-collection.md`).
  상태를 바꿨으면 **가역 조치(장바구니 비우기 등)를 하고 무엇을 했는지 보고한다** —
  승인은 불요하지만 조용히 하지 않는다. 비로그인 원칙은 유지 — 로그인이 필요하면 묻는다.
- **하지 않는 것** — 판매량 추정(리뷰 수 역산 등), 유사도·가격 기반 상품 매칭
  (완전일치만 — 근거는 `docs/EVIDENCE.md` §5), 이미지 재배포.

## 데이터 계약 (요약)

플랫폼 스킬의 산출 JSON은 `meta`(site·story·target·collected_at·item_count·source_total·
incomplete·notes[])와 `items[]`로 구성된다. 필드 정의·필수 기준·축약/구간 표기 규칙·
쿠폰적용가 정의는 `references/db-contract.md`가 정본이다. 핵심만:

- 필수: `product_id` `name` `url` `image_url` `brand` `category` `price_original`
  `price_sale` `discount_rate` `sold_out` (결측 5% 경고 / 30% 실패)
- 노출 시만: `review_count` `rating` `view_count` `purchase_count` `like_count`
  `viewers_now` `buyers_now` — **안 보이면 `null`**
- `price_sale`은 **전 회원 공통 쿠폰적용가**, `rating`은 5점 만점 통일
- 축약(`1.2천`)은 정수 파싱 허용, 구간(`300회 이상`)은 `null` + `*_display`만
- `source_total`에 수집 건수를 넣지 않는다(순환 검증 금지) — 독립 총계가 없으면 `null`
