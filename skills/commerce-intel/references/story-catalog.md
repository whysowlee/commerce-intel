# 스토리 카탈로그 — 검증된 절차

라인시트·전수조사·랭킹 모니터링은 실측으로 검증된 절차다. 그 밖의 요구는 이 절차들을
부품 삼아 SKILL.md 원칙 안에서 조합한다. 사이트별 실행 방법은 각 플랫폼 스킬에 있고,
여기는 **플랫폼 무관 절차와 판정 기준**만 둔다. 수치의 근거는 전부 `docs/EVIDENCE.md`.

## A. 브랜드 라인시트 — 멀티 플랫폼 비교

입력: 브랜드 + 플랫폼 1개 이상(요청에 명시된 것만 — 친절하게 더 붙이지 않는다).

1. 플랫폼마다 브랜드 **전 상품**을 끝까지 모은다. 상한 3,000은 플랫폼별 적용.
   - **품절 포함이 기본이다. 목록 기본 필터가 사이트마다 다르므로 반드시 맞춘다** —
     안 맞추면 단독 입점 분석이 통째로 틀어진다(실측: 83건 → 0건). 각 플랫폼 스킬의
     품절 절차를 따른다
   - 완전성은 **독립 총계 대조**로만 판정한다. 총계가 없는 사이트는 그 스킬이 정한
     대체 근거(카테고리 소진 등)를 쓰고 리포트에 명시한다
   - 한 사이트가 실패해도 나머지는 끝낸다 — 부분 실패를 전체 실패로 만들지 않는다
2. 사이트별 JSON을 따로 만든다(`story: brand-linesheet`). 상품명은 원문 그대로.
3. 리포트 생성기에 JSON을 모두 넘긴다 — 합집합·매칭·통합축·비교 3블록은 코드가 만든다.

**동일 상품 매칭은 완전일치만.** 정규화(소문자화 · `[...]`·`(...)` 제거 · 영숫자+한글만)
후 완전히 같을 때만 같은 상품이다. 유사도·가격 보조 매칭 금지 — 정가까지 같은 다른
상품이 실측됐다(EVIDENCE §5). 미매칭은 실패가 아니라 **단독 입점 사실**이다.

**품목 통합축은 매칭 상품에서 자동 추출** — 손 매핑 표 금지. 사이트 카테고리 이름은
거의 안 겹친다(실측 8/43·37종).

반응 지표를 노출하지 않는 플랫폼(자사몰 등)은 반응 비교 블록에서 **빼고 각주로 밝힌다** —
빈 열이나 0으로 그리지 않는다(미수집 ≠ 0).

## B. 카테고리 시장 전수조사

0. **플랫폼이 지정 안 됐으면** — 임의로 고르지 않는다. `channel-scout` 카테고리 모드로
   누적 카탈로그(platforms)의 플랫폼별 해당 상품군 규모를 확인해 제시하고 사용자가
   고른다. 선택된 플랫폼이 전용 스킬 없는 곳이면 `platform-generic`으로 수집한다.
1. **카테고리를 특정한다.** 코드 카탈로그(`data/.tools/ranking_targets.json`, 1,546개)에서
   이름으로 찾는다. 사이트에 그 이름이 없으면 **검색 키워드 ∩ 상위 카테고리**로 잡되
   가드 3종을 건다: G1 교집합 0건 → 중단 보고 · G2 카테고리의 90% 이상 → 키워드 무의미,
   멈추고 질문 · G3 상품명 실제 매칭률을 계산해 notes와 리포트에 명시.
2. **규모 확인 → 범위 협의.** 첫 페이지에서 총계를 읽고: 0건 중단 / 5,000 이하 진행
   (한 줄 보고) / 초과 시 **좁힐 축의 실제 개수를 조회해** 제시하고 사용자가 고른다.
   **임의 샘플링 금지** — 묻지 않고 상위 N개만 모으는 것이 최악의 실패다.
   최종 범위를 `meta.target`에 정직하게 쓴다("데님팬츠(남성)" 형식).
3. **목록을 끝까지 수집한다.** 상세는 목록에 없는 값이 꼭 필요할 때만 연다.
4. **속성 분류** — 근거 순서: ① 이름·텍스트 ② **DB 재사용**(`intel_db.py reuse-attrs` —
   TTL 90일 이내 판정 재사용) ③ 색상 변형 그룹 전파(`group_variants.py`, 완전일치 그룹만)
   ④ 대표 이미지 판단 ⑤ `unknown`. **찍지 않는다.**
   - 핏 값 7개: `부츠컷` `와이드` `스트레이트` `슬림` `테이퍼드` `쇼츠` `unknown`.
     쇼츠 이름 신호와 함정(하프 밴딩, `shorts_` 밑줄)은 EVIDENCE §5
   - 기본 분류 속성은 핏 하나. 추가 속성은 명시 요청 시에만(예상 소요 먼저 보고)
5. `story: market-scan`. 성공 기준: 합의 범위 완주 · **분류율 80% 이상** ·
   결측이 실제 미노출과 일치(추정 0건). 미달 시 이미지로 채울지 사용자가 정한다.

## C. 랭킹 모니터링

동작 2개를 먼저 가른다: **C-1 시작**(스냅샷 1개 + 주기 등록) / **C-2 변화 조회**(기간 필수).

- **과거는 소급할 수 없다**(EVIDENCE §8 — API·아카이브 전 경로 검증됨). 재료는 축적분뿐.
  기간 내 스냅샷이 없으면 스냅샷 1개를 찍고 C-1을 제안한다.
- C-1: 첫 스냅샷 정상 확인 → 스케줄 등록(주기 = **사이트 원본 갱신 주기**, 플랫폼 스킬
  frontmatter의 `refresh-cycle`) → 등록 내용 보고(사이트/카테고리/주기/절대 경로).
  스냅샷 후 `intel_db.py load`까지 잡이 수행하게 등록한다.
- C-2: `diff_snapshots.py`로 기간 diff → `build_report.py`. 스냅샷 1개 이하면 빈 diff를
  만들지 않는다.
- 한 스냅샷은 **한 시점**이다 — 끊겼으면 이어 붙이지 말고 다시 찍는다.
- 범위가 다른 스냅샷끼리 비교하지 않는다 — 폴백으로 범위를 낮췄으면 `meta.target`을
  낮춘 이름으로 저장한다.
- top 100 고정(기존 축적과의 diff 연속성). 실시간 지표(`viewers_now`/`buyers_now`)는
  랭킹 화면에만 있다 — 다른 스토리에 끌어와 채우지 않는다.
- 판정 기준(코드가 계산): 급등락 강조 = 랭킹 길이의 10%(최소 3계단) · 추이 요약 =
  48시점 초과 시 균등 구간 대표 스냅샷(평균 금지) · **가격·할인 변화 감지 = 상품별
  마지막 관측 대비**(관측 창 `from_at`~`to_at` 기록, 상한 없음).

## D. 개방형 요구 (스토리 밖)

"핏별 가격대 차이", "지난달 할인 상품 반응", "이 브랜드 어디 입점?" 같은 요구는:

1. **DB에 먼저 묻는다** — 이미 축적된 관측으로 답할 수 있으면 수집 없이 분석 리포트로 간다.
2. 부족하면 필요한 만큼만 수집한다(위 절차의 부품을 재사용 — 범위 협의·완전성 검증 포함).
3. 결과는 반드시 DB에 적재하고 리포트로 낸다 — 일회성 답변으로 흘리지 않는다.
4. 입점처 리서치는 `channel-scout`를 스폰하고 결과를 `platforms`에 적재한다.
5. 같은 조합이 3회 반복되면 스토리 승격을 제안한다 — 임의로 스펙화하지 않는다.

**브랜드 간 경쟁 비교 요청**("우리 브랜드랑 A브랜드 비교해줘")의 산출 구조는 경쟁 브리프
형식을 따른다(knowledge-work-plugins 차용): ① 요약(기회·위협 각 1개 이상) ② 브랜드별
프로필(카탈로그 폭·가격 포지션·반응 지표) ③ 비교 매트릭스 ④ 품목 갭(한쪽에만 있는
품목) ⑤ 관찰된 사실 기반 기회 요소. **전부 수집된 노출값으로만 구성한다** — 전략 추론·
내부 사정 추측은 쓰지 않는다.
