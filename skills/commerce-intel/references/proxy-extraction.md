# 파생 프록시 — 정의·판정 캐시·대시보드 주입 (SPEC-INTEL §7)

계약 필드 밖의 신호를 가설 재료로 쓴다. 예: 썸네일에 모델이 있는가(스튜디오 컷/일반
착용 컷, 모델 외형 특성), `[00 착용]`·`[00 PICK]` 배지, 상품명 영문/한국어.
**예시는 예시일 뿐이다 — 프록시는 요청마다 새로 정의될 수 있고, 하드코딩하지 않는다.**

핵심 설계(D19): **수집은 재료 보존까지만 · 추출은 리포트 단계에서 · 비싼 판정은
캐시로 재사용.** DB 관측 테이블에 차원을 늘리지 않는다.

## 1. 재료 보존 (수집 단계의 유일한 책임)

- 목록 카드·상세에 노출되는 부가 표시물(배지·라벨·마크 문자열)을 상품 레코드의
  **`raw_extras`**(선택 필드, JSON)에 **원문 그대로** 담는다. 해석·분류하지 않는다.
  예: `{"badges": ["[아이유 착용]", "무신사 단독"], "labels": ["쿠폰"]}`
- 이미지는 `image_url`로 이미 보존된다. 프록시 판정용 다운로드는 `data/images/`에
  임시로만(기존 핏 분류와 동일 — 재배포 금지).
- 재료가 남아 있으면 프록시는 나중에 얼마든지 새로 뽑는다 — **수집을 다시 하지 않는다.**

## 2. 프록시 정의 — 요청에서 태어나고, 등록되면 재사용된다

사용자 요청("모델 착용컷인 상품만 보고 싶어")에서 프록시를 **정의 카드**로 만든다:

| 필드 | 예 |
|---|---|
| `proxy_name` | `thumb_model` (kebab/snake, 안정적 이름 — 캐시 키가 된다) |
| `question` | "썸네일에 사람 모델이 있는가, 있다면 어떤 컷인가" |
| `material` | `image` (name/image/badge/detail 중) |
| `value_space` | `["모델 없음(제품만)", "스튜디오 모델컷", "일반 착용컷", "unknown"]` 또는 `"numeric"` |
| `method` | `vision` (rule/vision/llm 중) |

- 정의는 `intel_db.py proxy-load`로 `proxy_defs`에 등록된다 — **한 번 정의된 프록시는
  다음 요청·다른 카테고리에서 그대로 재사용된다.**
- 새 요청이 오면 먼저 `proxy_defs`를 조회해 **비슷한 프록시가 이미 있으면 그것을 쓴다**
  (이름만 다른 중복 정의를 만들지 않는다). 값 공간을 바꿔야 하면 새 이름으로 정의한다 —
  같은 이름의 값 공간을 바꾸면 기존 캐시와 섞인다.
- **정의 주체는 AI다 (D23, 2026-07-31 사용자 확정).** 분석 요청을 받으면 그 요청에
  유용한 프록시를 **스스로 판단해 정의 카드를 만들고 즉시 등록·판정한다** — 사용자에게
  프록시 선택이나 값 공간을 묻지 않는다. 대신 등록한 **정의 카드(질문·값 공간·method)를
  보고**해 사용자가 사후에 바로잡을 수 있게 한다. **예외 없다** — 사람 외형을 다루는
  값 공간도 AI가 §5 정직성 규칙 안에서 설계·등록한다(사전 확인 절차 없음, D23 후속 지시).
- **broad 요청은 여러 축으로 디테일화한다** — "썸네일에 따라"처럼 재료만 가리키는
  요청이면 그 재료에서 판정 가능한 축들을 AI가 분해해 **정의 카드 여러 장**으로 만든다
  (예: 모델 유무·컷 종류 / 배경 유형 / 이미지 내 텍스트·배지 유무 / 색감 계열).
  같은 재료의 카드들은 proxy-extractor에 **한 번에 넘겨 재료 1회 열람으로 동시
  판정**한다(이미지를 축 수만큼 다시 보지 않는다 — 에이전트가 다중 카드를 받는다).
  축이 늘수록 다중비교 위험이 커진다 — 리포트 가드레일(§4의 8)이 이를 상기시킨다.

## 3. 판정 — method별 실행

| method | 비용 | 실행 |
|---|---|---|
| `rule` | 0 | 정규식·문자열 규칙(영문/한글 판별, 배지 패턴 매칭). 리포트 생성 시 즉석 계산해도 되지만, 캐시에 넣어두면 시트 미러로도 공유된다 |
| `vision` | 상품당 이미지 1회 판정 | **반드시 캐시 먼저 조회.** 미캐시분만 `proxy-extractor` 서브 에이전트에 배치로 위임(이미지 20~40장 묶음, 병렬 스폰 가능 — 전수조사 핏 분류에서 검증된 패턴) |
| `llm` | 텍스트 판정 | 상품명·상세 텍스트 기반. 캐시 우선은 동일 |

판정 결과는 `intel_db.py proxy-load`로 `proxy_cache`에 적재한다:

```json
{"proxy": {"proxy_name": "thumb_model", "question": "...", "material": "image",
           "value_space": ["모델 없음(제품만)", "스튜디오 모델컷", "일반 착용컷", "unknown"],
           "method": "vision"},
 "judgments": [{"site": "musinsa", "product_id": "4297589",
                "fingerprint": "https://image.msscdn.net/....jpg",
                "value": "스튜디오 모델컷", "basis": "전신 포즈·무지 배경"}]}
```

- **fingerprint = 판정 재료의 식별자** — image 프록시는 `image_url`, name 프록시는
  `name` 원문. 재료가 안 바뀌면 캐시가 유효하고, 이미지가 교체되면 지문이 달라져
  **자동으로 재판정 대상**이 된다. TTL이 필요 없다.
- 판정 전에 **미캐시 건수와 예상 비용을 보고**한다("120건 중 85건은 캐시, 35건만
  신규 판정"). 전량 미캐시 + 대규모면 범위 협의(상위 N개부터).

## 4. 분석 축 주입 (자동)

`intel_data.collect()`가 `proxy_defs`를 읽고, 상품마다 **현재 재료의 지문과 맞는**
캐시 값을 `px_<이름>` 필드로 붙인다(지문이 어긋나면 `null` — 이미지가 바뀌면 자동 무효화).
`meta.proxies`에 정의 목록·판정 건수도 함께 담긴다.

그 다음은 **자동으로 검정 대상이 된다**(D39):

- 범주형 프록시 → `cat_axes()`가 **그룹 비교 축**으로 넣는다("착용컷이 제품컷보다
  하트가 높은가"가 5관문을 거쳐 검정된다)
- 수치형 프록시 → `num_axes()`가 **상관·분포 축**으로 넣는다. 스타일 접기에서
  중앙값 집계된다(D34)
- 미판정(`null`)은 결측으로 잡혀 EDA 결측 지도에 뜬다 — 판정률이 낮으면 그 사실이 보인다

※ 구 HTML 대시보드의 "변인통제 필터 자동 생성"은 D27로 폐기됐다. 조건을 바꿔가며
확인하는 일은 사람 손이 아니라 **엔진이 5관문으로 미리 돌린다.**
- 숫자형 프록시 → 산점도 축 후보에 자동 추가
- 프록시 필터·축에는 **"AI 판정"** 표기가 붙는다 — 노출값과 판정값을 구분한다

## 5. 정직성 규칙

- **프록시 값은 판정이지 사실이 아니다.** 미판정은 `(미판정)`으로 구분한다(0도
  unknown도 아니다 — 판정을 안 한 것이다).
- 확신 없으면 `unknown` — 찍지 않는다. basis(판정 근거 한 줄)를 캐시에 남긴다.
- **사람 외형 판정(모델 특성 등)은 이미지에 보이는 인상의 분류이지 실제 국적·정체성
  추정이 아니다.** 값 이름에 그 성격이 드러나게 짓고("~인상"처럼 분류임이 보이게),
  리포트 각주에 명시하며, 정의 카드 보고에 포함한다. 판별이 안 서면 unknown.
- 프록시로 만든 상관도 §4 가드레일(심슨·다중비교·n)을 그대로 받는다 — 프록시 축이
  늘수록 다중비교 위험이 커진다는 것을 안내문이 상기시킨다.
