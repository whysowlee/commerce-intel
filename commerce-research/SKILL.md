# commerce-research

공개 API가 없는 커머스 사이트에서 **화면에 노출된 값만** 모아 표와 리포트로 만든다.

## 이 스킬의 원칙

1. **추정하지 않는다.** 사이트가 보여주지 않는 값은 `null`이고 리포트에 "미노출"로 찍힌다.
   리뷰 수로 판매량을 역산하는 식의 추정은 하지 않는다. 사용자가 요청해도 하지 않고,
   대신 무엇이 미노출인지 알려준다.
2. **수집과 처리를 나눈다.** 수집 결과는 항상 §데이터 계약대로 JSON에 담고,
   검증·집계·리포트는 `scripts/`가 한다. 이 경계 덕분에 수집 방식이 바뀌어도 리포트는 그대로다.
3. **막히면 멈추고 보고한다.** 차단(403/429/캡차)을 우회하지 않는다. 거기까지 모은 것으로
   부분 리포트를 만들고 어디서 멈췄는지 밝힌다.

## 시작하기 전에 확정할 것

사용자 요청에서 아래를 뽑아낸다. **추론하지 말고, 빠진 게 있으면 한 번 물어본다.**

| 항목 | 설명 |
|---|---|
| 스토리 | A 브랜드 라인시트 / B 카테고리 전수조사 / C 랭킹 스냅샷·변화 |
| 대상 | 브랜드명 또는 카테고리명 |
| 사이트 | **모든 스토리에서 필수. 기본값이 없다.** 요청에 명시된 무신사/29CM만 수집한다 |
| 기간 | **스토리 C에서만, 그리고 필수다.** 기간이 없으면 변화 분석을 하지 않는다 |

**사이트에 기본값을 두지 않는다.** 애초에 요청에 플랫폼 이름이 없으면 이 스킬은
트리거되지 않는 것이 맞다(frontmatter description 참조). 그럼에도 사이트가 특정되지
않은 채 실행됐다면 — 예: 대화 중간에 "그 브랜드도 정리해줘" — 무신사로 가정하지 말고
어느 사이트인지 물어라. "둘 다"라고 답하면 둘 다 수집한다.

기간은 절대 날짜로 바꿔 리포트에 적는다("지난 일주일" → 실행일 기준 7일 전 ~ 오늘).
오늘 날짜를 모르면 추측하지 말고 `date +%Y-%m-%d`로 확인한다.

## 공통 워크플로우

### 1단계 — 사이트 어댑터를 읽는다

작업할 사이트의 참고 파일을 **먼저 읽는다.** URL 패턴, 페이지 순회 방법, 필드 매핑,
그 사이트만의 함정이 거기 있다.

- 무신사 → `references/musinsa.md`
- 29CM → `references/29cm.md`

### 2단계 — 대상이 실제로 있는지 확인한다

브랜드/카테고리를 찾고 **사이트가 말하는 총 개수를 적어둔다.** 이 숫자가 나중에
수집이 온전했는지 판정하는 기준(`meta.source_total`)이 된다.

검색 결과가 0건이면 **거기서 멈춘다.** 빈 리포트를 만들지 말고 "그런 브랜드/카테고리를
찾지 못했다"고 알린다. 비슷한 후보가 있으면 같이 제시한다.

### 3단계 — 수집한다

어댑터에 적힌 경로로 목록을 끝까지 순회한다. 규칙은 §지켜야 할 규칙에 있다.

수집하면서 **페이지 단위로** `data/raw/`에 저장한다. 중간에 끊겨도 이어서 할 수 있어야 한다.

### 4단계 — 검증한다

```bash
python3 scripts/validate_data.py data/raw/<파일>.json --json data/validation.json
```

종료 코드로 판단한다.

- `0` 그대로 리포트를 만든다
- `1` 만들되, 출력된 경고를 사용자에게도 전한다
- `2` **리포트를 만들지 말고 원인부터 본다.** 결측이 30%를 넘었다면 사이트 구조가
  바뀐 것이다. 어댑터의 필드 매핑을 다시 확인한다

### 5단계 — 리포트를 만든다

```bash
python3 scripts/build_report.py data/raw/<파일>.json \
    --validation data/validation.json \
    --out output/<스토리>-<대상>-<YYYYMMDD-HHmm>.html
```

여러 사이트를 나란히 보려면 JSON을 여러 개 넘긴다. 끝나면 저장 경로를 알리고,
경고 배너가 붙었다면 그 이유도 말한다.

**코드 실행이 안 되는 환경이면** `assets/report-template.html`의 구조와 클래스 이름을
그대로 따라 직접 HTML을 쓴다. 섹션 구성은 `references/report-spec.md`에 있다.

## 스토리별 절차

### A. 브랜드 라인시트

> "무신사에서 인사일런스 상품 전체 라인시트로 정리해줘"

1. 브랜드 페이지를 찾아 **전 상품**을 페이지 끝까지 모은다. 상위 몇 개만 보고 끝내지 않는다.
   단, 총 상품 수가 **2,000개를 넘으면** 수집을 시작하지 않고 규모·예상 소요를 알린 뒤
   좁힐 축을 제시한다 — 스토리 B의 범위 협의 절차와 같다 (임의 샘플링 금지도 동일).
2. 목록에서 얻을 수 있는 필드는 목록에서 얻는다. 목록에 없는 값 때문에 상품 상세를
   전부 열지 않는다 — 수백 페이지가 된다.
3. `story`는 `brand-linesheet`.
4. 두 사이트를 같이 요청받았으면 사이트별로 JSON을 따로 만들고 리포트에서 합친다.
   **같은 상품을 플랫폼 간에 매칭하지 않는다.** 플랫폼 비교는 리포트가 자동으로 만드는
   두 섹션까지다 — ① 품목(카테고리) 단위 하트 합·후기 합 비교("어떤 품목이 어느
   플랫폼에서 인기인가") ② 사이트별 인기 상품 상위 10.

### B. 카테고리 시장 전수조사

> "무신사 데님팬츠 시장 전수조사 해줘"

**리뷰 본문은 수집하지 않는다.** 만족/불만족 판단 재료는 사이트가 각 상품에 노출한
**후기 수와 평균 평점**뿐이다. 리뷰를 한 건씩 읽고 해석하는 일은 이 스킬의 범위 밖이다.

1. **카테고리를 특정한다.** "바지"처럼 넓으면 사이트의 세부 카테고리 후보를 보여주고
   고르게 한다.
2. **규모를 확인하고 범위를 정한다.** 아래 순서를 그대로 따른다.

   1. 목록 첫 페이지를 요청해 **사이트가 말하는 총 상품 수**를 읽는다 → `source_total`
   2. **0건** → 수집하지 않는다. "검색 결과 0건"으로 보고하고 비슷한 후보를 제시한다
   3. **3,000건 이하** → 묻지 않고 진행한다. 시작할 때 한 줄만 보고한다:
      "데님팬츠(남성, 10~20만원) 2,833개 수집을 시작한다. 예상 소요 약 5분"
   4. **3,000건 초과** → 수집을 시작하지 않는다. 좁힐 축의 **실제 개수를 조회해서**
      함께 제시하고 사용자가 고르게 한다:

      > 데님팬츠는 24,673개다. 이대로는 너무 크다. 좁힐 방법:
      > - 성별 — 남성 N개 / 여성 N개 (조회해 온 실제 값. 유니섹스가 양쪽에 중복 집계돼
      >   절반이 되지 않는 사이트도 있다)
      > - 가격대 — 예: 10~20만원 N개 (무신사는 minPrice/maxPrice 확인)
      > - 세부 카테고리 — 후보와 개수
      >
      > 어느 범위로 할까? ("전체로 해"라고 답하면 전체를 진행하되 예상 소요를 먼저 말한다)

      상한 3,000의 근거는 목록 수집량이 아니라 **총 소요 시간**이다(핏 분류 중 이미지
      확인이 상품당 몇 초씩 든다). 상세는 SPEC §4를 따른다.
   5. 최종 범위를 `meta.target`에 쓴다 — **"데님팬츠(남성)"** 형식.
      리포트 헤더에도 이 이름이 그대로 실린다. 좁혀 놓고 "데님팬츠 전수"라고 쓰면 거짓이다

   **임의 샘플링은 금지다.** 묻지 않고 상위 N개만 수집하는 것이 최악의 실패다 —
   사용자는 시장 전체를 봤다고 믿게 된다.
3. **목록을 끝까지 수집한다.** 후기 수·평점·좋아요 등은 목록에 노출된 값을 그대로 담는다.
   상품 상세는 목록에 없는 값이 꼭 필요할 때만 연다 — 상세 1만 번 열기는 목록 170번의
   수십 배 비용이다.
4. **속성 분류** — 근거가 확실한 순서로 시도한다.
   1. 상품명·옵션·상세 텍스트에 답이 있으면 그걸 쓴다 (예: 이름에 "부츠컷")
   2. 텍스트로 안 되면 대표 이미지를 내려받아 직접 보고 판단한다
   3. 그래도 모르겠으면 `"unknown"`. **찍지 않는다.**

   데님 핏 값: `부츠컷` `와이드` `스트레이트` `슬림` `테이퍼드` `unknown`.
   판단 근거를 `attributes_basis`에 `name`/`detail`/`image`/`unknown` 중 하나로 남긴다.

   **기본 분류 속성은 핏 하나다.** 워싱 톤·기장·소재 같은 추가 속성은 사용자가
   명시적으로 요청할 때만 넣는다 — 이미지 전수 확인이 필요한 속성은 상품 수 × 몇 초의
   비용이 드니 예상 소요를 먼저 알린다.
5. `story`는 `market-scan`. 검증 → 리포트는 공통 워크플로우대로.
   리포트가 후기 수 가중 평균 평점, 상품 평점 분포, 속성 분포를 자동으로 계산한다.
   **전수조사 표는 이미지 열 없이 전 행을 싣는다** — 1만 행 규모에서도 한 파일로
   열리게 하기 위한 결정이다.

### C. 랭킹 스냅샷과 변화

> "무신사 바지 랭킹 top 100, 지난 일주일 변화 보여줘"

한 번 실행하면 **스냅샷 하나가 쌓인다.** 변화는 쌓인 스냅샷들을 비교해서 나온다.
주기 실행은 이 스킬 밖의 일이다 — 실행 환경의 스케줄 기능에 등록하도록 안내하되,
**축적 주기는 30분에 1번이 기준이다.**

주기 실행을 등록할 때는 스냅샷 폴더를 **절대 경로로 고정해라.** 실행마다 작업 폴더가
달라지면 스냅샷이 흩어져 diff가 성립하지 않는다. 축적분은 전부 보존한다 — 오래된
스냅샷을 임의로 지우지 않는다.

**과거는 소급할 수 없다. 변화 분석의 재료는 30분 축적분뿐이다.** 두 사이트 모두
현재 랭킹만 노출한다. "지난주 랭킹 변화"를 요청받았는데 그 기간의 스냅샷이 없다면,
만들 수 없는 것이다 — 지금부터 축적을 시작하자고 안내하고 현재 스냅샷부터 찍는다.
과거 랭킹을 추측으로 채우지 않고, 다른 출처로 대체하지도 않는다.

1. 현재 랭킹 top 100을 모아 `data/snapshots/<site>-ranking-<카테고리>-<YYYYMMDD-HHmm>.json`로
   저장한다. `story`는 `ranking-snapshot`.
   랭킹 목록에는 **"N명이 보는 중", "N명이 구매 중" 같은 실시간 지표**가 붙는 사이트가 있다.
   보이면 `viewers_now` / `buyers_now`에 담는다. 이건 목록에만 있고 상품 상세에는 없다.
2. **기간을 지정받았으면** 비교한다.
   ```bash
   python3 scripts/diff_snapshots.py data/snapshots \
       --site musinsa --target 바지 --from 2026-03-01 --to 2026-03-31 --out data/diff.json
   python3 scripts/build_report.py data/diff.json --out output/ranking-diff.html
   ```
   `diff_snapshots.py`가 `1`을 반환하면 기간 안에 스냅샷이 1개 이하라는 뜻이다.
   **빈 변화 리포트를 만들지 말고** 방금 찍은 스냅샷 리포트만 만든 뒤,
   "비교하려면 스냅샷이 2개 이상 필요하다"고 알린다.
3. **기간을 지정받지 않았으면** 변화 분석을 하지 않는다. 스냅샷만 찍고 리포트를 만든 다음,
   기간을 정해주면 변화를 볼 수 있다고 안내한다.
4. **범위가 다른 스냅샷끼리 비교하지 않는다.** 폴백 등으로 랭킹 범위를 낮췄으면
   (예: 소분류 → 중분류) `meta.target`을 낮춘 이름으로 정직하게 저장한다 —
   `diff_snapshots.py`가 target이 다른 스냅샷을 자동으로 걸러내므로, 이름을 속이면
   서로 다른 랭킹이 섞인 diff가 만들어진다.

## 지켜야 할 규칙

**요청 속도** — 페이지 사이에 0.5~1.5초 쉰다. 병렬로 몰아치지 않는다.

**순회 상한** — 목록 페이지는 200페이지에서 멈춘다. 무한 루프 방지용이며, 상한에 닿으면
`meta.notes`에 적는다.

**재시도** — 실패하면 간격을 늘리며 2번까지 다시 시도한다. 3번 연속 실패하면 그 항목을
건너뛰고 `meta.notes`에 남긴다.

**차단** — 403/429/캡차가 나오면 **즉시 멈춘다.** User-Agent를 바꾸거나 우회하지 않는다.
`meta.incomplete`를 `true`로 두고 중단 지점을 `meta.notes`에 적은 뒤 부분 리포트를 만든다.

**로그인** — 비로그인으로 보이는 것만 모은다. 로그인 벽이 나오면 거기서 멈추고 알린다.

**구조 변경** — 필수 필드가 자꾸 비면 사이트가 바뀐 것이다. `validate_data.py`가 30%를
넘겨 `2`를 반환하면 수집을 계속하지 말고 어댑터의 필드 매핑부터 확인한다.

**하지 않는 것** — 구매·장바구니·찜 등 상태를 바꾸는 조작, 로그인 전용 데이터,
판매량 추정, 플랫폼 간 동일 상품 매칭, 이미지 재배포(리포트는 원본 URL을 링크할 뿐이다).

## 데이터 계약

수집 JSON은 항상 이 모양이다. 스크립트가 이걸 전제로 동작한다.

```json
{
  "meta": {
    "site": "musinsa",
    "story": "brand-linesheet",
    "target": "인사일런스",
    "collected_at": "2026-07-29 14:00:00",
    "item_count": 564,
    "source_total": 564,
    "incomplete": false,
    "notes": []
  },
  "items": [{
    "product_id": "4297589",
    "name": "...", "url": "https://...", "image_url": "https://...",
    "brand": "인사일런스", "category": "데님팬츠",
    "price_original": 139900, "price_sale": 97890, "discount_rate": 30,
    "review_count": 212, "rating": 4.8,
    "view_count": null, "view_count_display": "300회 이상 (최근 1개월)",
    "purchase_count": 5500, "like_count": 84,
    "viewers_now": null, "buyers_now": null,
    "sold_out": false,
    "rank": null,
    "attributes": {"핏": "와이드"}, "attributes_basis": "name"
  }]
}
```

| 필드 | 언제 필수인가 |
|---|---|
| `product_id` `name` `url` `image_url` `brand` `category` `price_original` `price_sale` `discount_rate` `sold_out` | 항상. 결측률 5%를 넘으면 경고, 30%를 넘으면 수집 실패로 본다 |
| `review_count` `rating` `view_count` `purchase_count` `like_count` `viewers_now` `buyers_now` | 사이트가 보여줄 때만. **안 보이면 `null`** |
| `view_count_display` `purchase_count_display` | 사이트가 **구간으로만** 보여줄 때. 아래 참조 |
| `rank` | 스토리 C |
| `attributes` `attributes_basis` | 스토리 B |

`reviews[]`(리뷰 본문)는 **수집하지 않는다.** 담겨 있으면 검증기가 경고한다.

`rating`은 **5점 만점으로 통일한다.** 사이트가 100점 척도로 주면 나눠서 넣는다(어댑터 참조).
`price_sale`은 할인 없으면 `price_original`과 같다. 쿠폰가는 판매가로 치지 않는다.

### 구간으로만 보여주는 값은 정수로 바꾸지 않는다

무신사 조회수는 `"300회 이상 (최근 1개월)"`처럼 나온다. 이걸 `view_count: 300`으로
담으면 **없는 정밀도를 만들어내는 것**이고, 그 값으로 순위를 매기면 리포트가 조용히 틀린다.

- 정확한 정수가 보일 때만 `view_count`에 담는다
- 구간 표기면 `view_count`는 `null`, 원문을 `view_count_display`에 **문자열 그대로**
- 리포트는 문구 그대로 싣고 순위 차트에는 쓰지 않는다. 둘 다 채우면 검증기가 경고한다
