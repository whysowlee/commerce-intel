# commerce-research

공개 API가 없는 커머스 사이트에서 **화면에 노출된 값만** 모아 표와 리포트로 만든다.

## 이 스킬의 원칙

1. **추정하지 않는다.** 사이트가 보여주지 않는 값은 `null`이고 리포트에 "미노출"로 찍힌다.
   리뷰 수로 판매량을 역산하는 식의 추정은 하지 않는다. 사용자가 요청해도 하지 않고,
   대신 무엇이 미노출인지 알려준다.
2. **수집과 처리를 나눈다.** 수집 결과는 항상 §데이터 계약대로 JSON에 담고,
   검증·집계·리포트는 `scripts/`가 한다. 이 경계 덕분에 수집 방식이 바뀌어도 리포트는 그대로다.
3. **막히면 멈추고 보고한다.** 차단(403/429/캡차)을 우회하지 않는다. 거기까지 모은 것으로
   부분 리포트를 만들고 어디서 멈췄는지 밝힌다.

## 시작하기 전에 확정할 것

사용자 요청에서 아래를 뽑아낸다. **추론하지 말고, 빠진 게 있으면 한 번 물어본다.**

| 항목 | 설명 |
|---|---|
| 스토리 | A 브랜드 라인시트(멀티 플랫폼) / B 카테고리 전수조사 / C 랭킹 스냅샷·변화 |
| 대상 | 브랜드명 또는 카테고리명 |
| 사이트 | **모든 스토리에서 필수. 기본값이 없다.** 요청에 명시된 무신사/29CM/**자사몰**만 수집한다. **스토리 A는 1개 이상** — 2개 이상이면 합집합 비교가 된다. 자사몰은 브랜드마다 도메인이 다르므로 **먼저 도메인을 확정한다**(2단계) |
| 기간 | **스토리 C에서만, 그리고 필수다.** 기간이 없으면 변화 분석을 하지 않는다 |

**사이트에 기본값을 두지 않는다.** 애초에 요청에 플랫폼 이름이 없으면 이 스킬은
트리거되지 않는 것이 맞다(frontmatter description 참조). 그럼에도 사이트가 특정되지
않은 채 실행됐다면 — 예: 대화 중간에 "그 브랜드도 정리해줘" — 무신사로 가정하지 말고
어느 사이트인지 물어라. "둘 다"라고 답하면 둘 다 수집한다.

기간은 절대 날짜로 바꿔 리포트에 적는다("지난 일주일" → 실행일 기준 7일 전 ~ 오늘).
오늘 날짜를 모르면 추측하지 말고 `date +%Y-%m-%d`로 확인한다.

## 공통 워크플로우

### 1단계 — 사이트 어댑터를 읽는다

작업할 사이트의 참고 파일을 **먼저 읽는다.** URL 패턴, 페이지 순회 방법, 필드 매핑,
그 사이트만의 함정이 거기 있다.

- 무신사 → `references/musinsa.md`
- 29CM → `references/29cm.md`
- 자사몰(브랜드 자체 쇼핑몰) → `references/cafe24.md` — **Cafe24 기반만 지원한다.**
  이 어댑터는 사이트 하나가 아니라 엔진 하나를 다룬다

### 2단계 — 대상이 실제로 있는지 확인한다

브랜드/카테고리를 찾고 **사이트가 말하는 총 개수를 적어둔다.** 이 숫자가 나중에
수집이 온전했는지 판정하는 기준(`meta.source_total`)이 된다.

검색 결과가 0건이면 **거기서 멈춘다.** 빈 리포트를 만들지 말고 "그런 브랜드/카테고리를
찾지 못했다"고 알린다. 비슷한 후보가 있으면 같이 제시한다.

#### 자사몰이면 먼저 도메인을 확정한다

무신사·29CM는 사이트가 하나씩이지만 **자사몰은 브랜드마다 도메인이 다르다.**
사용자가 URL을 줬으면 그대로 쓰고, 브랜드 이름만 말했으면 아래 순서로 확정한다.
**도메인을 지어내지 마라** — `{브랜드}.co.kr`을 추측해 넣는 것이 대표적인 실패다.

1. **검색해서 공식 자사몰 후보를 찾는다**
2. **후보를 열어 브랜드가 맞는지 확인한다** — 페이지 타이틀·상단 로고·푸터의 상호를
   대조한다. 후보가 여럿이거나 애매하면 **제시하고 사용자가 고르게 한다**
3. **Cafe24인지 확인한다** — 페이지 HTML에 `cafe24` 계열 신호가 있어야 한다
   (`cfa-js.cafe24.com` 등, 판별식은 어댑터 §1). **Cafe24가 아니면 수집하지 않고
   비범위임을 알린다.** 고도몰·임웹·Shopify는 지원하지 않는다
4. 확정한 도메인을 `meta.site`에 담고(`insilence.co.kr`), 어떻게 찾았는지를
   `meta.notes`에 남긴다

#### 무신사에서 동명 브랜드 매장 확인

무신사의 일부 브랜드는 성별 매장이나 지역 매장 등 여러 매장으로 분산돼 있다
(예: 인사일런스 + 인사일런스 우먼). **주소(brand slug)를 이미 알아도** 수집 시작 전에
반드시 브랜드 이름으로 한 번 검색해야 한다(절차 불변식). 자세한 API 경로와 예시는
`references/musinsa.md`에 있다.

- 동명 매장이 2개 이상이면 개수와 함께 제시하고 어느 쪽을 원하는지 물어본다
- 1개뿐이면 그냥 진행한다

### 3단계 — 수집한다

**브라우저로 화면을 열어 모으는 것이 기본이다.** 어댑터에 적힌 경로로 목록을 끝까지
순회한다. 규칙은 §지켜야 할 규칙과 §브라우저로 목록을 모으는 방법에 있다.

수집하면서 **페이지 단위로** `data/raw/`에 저장한다. 중간에 끊겨도 이어서 할 수 있어야 한다.

## 브라우저로 목록을 모으는 방법

목록 수집에는 **브라우저를 제어할 수 있는 도구가 필요하다** — 페이지를 열고, 스크롤하고,
**페이지 안에서 JS를 실행**할 수 있으면 된다. 없으면 어댑터의 HTTP 경로로 낮춰서 모으되
**전량 보장이 깨진다는 것을 리포트에 명시한다**(품절 상품이 빠질 수 있다).

1. **추출은 페이지 안에서 JS로 한다.** 화면을 읽는 스냅샷으로 카드를 훑지 마라 —
   수천 개 규모에서 컨텍스트가 터진다. 카드에서 필요한 필드만 뽑아 배열로 받아라.
   **HTML을 문자열로 받아 정규식으로 카드를 자르지도 마라** — 카드 안에 같은 태그가
   중첩돼 있으면 첫 닫는 태그에서 끊겨 조용히 놓친다(실측: 608개 중 574개만 잡혔다).
   카드는 **DOM에서** 잡는다 — 상품 링크가 하나뿐인 가장 가까운 조상이 카드다.
2. **스크롤 목록은 매 스텝마다 수집해 `product_id`로 누적한다.**
   목록 DOM은 화면에 보이는 만큼만 유지하는 경우가 있어서(가상 스크롤), **끝까지
   스크롤한 뒤 한 번 읽으면 마지막 화면 몇십 개만 잡힌다.** 실측에서 실제로 겪은 함정이다.
3. **끝났다는 판정은 3연속 무증가다.** 새 상품이 0개인 스텝이 3번 이어지면 끝으로 본다.
   페이지네이션 목록이면 빈 페이지나 "결과가 없습니다" 메시지로 끝나므로 추정이 필요 없다.
4. **자연 종료가 없는 목록이 있다.** 카테고리 목록은 수만 개까지 계속 나온다.
   규모 상한에 닿으면 마감하고, **상한에 걸려 끊은 것과 목록이 끝난 것을 구분해서**
   `meta.notes`에 적는다.
5. **수집 건수를 화면 총계와 대조한다.** 목록 화면에는 보통 `24,686개`처럼 총계가 찍혀
   있다. 그 값을 `meta.source_total`에 담는다. **수집 건수를 넣지 마라** — 자기 자신과
   비교하게 되어 검증이 항상 통과한다. 총계를 못 읽었으면 `null`로 두고 그 사실을 남긴다.
6. **랭킹은 순위 번호로 검증한다.** `가장 큰 순위 == 수집 건수 == 순위의 중복 없는 개수`가
   성립해야 한다. 결번이나 중복이 있으면 불완전이다. 순위 번호가 없는 카드는 광고이므로 뺀다.
7. **요청한 화면이 맞는지 확인한다.** 파라미터를 조용히 무시하고 다른 목록을 주는 화면이
   있다. 도달한 URL과 첫 상품이 요청한 조건과 맞는지 보고, 다르면 실패로 처리한다.
8. **축약 표기(`1.2천`·`판매 9만개`)는 정수로 파싱해 담는다**(가능하면 원문도 함께).
   **구간 표기(`300회 이상`)는 정수로 바꾸지 마라** — 둘의 오차 성질이 다르다.
   §데이터 계약의 표를 따른다.

### 4단계 — 검증한다

```bash
python3 scripts/validate_data.py data/raw/<파일>.json --json data/validation.json
```

종료 코드로 판단한다.

- `0` 그대로 리포트를 만든다
- `1` 만들되, 출력된 경고를 사용자에게도 전한다
- `2` **리포트를 만들지 말고 원인부터 본다.** 결측이 30%를 넘었다면 사이트 구조가
  바뀐 것이다. 어댑터의 필드 매핑을 다시 확인한다

### 4.5단계 — 리포트 전 점검 (2026-07-30 신설)

**검증이 `2`(FAIL)면 리포트를 만들지 마라.** 실제로 걸렸던 것들이고, 대상을 바꿔도
같은 자리에서 또 걸린다.

| 증상 | 원인 | 해야 할 일 |
|---|---|---|
| `category 결측 100%` | **브랜드·카테고리 목록에는 카테고리가 없다** | 무신사는 상품 상세의 `baseCategoryFullPath` 말단을 상품마다 받는다(스토리1의 지배 비용이 이것이다). 29CM은 목록의 `extraInfo.categories` 코드를 카테고리 페이지 `meta description`으로 해석한다 |
| 품절이 0건 | 무신사 목록은 **`isSoldOut=true` 없이는 품절을 빼고 준다** | URL·API에 `isSoldOut=true`를 붙인다. 붙이기 전/후 총계를 대조해 몇 건 늘었는지 `meta.notes`에 남긴다 |
| `attributes 누락` 경고가 전 건에 | 스토리 B에서 **속성 분류 단계를 건너뛰었다** | 수집 후 반드시 분류한다. 이름으로 되는 것부터 채우고 남는 것만 이미지를 본다 |
| 수집 건수 < 총계인데 페이지는 끝까지 갔다 | **추천순으로 순회했다.** 인기·추천 정렬은 깊은 페이지에서 재배열되어 경계 상품이 중복으로 오고 그만큼 건너뛴다(29CM 실측: 342페이지 완주했는데 유니크 13,811/17,093) | **결정적 정렬로 다시 순회한다**(신상품순·낮은가격순 등). 같은 페이지를 두 번 불러 비교하는 테스트로는 안 잡힌다 — **총계 대조가 유일한 탐지 수단이다** |
| 수집 건수 < 화면 총계 | 브라우저 파서가 카드를 놓쳤다 | **카드 = 고유 `product_id`가 1개인 가장 가까운 조상.** 링크 수로 세면 안 된다(이미지·상품명 2개), 가격 텍스트만 기준으로 올라가면 6개 카드를 담은 행 컨테이너까지 올라간다 |
| 성별로 좁혔는데 남성이 섞인다 | 무신사 카테고리 **화면은 스크롤하면 `gf`를 잃는다** | 성별 축은 경로 A(PLP API)로만 좁힌다. 화면 칩·총계는 필터를 보여주지만 목록 요청은 `gf=A`로 나간다 |

수집이 끝나면 **화면 총계와 수집 건수를 나란히 적어 보고한다.** 같으면 완주, 다르면 그 차이를 밝힌다.

### 5단계 — 리포트를 만든다

```bash
python3 scripts/build_report.py data/raw/<파일>.json \
    --validation data/validation.json \
    --out output/<스토리>-<대상>-<YYYYMMDD-HHmm>.html
```

**여러 플랫폼을 비교하려면 JSON을 여러 개 넘긴다** — 사이트당 하나씩이다. 생성기가
합집합·매칭·통합축·비교 섹션을 만든다(스토리 A 참조). `story`가 서로 다른 JSON을 섞으면
거부한다. 끝나면 저장 경로를 알리고, 경고 배너가 붙었다면 그 이유도 말한다.

**코드 실행이 안 되는 환경이면** `assets/report-template.html`의 구조와 클래스 이름을
그대로 따라 직접 HTML을 쓴다. 섹션 구성은 `references/report-spec.md`에 있다.
**실행이 거부되거나 반복 실패해서 뒤늦게 드러난 경우도 같다** — 확인 요청은 1회만 하고,
그래도 진행이 안 되면 이 폴백으로 전환한다. 검증 스크립트를 건너뛰었다는 사실을
리포트 경고 배너와 대화 양쪽에 명시한다.

## 스토리별 절차

### A. 브랜드 라인시트 — 멀티 플랫폼 비교

> "무신사랑 29cm에서 인사일런스 라인시트로 정리해줘"
> "무신사에서 인사일런스 상품 전체 라인시트로 정리해줘" (플랫폼 1개)

**이 스토리의 핵심은 한 브랜드를 여러 플랫폼에서 비교하는 것이다.** 입력은 브랜드 +
플랫폼 **1개 이상**이다. 1개면 단일 라인시트, 2개 이상이면 합집합 비교 리포트가 된다.

1. **요청에 적힌 플랫폼을 모두 확인한다.** "무신사랑 29cm", "둘 다", "두 플랫폼" 모두
   두 사이트를 뜻한다. 플랫폼이 하나만 적혀 있으면 하나만 한다 — 친절하게 더 붙이지 않는다.
2. **플랫폼마다 브랜드 전 상품을 끝까지 모은다.** 상위 몇 개만 보고 끝내지 않는다.
   - 규모 상한 **3,000개는 플랫폼별로** 적용한다(합집합 크기가 아니다). 어느 한쪽이
     초과하면 수집을 시작하지 않고 규모·예상 소요를 알린 뒤 좁힐 축을 제시한다 —
     스토리 B의 범위 협의 절차와 같다 (임의 샘플링 금지도 동일)
   - 목록에서 얻을 수 있는 필드는 목록에서 얻는다. 목록에 없는 값 때문에 상품 상세를
     전부 열지 않는다 — 수백 페이지가 된다
   - **브랜드 목록은 브라우저로 모은다.** 29CM의 브랜드 목록 API는 **카탈로그 전량을 주지
     않는다** — 실측에서 435개 중 422개만 왔다(누락 13건 중 11건이 품절이지만 품절 필터는
     아니다. 원인 미특정이라 **어떤 상품이 빠질지 예측할 수 없다**).
     빠진 상품은 **"상대 플랫폼 단독 입점"으로 잘못 집계**되어 이 스토리의 핵심 분석을
     직접 오염시킨다. HTTP로 낮춰 모을 수밖에 없다면 어댑터에 적힌 대로 `MONTHLY` +
     정렬 종류 합집합으로 모으고, **전량이 아닐 수 있다는 것을 리포트에 명시한다**
   - **무신사 브랜드는 URL이 두 개다.** `/brand/{slug}`는 브랜드 홈이라 일부만 나온다
     (실측 128/563). 전 상품은 `/brand/{slug}/products`다. 둘 다 상품이 보이므로
     **화면 총계와 대조**해야 구분된다
   - **⚠️ 품절 상품을 포함한다. 목록의 기본 필터가 사이트마다 다르다.**
     무신사는 기본이 **품절 제외**(인사일런스 563)이고 `&isSoldOut=true`를 붙여야
     전량(**2,022**)이다. 29CM은 기본이 **품절 포함**이다(필터 이름이 `품절상품 제외`).
     **플랫폼마다 필터를 맞춰라** — 안 맞추면 단독 입점 분석이 통째로 틀어진다.
     실측: 필터가 어긋난 상태에서 "29CM 단독 83건"이 나왔는데 맞추자 **0건**이 됐다
     (90건이 무신사 품절 상품과 매칭됐다).
     화면 총계를 `source_total`에 담을 때 **어떤 필터 상태인지 `meta.notes`에 함께 적어라** —
     필터가 걸린 총계도 대조를 정상 통과하기 때문에, 명시하지 않으면 근거가 되지 않는다
   - **카테고리는 화면의 소분류 필터를 순회해서 붙인다** — 카드에도 목록 API에도 없다.
     대분류별 총계 합이 전체 총계와 맞는지로 병렬 축(중복 집계 축)을 걸러내고,
     소분류별 수집 건수를 각각 화면 총계와 대조한다. 상세는 어댑터에 있다
   - **자사몰은 카테고리를 전부 돌아 모은다.** 브랜드 페이지 하나로 끝나는 다른 사이트와
     다르다. **`ALL` 카테고리 하나로는 부족하다** — 실측(인사일런스): 남·여 `ALL` 합집합
     428인데 `SEASON OFF` 349 중 **127건(23%)이 `ALL`에 없다.** 네비게이션의 상품
     카테고리를 모두 순회하고 `product_id`로 중복을 제거한다. **화면 총계가 없으므로
     `source_total`은 `null`**이고, 완전성 근거는 "모든 카테고리 소진 + 각 카테고리가
     `btnNext=#none` 도달"이다
   - **자사몰의 품절은 목록에 표시가 없다** — 배지 없이 섞여 들어온다(실측 192개 스캔에
     품절 문자열 0건인데 그중 실제 품절이 있었다). 상세 JSON-LD `offers`로만 판정하고,
     **비교할 때 무신사를 `&isSoldOut=true`로 맞춘다**
   - **자사몰은 후기·평점·좋아요·조회수·누적판매를 수집하지 않는다** — 전부 `null`이다.
     robots.txt가 후기 게시판 페이지 넘김을 막고, 스토어에 따라 화면에 개수 자체가 없다.
     **우회하지 않는다.** 이 사실을 리포트에 밝힌다
   - **한 사이트가 실패해도 나머지는 끝낸다.** 실패한 사이트는 `meta.notes`에 남기고
     리포트에 명시한다. 부분 실패를 전체 실패로 만들지 않는다
3. **사이트별로 JSON을 따로 만든다.** `story`는 `brand-linesheet`.
   **수집 JSON은 언제나 사이트 하나짜리다** — 합집합·매칭은 수집 단계에서 하지 않는다.
   상품명은 사이트가 준 문자열을 **그대로** 담는다(정규화는 리포트 생성기가 한다).
4. **리포트 생성기에 JSON을 모두 넘긴다.** 합집합·매칭·통합축·비교 섹션은 코드가 만든다.

   ```bash
   python3 scripts/build_report.py \
       data/raw/musinsa-brand-linesheet-인사일런스-<ts>.json \
       data/raw/29cm-brand-linesheet-인사일런스-<ts>.json \
       --validation data/v-musinsa.json --validation data/v-29cm.json \
       --out output/brand-linesheet-인사일런스-<ts>.html
   ```

#### 동일 상품 매칭은 완전일치만이다

두 플랫폼의 같은 상품을 한 행으로 묶는 규칙은 **하나뿐이다** — 상품명을 정규화해
(소문자화 · `[...]`·`(...)` 제거 · 영숫자와 한글만 남김) **완전히 같을 때만** 동일 상품이다.

**유사도·가격으로 추정 매칭하지 마라.** 실측에서 오탐이 확인됐다 —
`헨리넥 숏슬리브`와 `와플 헨리넥 롱슬리브`, `프렌치 워크 자켓 FADED BLUE`와 `FADED BLACK`은
다른 상품이고, `레터링 그래픽 티셔츠`와 `스탠실 그래픽 티셔츠`는 **정가까지 66,000원으로
같다.** 가격이 오탐을 확증해주므로 가격은 보조 신호로도 쓸 수 없다.

매칭이 안 되는 상품은 **실패가 아니라 단독 입점 사실이다.** 억지로 붙이지 않는다.

#### 리포트가 자동으로 만드는 것

플랫폼이 2개 이상일 때 코드가 계산한다 — 직접 표를 쓰지 마라.

- **합집합 전 상품 표 + `입점` 칼럼** — 매칭된 상품은 1행이고 어느 플랫폼에 있는지가 찍힌다
- **품목 통합축** — 사이트 카테고리 이름은 서로 다르다(실측: 43종/37종 중 8종만 겹침).
  매칭된 동일 상품의 카테고리 대응 관계에서 코드가 축을 만든다. **매핑 표를 손으로 쓰지 마라**
- **비교 레이어 3블록** — ① **품목별 입점 차이**(양쪽/단독 표 + 사이트별 단독 KPI·판매가 분포)
  ② 같은 상품 반응 강도 비교(매칭 상품만) ③ 가격·할인 포지셔닝 차이(**집계만** — 상품별
  대조는 전 상품 표의 `가격 차이` 열이다).
  구 `단독 입점 상품 성격`은 ①에 합쳤다(2026-07-30) — 품목 분포 막대가 ① 표의 `단독` 열과
  같은 값이었다
- **상품 목록이 나오는 표는 `전 상품` 하나뿐이다** (2026-07-30) — 같은 상품을 두 표에
  싣지 않는다. 걸러 보는 것은 칩으로 한다(판매·가격·입점·품목).
  **`판매` 축의 기본은 판매 중만**이고 품절은 칩으로 켠다 — 건수가 칩에 찍히므로
  조용히 숨기는 것이 아니다
- 사이트별 **품목 성적표**는 그대로 유지된다.
  **인기 상품 상위 10은 만들지 않는다**(2026-07-30) — 전 상품 표를 좋아요로 정렬하면
  같은 답이 나오므로 같은 답을 두 번 그리지 않는다

**조회수·누적판매로 플랫폼 비교 차트를 만들지 않는다** — 29CM이 노출하지 않는 지표다.
비교에 쓸 수 있는 건 하트·후기·평점·가격뿐이고, 나머지는 무신사 단독으로만 그린다.

**자사몰은 반응 강도 비교(②)에서 뺀다** — 하트·후기를 수집하지 않으므로 비교할 값이 없다.
**빈 열이나 0으로 그리지 마라**("반응이 없는 플랫폼"으로 읽힌다 — 미수집과 0은 다르다).
뺐다는 사실을 각주로 밝힌다. ①·③은 그대로 성립하고, 비교 대상이 자사몰뿐이면 ②를 만들지 않는다.

### B. 카테고리 시장 전수조사

> "무신사 데님팬츠 시장 전수조사 해줘"

**리뷰 본문은 수집하지 않는다.** 만족/불만족 판단 재료는 사이트가 각 상품에 노출한
**후기 수와 평균 평점**뿐이다. 리뷰를 한 건씩 읽고 해석하는 일은 이 스킬의 범위 밖이다.

1. **카테고리를 특정한다.** "바지"처럼 넓으면 사이트의 세부 카테고리 후보를 보여주고
   고르게 한다. **카테고리 코드를 매번 조사하지 마라** — 두 사이트의 실측 코드 카탈로그가
   있고(스토리 C와 공유), 이름으로 찾는다. 어느 플랫폼이든 절차가 같다.

   #### 사이트에 그 이름의 카테고리가 없을 때 (2026-07-30 사용자 확정)

   **검색 키워드 ∩ 상위 카테고리**를 범위로 삼는다. 예: 29CM에는 '여성 코튼 팬츠'가 없다
   (여성 바지 소분류 10종에 코튼이 없고 소재 필터도 비어 있다) → 검색 `코튼 팬츠` ∩
   여성의류>바지. **비슷한 다른 카테고리로 슬쩍 바꾸지 않는다** — 이름과 범위가 어긋난다.

   교집합은 사이트 검색이 만드는 것이라 **엉터리 키워드를 걸러내는 가드가 필수다.**
   세 가지를 반드시 건다.

   | 가드 | 판정 | 할 일 |
   |---|---|---|
   | **G1** | 교집합 **0건** | 수집하지 않는다. "그런 상품군을 찾지 못했다"고 보고한다. 실측상 무의미 키워드(`우주`·`라면 팬츠`·오타·자음 나열)는 전부 여기서 걸린다 |
   | **G2** | 교집합이 카테고리 총계의 **90% 이상** | 키워드가 사실상 무시된 것이다. 멈추고 물어본다 — 카테고리만으로 갈지, 다른 키워드를 쓸지. 실측: 무신사 코튼팬츠 카테고리에 `코튼 팬츠`를 걸면 **99.8%**가 나온다(무의미) |
   | **G3** | 상품명 **실제 매칭률** | 계산해서 `meta.notes`와 리포트에 적는다. 검색은 소재·상세까지 훑으므로 이름에 안 드러나는 상품이 섞인다(실측: 코튼 22.6%) |

   **범위를 더 좁혀야 하면 G3을 필터로 쓴다** — 상품명에 키워드가 실제로 있는 것만 남긴다.
   그러면 `meta.target`에 그 사실이 드러나야 하고(예: `코튼 팬츠(여성 바지, 검색∩상품명)`),
   **소재는 맞지만 이름에 안 쓴 상품이 빠진다는 것을 리포트에 명시한다.**

   **키워드 토큰 중 무엇이 변별력 있는지는 사이트에 물어서 정한다** — 토큰별로 교집합을
   세고 카테고리의 90% 이상을 덮는 토큰은 버린다(실측: 여성 바지에서 `바지` 100.0%,
   `팬츠` 98.3% → 버림 / `코튼` 26.4% → 남김). 불용어 목록을 손으로 관리하지 않는다.
2. **규모를 확인하고 범위를 정한다.** 아래 순서를 그대로 따른다.

   1. 목록 첫 페이지를 요청해 **사이트가 말하는 총 상품 수**를 읽는다 → `source_total`
   2. **0건** → 수집하지 않는다. "검색 결과 0건"으로 보고하고 비슷한 후보를 제시한다
   3. **5,000건 이하** → 묻지 않고 진행한다. 시작할 때 한 줄만 보고한다:
      "데님팬츠(남성, 10~20만원) 2,833개 수집을 시작한다. 예상 소요 약 5분"
   4. **5,000건 초과** → 수집을 시작하지 않는다. 좁힐 축의 **실제 개수를 조회해서**
      함께 제시하고 사용자가 고르게 한다:

      > 데님팬츠는 24,673개다. 이대로는 너무 크다. 좁힐 방법:
      > - 성별 — 남성 N개 / 여성 N개 (조회해 온 실제 값. 유니섹스가 양쪽에 중복 집계돼
      >   절반이 되지 않는 사이트도 있다)
      > - 가격대 — 예: 10~20만원 N개 (무신사는 minPrice/maxPrice 확인)
      > - 세부 카테고리 — 후보와 개수
      >
      > 어느 범위로 할까? ("전체로 해"라고 답하면 전체를 진행하되 예상 소요를 먼저 말한다)

      상한 5,000의 근거는 목록 수집량이 아니라 **총 소요 시간**이다(핏 분류 중 이미지
      확인이 상품당 몇 초씩 든다). 상세는 SPEC §4를 따른다.

      **좁힐 축의 개수는 추정하지 말고 조회한다.** 29CM은 `listing/facet-group` 한 번이면
      소분류별·브랜드별·색상별 개수와 가격 범위·품절 개수가 전부 온다(어댑터 §2-2).
      무신사는 `gf`·`minPrice`/`maxPrice`를 건 `totalCount`로 축마다 센다.
   5. 최종 범위를 `meta.target`에 쓴다 — **"데님팬츠(남성)"** 형식.
      리포트 헤더에도 이 이름이 그대로 실린다. 좁혀 놓고 "데님팬츠 전수"라고 쓰면 거짓이다

   **임의 샘플링은 금지다.** 묻지 않고 상위 N개만 수집하는 것이 최악의 실패다 —
   사용자는 시장 전체를 봤다고 믿게 된다.
3. **목록을 끝까지 수집한다.** 후기 수·평점·좋아요 등은 목록에 노출된 값을 그대로 담는다.
   상품 상세는 목록에 없는 값이 꼭 필요할 때만 연다 — 상세 1만 번 열기는 목록 170번의
   수십 배 비용이다.
4. **속성 분류** — 근거가 확실한 순서로 시도한다.
   1. 상품명·옵션·상세 텍스트에 답이 있으면 그걸 쓴다 (예: 이름에 "부츠컷")
   2. **이미지를 보기 전에 색상 변형을 묶는다** — 같은 상품의 색상 전개가 각각 별개
      상품으로 올라오고, 색상은 핏을 바꾸지 않는다. 그룹당 한 번만 판단한다:

      ```bash
      python3 scripts/group_variants.py data/raw/<수집>.json --attr 핏 --plan data/plan.json
      # plan.json에서 value가 빈 그룹만 대표 이미지를 보고 채운다
      python3 scripts/group_variants.py data/raw/<수집>.json --attr 핏 --apply data/plan.json
      ```

      묶는 규칙은 **같은 브랜드 + 색상·품번·괄호를 뗀 이름 완전일치**다.
      유사도로 묶지 않는다(이 프로젝트가 실측으로 기각한 방법이다).
      실측 절감: 슬랙스 3,004개에서 미분류 1,492건 → **판단 1,071회(28% 감소)**.
      색상 전개가 많은 카테고리일수록 절감이 커진다
   3. 텍스트로도 그룹으로도 안 되면 대표 이미지를 내려받아 직접 보고 판단한다
   4. 그래도 모르겠으면 `"unknown"`. **찍지 않는다.**
      한 그룹에 서로 다른 값이 섞여 있으면(`conflict`) 전파하지 말고 직접 정한다

   핏 값(상품군과 무관하게 이 일곱 개다): `부츠컷` `와이드` `스트레이트` `슬림`
   `테이퍼드` `쇼츠` `unknown`.
   판단 근거를 `attributes_basis`에 `name`/`detail`/`image`/**`group`**/`unknown` 중
   하나로 남긴다. `group`은 **색상 변형 그룹에서 전파받은 값**이다 — 직접 본 것과 구분된다.

   **반바지는 `쇼츠`다** (2026-07-30 결정). 앞의 다섯 값은 긴바지의 레그 실루엣 축이라
   반바지에는 정답이 없다. 그대로 두면 `unknown`에 뭉치고(실측: 쇼츠 107개 중 96개가
   unknown) 어떤 건 `와이드`가 붙어 같은 종류가 갈린다.
   쇼츠는 한 축의 한 값이라 "와이드 쇼츠"는 표현되지 않는다(그 축을 쪼개지 않기로 한 결정).

   이름 신호(있으면 근거 `name`): `쇼츠` `숏츠` **`숏팬츠`** `반바지` `버뮤다`
   **`BURMUDA`(오타가 실제로 쓰인다)** `shorts` `하프` `N부`(2~5부).
   두 가지 함정을 실측으로 확인했다.

   - **`하프 밴딩`·`Half-band`는 기장이 아니라 허리 밴딩이다** — 긴바지로 둔다
   - `shorts` 뒤에 밑줄이 오는 이름이 많다(`A-line shorts_light blue`).
     단어 경계로만 찾으면 밑줄이 단어 문자라서 **놓친다**

   이름에 단서가 없어도 **대표 이미지에 무릎 위 기장이 보이면 `쇼츠`**이고 근거는 `image`다.
   허리만 찍힌 컷처럼 기장을 볼 수 없으면 `unknown`으로 둔다 — 찍지 않는다.

   **기본 분류 속성은 핏 하나다.** 워싱 톤·기장·소재 같은 추가 속성은 사용자가
   명시적으로 요청할 때만 넣는다 — 이미지 전수 확인이 필요한 속성은 상품 수 × 몇 초의
   비용이 드니 예상 소요를 먼저 알린다.
5. `story`는 `market-scan`. 검증 → 리포트는 공통 워크플로우대로.
   리포트가 후기 수 가중 평균 평점, 상품 평점 분포, 속성 분포를 자동으로 계산한다.
   **전수조사 표는 이미지 열을 포함해 전 행을 싣는다** (2026-07-30 결정 — 구 "이미지 열
   제외"는 폐기됐다). 썸네일이 `loading="lazy"`라 화면에 들어올 때만 받으므로 전 행을
   유지하면서도 한 파일로 열린다(3,460행 실측 4.1MB).
   **표는 `판매` 필터 축이 기본 판매 중만**이다 — 품절은 칩으로 켜고 건수가 칩에 찍힌다
   (조용히 숨기지 않는다). 카테고리·속성은 정렬 열이 아니라 **다중 선택 칩**이다.

   **성공 기준은 세 가지다**: 합의된 범위 완주(중단했으면 부분 리포트에 명시) ·
   **속성 분류율 80% 이상** · 후기 수·평점 결측이 실제 미노출과 일치(추정·보간 0건).
   분류율이 80%에 못 미치면 `validate_data.py`가 경고한다 — **경고를 지우려고 찍지 마라.**
   남은 것을 이미지로 채울지, 미달인 채로 낼지는 예상 소요를 알리고 사용자가 정한다.

### C. 랭킹 모니터링

이 스토리는 **동작이 두 개다.** 요청이 어느 쪽인지 먼저 가른다.

| 동작 | 트리거 예 | 하는 일 |
|---|---|---|
| **C-1 모니터링 시작** | "무신사 바지 랭킹 모니터링 시작해줘", "추적해줘", "스냅샷 찍어놔" | 스냅샷 1개 + 주기 실행 등록 |
| **C-2 변화 조회** | "무신사 바지 랭킹, 지난 일주일 변화 보여줘" (기간 있음) | 축적분에서 diff 리포트 |

**과거는 소급할 수 없다. 변화 분석의 재료는 축적분뿐이다.** 두 사이트 모두 현재 랭킹만
노출한다. C-2를 요청받았는데 그 기간의 스냅샷이 없다면 만들 수 없는 것이다 —
스냅샷 1개를 찍고 C-1(모니터링 시작)을 제안한다. 과거 랭킹을 추측으로 채우지 않고,
다른 출처로 대체하지도 않는다.

#### C-1. 모니터링 시작

1. **지금 즉시 스냅샷 1개를 찍는다** (아래 수집 규칙). 첫 스냅샷이 잘 찍히는 걸
   확인한 뒤에 등록으로 넘어간다 — 안 되는 파이프라인을 스케줄에 걸지 않는다.
2. **실행 환경의 스케줄 기능에 주기 실행을 등록한다.**
   - 주기는 **사이트의 원본 갱신 주기**를 따른다(어댑터에 명시돼 있다).
     갱신 주기보다 촘촘히 찍으면 같은 랭킹을 중복 저장할 뿐이다
   - 스냅샷 폴더는 **절대 경로로 고정한다** — 실행마다 폴더가 달라지면 축적이 흩어진다
3. **등록 내용을 보고한다**: 사이트 / 카테고리 / 주기 / 저장 경로.
4. 스케줄 기능이 없는 환경이면 등록할 수 없다고 말하고, 수동으로 주기 실행하는
   방법을 안내한다.

축적분은 전부 보존한다 — 오래된 스냅샷을 임의로 지우지 않는다.

#### C-2. 변화 조회

1. 기간을 절대 날짜로 해석하고, 축적분에서 비교한다.
   ```bash
   python3 scripts/diff_snapshots.py data/snapshots \
       --site musinsa --target 바지 --from 2026-03-01 --to 2026-03-31 --out data/diff.json
   python3 scripts/build_report.py data/diff.json --out output/ranking-diff.html
   ```
2. `diff_snapshots.py`가 `1`을 반환하면 기간 안에 스냅샷이 1개 이하라는 뜻이다.
   **빈 변화 리포트를 만들지 말고** 현재 스냅샷 리포트만 만든 뒤 C-1을 제안한다.
3. 기간 없이 "변화 보여줘"라고만 하면 스냅샷 1개를 찍고, 기간을 지정하면 조회할 수
   있고 모니터링 시작을 원하면 등록하겠다고 안내한다.

#### 공통 수집 규칙

1. 현재 랭킹 top 100을 모아 `data/snapshots/<site>-ranking-<카테고리>-<YYYYMMDD-HHmm>.json`로
   저장한다. `story`는 `ranking-snapshot`.
   **한 스냅샷은 한 시점의 목록이다** — 브라우저 스크롤 세션이든 한 번의 요청이든,
   **수집 도중에 시점이 섞이지 않게 한 번에 끝낸다.** 랭킹은 30분~1시간마다 바뀌므로
   중간에 멈췄다 이어 붙이면 서로 다른 시점의 순위가 한 스냅샷에 들어가고, 그 스냅샷으로
   만든 diff는 일어나지 않은 변화를 보고한다. 끊겼으면 이어 붙이지 말고 다시 찍는다.
2. 랭킹 목록에는 **"N명이 보는 중", "N명이 구매 중" 같은 실시간 지표**가 붙는 사이트가 있다.
   보이면 `viewers_now` / `buyers_now`에 담는다. diff 리포트가 이 값의 추이 차트도 그린다.
   - **이 지표는 랭킹 화면에만 있다.** 카테고리 목록·브랜드 목록·상품 상세에는 없다(실측).
     그래서 **스토리 A·B에서는 `null`이고 리포트에 "미노출"로 나간다** — 사용자가
     "조회수"를 물어도 랭킹에서 끌어와 채우지 않는다(출처가 섞이고 랭킹에 든 상품만
     채워져 일관성이 깨진다). 무엇이 미노출인지 알려주는 것이 맞는 응답이다
   - 모든 상품에 붙지도 않는다 — 랭킹 1,019건 중 `보는 중` 29~46%, `구매 중`은 0~3건이었다
3. **범위가 다른 스냅샷끼리 비교하지 않는다.** 폴백 등으로 랭킹 범위를 낮췄으면
   (예: 소분류 → 중분류) `meta.target`을 낮춘 이름으로 정직하게 저장한다 —
   `diff_snapshots.py`가 target이 다른 스냅샷을 자동으로 걸러내므로, 이름을 속이면
   서로 다른 랭킹이 섞인 diff가 만들어진다.

리포트의 판정 기준(전부 코드가 계산한다): 급상승/급하락 강조는 **랭킹 길이의 10%
(최소 3계단)** 이상 움직인 상품, 추이 차트는 시점이 48개를 넘으면 **균등 구간의
대표 스냅샷만** 골라 그린다(평균을 내지 않는다).

**가격·할인 변화는 상품별 마지막 관측 상태 대비로 감지한다** (2026-07-30 개정).
구 규칙("연속한 스냅샷 쌍에 둘 다 있는 상품만 비교")은 순위권을 드나든 상품을 통째로
놓쳤다 — 바지 33개 축적분 실측에서 등장 상품 679개 중 전 시점 상주는 **7개(1%)**뿐이라
연속 관측 쌍 2,621개 중 **71%만** 비교 대상이었고, 남아 있는 실제 변화 2건을 **0건으로
보고**했다. 요약 해상도와 무관하게 **원본 전체 해상도**로 감지하는 것은 그대로다.

- **관측 창을 사건마다 기록한다** — `from_at` · `to_at` · `gap_snapshots` · `exact_at`.
  결석이 0이면 시점을 단일로 찍고, 아니면 `A ~ B 사이 (N시간 · 스냅샷 M개 결석)`로 낸다.
  **창 길이에 상한을 두지 않는다** — 잘라내면 그것도 조용한 누락이다
- **밝혀야 하는 한계 2개**: 결석 구간에서 여러 번 변했으면 순변화 1건으로 뭉쳐지고,
  변했다 원래대로 돌아왔으면 아예 잡히지 않는다(순위권 밖은 관측 자체가 없다)

## 지켜야 할 규칙

**요청 속도** — 페이지 사이에 0.5~1.5초 쉰다. 병렬로 몰아치지 않는다.

**순회 상한** — 상한은 **상품 수 하나뿐이다**(스토리1 3,000 / 스토리2 5,000 / 스토리3 top 100).
페이지 수·스크롤 횟수로는 끊지 않는다 — 페이지 크기가 사이트마다 다르고 스크롤은 한 스텝이
몇 개인지 정해져 있지 않아서, 같은 숫자가 사이트마다 다른 양을 뜻한다.
무한 루프는 **3연속 무증가**(§브라우저로 목록을 모으는 방법)와 직전 페이지와 동일 항목
검사로 막는다. 상한에 닿아 끊었으면 `meta.notes`에 적고 **목록이 끝난 것과 구분한다**.

**재시도** — 실패하면 간격을 늘리며 2번까지 다시 시도한다. 3번 연속 실패하면 그 항목을
건너뛰고 `meta.notes`에 남긴다.

**차단** — 403/429/캡차가 나오면 **즉시 멈춘다.** User-Agent를 바꾸거나 우회하지 않는다.
`meta.incomplete`를 `true`로 두고 중단 지점을 `meta.notes`에 적은 뒤 부분 리포트를 만든다.

**로그인** — 비로그인으로 보이는 것만 모은다. 로그인 벽이 나오면 거기서 멈추고 알린다.

**구조 변경** — 필수 필드가 자꾸 비면 사이트가 바뀐 것이다. `validate_data.py`가 30%를
넘겨 `2`를 반환하면 수집을 계속하지 말고 어댑터의 필드 매핑부터 확인한다.

**하지 않는 것** — 구매·장바구니·찜 등 상태를 바꾸는 조작, 로그인 전용 데이터,
판매량 추정, **유사도·가격으로 추정하는 플랫폼 간 상품 매칭**(완전일치 매칭은 하며 규칙은
§A에 있다), 이미지 재배포(리포트는 원본 URL을 링크할 뿐이다).

## 데이터 계약

수집 JSON은 항상 이 모양이다. 스크립트가 이걸 전제로 동작한다.

```json
{
  "meta": {
    "site": "musinsa",
    "story": "brand-linesheet",
    "target": "인사일런스",
    "collected_at": "2026-07-29 14:00:00",
    "item_count": 2022,
    "source_total": 2022,
    "incomplete": false,
    "notes": ["경로 B: 브라우저 순회. 품절 포함(isSoldOut=true) 상태의 화면 총계 2,022와 대조"]
  },
  "items": [{
    "product_id": "4297589",
    "name": "...", "url": "https://...", "image_url": "https://...",
    "brand": "인사일런스", "category": "데님팬츠",
    "price_original": 139900, "price_sale": 97890, "discount_rate": 30,
    "review_count": 212, "rating": 4.8,
    "view_count": null, "view_count_display": "300회 이상 (최근 1개월)",
    "purchase_count": 5500, "purchase_count_display": null,
    "like_count": 84, "like_count_display": null,
    "viewers_now": null, "buyers_now": null,
    "sold_out": false,
    "rank": null,
    "attributes": {"핏": "와이드"}, "attributes_basis": "name"
  }]
}
```

| 필드 | 언제 필수인가 |
|---|---|
| `product_id` `name` `url` `image_url` `brand` `category` `price_original` `price_sale` `discount_rate` `sold_out` | 항상. 결측률 5%를 넘으면 경고, 30%를 넘으면 수집 실패로 본다 |
| `review_count` `rating` `view_count` `purchase_count` `like_count` `viewers_now` `buyers_now` | 사이트가 보여줄 때만. **안 보이면 `null`** |
| `view_count_display` `purchase_count_display` **`like_count_display`** | 사이트가 **구간**(`300회 이상`)이나 **축약**(`1.2천`)으로만 보여줄 때. 아래 참조 |
| `rank` | 스토리 C |
| `attributes` `attributes_basis` | 스토리 B |

`reviews[]`(리뷰 본문)는 **수집하지 않는다.** 담겨 있으면 검증기가 경고한다.

`rating`은 **5점 만점으로 통일한다.** 사이트가 100점 척도로 주면 나눠서 넣는다(어댑터 참조).

### 판매가는 전 회원 공통 쿠폰적용가다 (2026-07-30 개정)

`price_sale`은 **비로그인 화면에 그대로 찍히는 쿠폰적용가**다. 개인화 가격이 아니라 누구나
받는 할인가이므로 재현되고 상품 간 비교도 성립한다. 할인이 없으면 `price_original`과 같다.

**근거는 사이트마다 다르다.** 무신사는 상세의 안내 문구("모든 회원이 사용 가능한 상품 쿠폰 중
최대 할인 쿠폰을 기준으로 산정")로 확인했다. **29CM에는 그런 문구가 아예 없어서 쿠폰 조건을
전수 확인해 판정했다** — 가격을 정하는 상품쿠폰 43건이 전부 무조건부(첫구매·등급·신규·앱전용
0건)이고 선착순 총량 제한도 없었다(2026-07-30 브라우저 실측, 어댑터 참조).

- **쿠폰 전 판매가를 담지 마라.** 무신사 로우클래식 261개 실측에서 쿠폰 전 값으로는 할인 중이
  **4개**였는데 쿠폰적용가로는 **115개**였다. 5% 쿠폰이 걸린 102개를 "할인 없음"으로 기록하게 된다
- `discount_rate`도 **같은 기준**이어야 한다. 가격은 쿠폰가인데 할인율은 쿠폰 전 값으로
  섞으면 둘이 어긋나고 `validate_data.py`가 경고한다
- **개인 쿠폰가는 담지 않는다.** `"보유 쿠폰에 따라 더 높은 할인이 적용될 수 있습니다"`는
  사람마다 다르므로 재현되지 않는다. 화면에 **「나의 구매 가능 가격」·「첫 구매가」**처럼
  따로 찍히는 값도 같다 — 앱전용·신규회원 한정 쿠폰이 얹힌 값이라 판매가가 아니다.
  **필드 이름이 그럴듯해도 화면 메인 판매가와 같은 값인지 대조해라**(29CM 실측 55% 불일치)
- 사이트별 필드는 어댑터에 있다 — 무신사 `finalPrice`/`finalDiscount`,
  29CM `displayPrice`/`saleRate`. **구 규칙(쿠폰가는 판매가로 치지 않는다)은 폐기됐다**

### 축약은 정수로 담고, 구간은 문구 그대로 담는다

사이트가 정확한 수를 안 보여주는 방식이 두 가지인데 **오차 성질이 달라서 처리도 다르다**
(2026-07-30 개정).

| 표기 | 예 | 참값 범위 | 어떻게 담나 |
|---|---|---|---|
| **축약** | `1.2천` · `판매 9만개` | 1,150~1,249 · 635,000~644,999 | **정수로 파싱해 담는다** (`천`=×1,000 · `만`=×10,000). 원문도 `*_count_display`에 함께 담으면 좋다 |
| **구간** | `300회 이상 (최근 1개월)` | 300~**∞** | **정수로 바꾸지 마라.** 정수 칸은 `null`, 원문만 `view_count_display`에 |

축약은 반올림이라 오차가 **±4% 안에 갇히고** 그 정도로 뒤집히는 판정이 이 스킬에 없다.
구간은 상한이 없어서 `300회 이상`을 300으로 담으면 **오차가 무한**이다 — 여기서만 금지다.

- **구간 원문과 정수를 같이 담으면 검증기가 경고한다.** 축약 원문과 정수는 병기해도 통과한다
- **정확값을 주는 경로가 있으면 그쪽이 낫다** — 좋아요는 무신사 하트 배치 API가 정수를 준다.
  경로 A로 보완했으면 `meta.notes`에 남긴다
- 리포트는 축약에서 온 값임을 각주로 밝힌다. **파싱을 허용한 것이지 정밀도가 생긴 게 아니다** —
  자릿수 규모의 비교에만 쓴다
